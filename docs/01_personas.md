# ペルソナ

本書は本システムの想定ユーザー像を具体的な人格として定義する。
要件定義・機能優先度・UX判断で迷ったときの拠り所とする。

全体方針は [it-hazy-comet.md](../../../../../Users/nakasita/.claude/plans/it-hazy-comet.md) を参照。

> 本書は **要件定義・画面設計より上流** のドキュメントである。
> したがって本書には、**本システム固有の機能名・画面名・実装手段を一切書かない**。
> ここに書くのは「誰が」「どんな状況で」「何に困っていて」「何を実現したいか」だけであり、
> それをどんな機能で実現するかは要件定義以降で決める。
> 機能は本書を根拠に決められるが、本書を機能に合わせて書き換えてはならない。

## P1: 田中 太郎(たなか たろう)― 長男・家族の主担当

### プロフィール
- 58歳、男性、東京都世田谷区在住
- 家族構成: 妻、長女(高校生)、長男(大学生)
- 職業: 食品メーカー部長、平日多忙
- 父(一郎・85歳・入居者)を愛媛から呼び寄せ、自宅近くの介護施設に入居させた
- 母(P2 ハナ子)は松山に残り独居、妹(恵子)は東京在住

### 介護への関与
- **家族の中で連絡窓口役**(母・妹・姪への情報共有も自分の役目)
- 月1〜2回、土曜日に車で面会
- 平日は朝7時〜夜9時まで仕事、電話対応は昼休みのみ
- 施設からの電話は出られないことが多く、伝言+折り返しが常態化

### ITスキル
- Google Workspace、SAP、Slack を業務で使用
- iPhone(個人)、Pixel(業務)、両方で通知過多
- LINE、Gmail はチェックする / Facebook は使わない

### 一日の典型(平日)
```
07:00 出社移動                ← 通勤電車内でメール・LINE
08:30 会議
12:00 昼食                    ← 唯一電話に出られる時間
13:00 会議
19:00 帰宅                    ← 帰宅後は子供の世話、通知に手が回らない
22:00 就寝前にLINE             ← 1日分の通知をざっと見る
```

### Need(満たしたいこと)
- 父の様子を **隙間時間に手軽に知りたい**(通勤電車内 / 寝る前)
- 母や妹・姪にも **同じ情報が届いてほしい**(現状は自分が転送する手間)
- 発熱・転倒など何か起きたときは **すぐ気づきたい**
- 面会に行く前に、最近の父の様子を **おさらいしておきたい**(会話の糸口が欲しい)

### Pain(現状の困りごと)
- 施設から電話が来ても出られない → 折り返したら担当者不在 のループ
- 妹から「お父さんどう?」と聞かれても、自分も最新情報を持っていない
- 紙の連絡帳は面会時にしか見られない
- 写真がなく、日々の雰囲気がわからない

### 代表的クォート
> 「電車の中で父の写真が1枚届くだけで、その日1日が違うんです。」

### 期待・配慮ポイント
- **移動中のスマホ利用が中心**(PCの前に座って見ることはない)
- 通知は **まとめて1日数回** が良い(1件ごとの連打はつらい)
- 片手・親指だけで完結する操作量に収めたい
- 見た情報を **他の家族にそのまま渡せる** こと

## P2: 田中 ハナ子(たなか はなこ)― 妻・最も配慮が必要な家族

### プロフィール
- 82歳、女性、愛媛県松山市在住、独居
- 家族構成: 夫(一郎・85歳・入居者)、長男(P1 太郎・東京)、長女(恵子・東京)、孫4人
- 夫が認知症で東京の施設に入居後、自宅で一人暮らし
- 自身の持病の関係で松山から離れにくく、面会は2〜3ヶ月に1回

### 介護への関与
- 心配性、夫の様子を毎日知りたい
- 自分も健康に不安があり、いつまで面会に行けるか先々の不安
- 息子(太郎)経由でしか情報を得られていない

### ITスキル
- **ガラケー併用**(電話は古い携帯)、最近スマホ(子のお下がりのiPhone SE)を導入
- スマホ用途: **LINE のみ**(息子・娘・孫からのメッセージ受信)
- メールアドレスは持っているが使えない
- アプリのインストール、パスワード入力でつまずく
- 文字サイズは最大設定、それでも読みにくい

### 一日の典型
```
06:30 起床、新聞
08:00 朝食
10:00 デイサービス(週3)
15:00 帰宅
16:00 ご近所さんとお茶
17:00 夕食
19:00 LINEチェック(息子からの連絡)
21:00 就寝
```

### Need
- 夫の写真と「今日も元気でした」の一言を **毎日ひとつ見たい**
- 世話をしてくれる職員に **「ありがとう」を伝えたい**
- 自分から探しに行かなくても **情報が向こうから届く** 状態がいい

### Pain
- 施設からの連絡は窓口である息子(太郎)にだけ行き、自分に直接届くことはない
- 息子(太郎)が忙しく、夫の様子を聞けないまま何週間も過ぎる
- スマホの操作が苦手で、新しいアプリは怖い
- パスワードを忘れる、再発行の手続きでつまずく
- 難しい言葉・カタカナ語が出てくると、そこで手が止まる

### 代表的クォート
> 「主人の顔が見られれば、それだけで安心できます。難しいことはできません。」

### 期待・配慮ポイント ★最重要★
- **パスワードを覚える・入力することが実質的に不可能** — 認証手段は本人に記憶や入力を求めない方式である必要がある
- 文字は大きく、写真は大きく。**1画面に情報を詰め込まない**
- 押し間違えない大きさの操作要素、**複雑な操作(横スワイプ・階層移動)を前提にしない**
- 通知文は **技術用語を使わない自然な日本語**(例:「お父さんの様子が届きました」)
- **説明を読まなくても使える** こと(初回の手順が多い時点で脱落する)
- お下がりの古い機種でも軽快に動くこと
- 感謝を伝える手段は、文章を書かせない(**一押しで気持ちが伝わる**)形が現実的

## P3: 鈴木 美咲(すずき みさき)― 孫・遠方在住の若手家族

### プロフィール
- 28歳、女性、福岡市在住
- 家族構成: 独身、一人暮らし。母は鈴木 恵子(太郎の妹)、両親は東京
- 職業: Web デザイナー(リモートワーク中心)
- 入居者・一郎の孫(長女 恵子の娘)
- 物理的に遠く、年1回お盆に帰省して施設に顔を出す程度

### 介護への関与
- 直接の介護にはノータッチ
- でも「祖父を大切にしたい」気持ちは強い
- 母(恵子)経由で時々様子を聞く

### ITスキル
- **デジタルネイティブ**
- Instagram、X、TikTok、Slack、Figma、Notion
- iPhone、MacBook Pro
- 通知はカテゴリ別に細かく管理

### 一日の典型
```
08:00 起床、SNS チェック
09:00 仕事開始(リモート)
12:00 昼食、SNS
18:00 仕事終了
20:00 友人とビデオ通話 / ジム
23:00 就寝前にSNS、動画
```

### Need
- 祖父の **日常の "素" の様子** を見たい(かしこまった報告ではなく)
- **軽いタッチで関与** したい(長文を書くほどの関与はできないが、無関心ではない)
- 帰省前に祖父の最近の **エピソードを把握** したい(会話の糸口)
- 自分が知っている祖父のこと(好物・昔話)を **施設側にも伝えたい**

### Pain
- 既存の介護記録系サービスは **画面が業務システム感** で温度がない
- 母経由のLINEでしか情報が来ないが、母も毎週送ってくれるわけではない
- 自分も家族の輪に入りたいが、入り方がわからない

### 代表的クォート
> 「SNSの投稿みたいに、祖父の"今日"が見られたらいいのに。」

### 期待・配慮ポイント
- **モダンでミニマル** なデザイン期待値が高い(業務システム然としていると使わない)
- 写真が主役の見せ方
- 反応の返し方は **軽く・カジュアルに**(堅い定型文はNG)
- 通知はリアルタイムで来てもよいが、**自分で頻度を調整できる** こと

## P4: 山田 さくら(やまだ さくら)― 介護福祉士・現場の主役

### プロフィール
- 32歳、女性、東京都調布市在住
- 家族構成: 夫、子供(5歳、2歳)
- 職業: 介護福祉士、勤続5年目
- 勤務: 早番 / 遅番 / 夜勤 のシフト制、月160時間

### 担当業務
- 入居者 8〜10名を担当(プライマリーケア制)
- 食事介助、入浴介助、排泄介助、レクリエーション、記録
- 1日のうち PC の前に座れるのは1時間程度

### ITスキル・端末環境
- **スマホは LINE、Instagram、メルカリ**(いずれも私物)
- 業務 PC は既存の介護記録ソフト(ほのぼのNEXT)を入力するだけ
- タイピング遅め(片手フリック入力の方が早い)
- **業務用のスマホは支給されていない**。入居者の写真は施設共用のカメラで撮り、事務室PCに取り込む(私物スマホでの撮影は個人情報の持ち出しにあたるため施設ルールで禁止)

### 一日の典型(早番:6:30〜15:30)
```
06:30 出勤、夜勤者からの申し送り
07:00 朝食介助
09:00 バイタル測定、入浴介助
11:30 昼食介助
13:00 レクリエーション(歌、塗り絵)
14:30 介護記録入力(端末は事務室のPC、空き待ち)
15:30 退勤
```

### Need
- 家族への近況共有を **1分以内** に終わらせたい(業務の合間で)
- 手元のスマホだけで完結したい(事務室PCは取り合い)
- 「家族からのありがとう」をもらえると **頑張れる**
- 担当入居者の **人となり(好物・昔の仕事・思い出)を知りたい** — ケアや会話に活きる

### Pain
- 記録ソフトに付いている家族向けの連絡機能は事務室のPCからしか入力できず、業務時間内に書ききれない
- 家族からの感謝が届く仕組みがなく、自分の仕事の意義を感じにくい
- 書く内容に気を遣う(クレーム化を恐れる)→ 結局書かなくなる
- 業務が中断されるのが前提の職場(呼び出しが常時入る)

### 代表的クォート
> 「『今日もありがとうございました』の一言でも書こうと思うのに、PCの前に座る時間がないんです。」

### 期待・配慮ポイント
- **スマホ前提**(PC操作を前提にした運用は現場で回らない)
- 撮る → 短く書く → 家族に届く、までを **片手で** 完結させたい
- **中断に耐える**(呼び出しで離席しても、書きかけが消えない)
- 文章を書くハードルを下げる工夫が要る(**文例からの選択**など、ゼロから書かせない)
- 家族からの反応が本人に返ってくること(**報われる感覚**の設計)
- 完璧な日本語を強要しない雰囲気(誤字を怖がらせない)

## P5: 中村 浩二(なかむら こうじ)― 施設長・導入の意思決定者

### プロフィール
- 48歳、男性、施設のある世田谷区在住
- 家族構成: 妻、子供2人
- 職業: 介護福祉士 → 主任 → 施設長(現職5年目)
- 入居定員80名規模の有料老人ホームを統括

### 役割・関心
- 経営、職員管理、家族対応、自治体対応
- **家族からのクレーム対応** に最も時間を取られる
- 離職率の低下が KPI(慢性的な人手不足)
- **「選ばれる施設」** にするための差別化施策を常に考えている

### ITスキル
- 中(業務PCで Excel、Word、メール、ほのぼのNEXT)
- スマホは Gmail、LINE、ニュースアプリ
- 新システムの導入判断ができるリテラシー
- ただし **複雑な設定や運用は職員に任せたい**

### 一日の典型
```
08:30 出勤、夜勤者と申し送り確認
09:00 メール対応、家族からの問い合わせ
10:00 ケア会議
12:00 昼食、休憩
13:00 自治体報告書類
15:00 家族との面談(月数件)
17:00 翌日のシフト確認
18:30 退勤
```

### Need
- **家族満足度の向上**(クレームを未然に防ぎたい)
- **職員のモチベーション維持**(離職を減らしたい)
- **施設の差別化要素**(入居検討者へのアピール材料)
- **導入・運用の手間が小さい**(自分たちで回せる範囲に収まること)
- **入居者・家族の情報を自施設側で管理できる**(個人情報を外部事業者に預けたくない)
- 現場の利用状況を **ざっくり把握したい**(定着しているのか、していないのか)

### Pain
- 既存ベンダーの家族向けサービスは月額数十万円 → 施設規模に見合わない
- LINE公式アカウントで代用しているが、職員ごとに対応が分かれて統一感がない
- 「写真を載せて」と現場に頼んでも、職員の負荷が増えるだけで定着しない
- 自治体・法人への報告のたびに、手作業で数字をまとめている

### 代表的クォート
> 「家族が安心していると、現場の負担も結局減るんです。クレーム電話が減れば、その時間をケアに回せる。」

### 期待・配慮ポイント
- 管理者向けの画面は **情報密度が高くてよい**(P1〜P4と違い、業務時間にPCの前で見る)
- 集計値が一目でわかること
- **既存の報告業務に転用できる形でデータを取り出せる** こと
- 導入手順の説明が **日本語で丁寧**(英語ドキュメントだけでは判断・実行ができない)
- 導入作業は「IT に強い職員1人が数時間でできる」程度に収まってほしい

## ペルソナ間で衝突する論点(要件定義への申し送り)

以下はペルソナ同士の要求が真っ向から対立する点。**ここでの結論は要件定義で出す**ため、本書では論点のみを記録する。

### 論点1: 家族への情報の届け方(頻度)
- P1(太郎): まとめて1日数回がいい。1件ずつ通知が来ると埋もれる
- P2(ハナ子): 様子があれば都度知りたい。ただし通知設定を自分で変えることはできない
- P3(美咲): リアルタイムで来てもよい。頻度は自分で調整したい
- → **デフォルト値と、設定変更を誰に許すかが論点**

### 論点2: 家族の本人確認の方法
- P2(ハナ子): パスワードの記憶・入力が実質不可能。ここが解けないと P2 は使えない
- P1(太郎)/P3(美咲): 一般的な方式で問題ない
- → **最も弱いユーザー(P2)に合わせると、セキュリティ要件との緊張が生じる**

### 論点3: 職員の入力負荷と、家族が欲しい情報量のギャップ
- P4(さくら): 1分以内。項目が増えるほど書かなくなる
- P1・P2・P3: 情報は多いほど嬉しい
- → **「職員が書ける量」が上限。家族の要望を足しすぎない歯止めが要る**

### 論点4: 情報の公開範囲
- P4(さくら): 誰に見せるかを毎回選ぶのは負荷
- P5(中村): 運用が分岐すると事故る。一律が望ましい
- P1(太郎): 親族間で共有したい(見せる相手を自分で増やしたい)
- → **範囲の指定を「誰が・いつ」やるのかが論点**
