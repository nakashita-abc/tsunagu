# ADR（Architecture Decision Records）

本書は、本システムの**設計判断とそのトレードオフ**を1件ずつ記録する。

> **なぜ要件定義から分けるか。**
> [05_要件定義.md](05_要件定義.md) は「**何を満たすか（What）**」に徹し、製品名を書かない（step4）。
> 一方で「どう実現するか（How）」には、**別の選択肢がありえた判断**が必ず含まれる。その判断を要件の中に埋めると、後から読んだときに*要件だったのか、選択の結果だったのか*が区別できなくなる。
> 本書は**選択の結果**だけを集め、「なぜそちらを選ばなかったか」と「何を代償として引き受けたか」を残す。
>
> **記録の対象**：技術選定だけでなく、**MVPのスコープを削る判断**も含める（削ったことも設計判断であるため）。
> **ステータス**：`提案` → `承認` → （`置換` / `撤回`）。撤回したADRは**消さずに残す**。

## ADR-001: 提供側が運用する共有環境に、施設をテナントとして収容する

**ステータス**：承認（2026-08-24） ／ **関連**：[04_to-be.md](04_to-be.md) 4章・NFR-47・NFR-71〜73

### 文脈
データをどこに置くかで2案があった。**モデルA**＝施設が自らクラウドを契約し、そこに施設のデータを置く（施設ごとに独立した環境）。**モデルB**＝提供側が運用する1つの共有環境に、複数施設をテナントとして収容する。
当初はモデルAを採っていた。根拠は「P5 は個人情報を外部事業者に預けたくない」という想定である。

### 決定
**モデルB を採る。施設はクラウドの契約も環境構築も行わない。**

### 根拠
1. **モデルAの根拠が未検証の仮説だった。** 「施設が自らクラウドを契約したい」は実地のヒアリングではなく、こちらが置いた想定にすぎない。裏付けのない仮説を守るために設計を縛っていた（[01_ペルソナ.md](01_ペルソナ.md) 改訂の記録）。
2. **導入体験と正面から衝突する。** モデルAでは施設側に契約手続き・支払い情報の登録・初回パラメータ入力が残る。IaC で自動化しても消えない。**最も弱いユーザーに合わせるという原則を、導入の局面だけ適用しないのは一貫していない。**

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| モデルA（施設がクラウドを契約） | 上記2。導入の入口に技術作業を置いた時点で P5 は止まる |
| 施設内に物理サーバーを設置 | 固定費と運用負荷が発生し G軸に反する（NFR-72） |

### 結果（引き受けた代償）
- **既存手段に対する差別化が C（P2適合）と G（コスト）の2点に絞られた。** データを施設側に置けることは、もはや売りではない（[03_既存サービス比較.md](03_既存サービス比較.md) F軸＝撤回・欠番）。
- **施設間の分離がアプリケーション側の責任になった**（NFR-47）。インフラの契約境界に頼れない。
- **個人情報の管理主体が、施設単独から提供者との共同体制に変わった**。責任分界の明示が新たに必要になった（NFR-56）。
- ロックイン回避のため、施設がデータを取り出せることを要件として残した（FR-601）。

### 未決（step5 へ）
テナント分離の**実装方式**（行レベルのアクセス制御／スキーマ分割／アプリ層フィルタのどれか）は未決。[05_要件定義.md](05_要件定義.md) U6。

## ADR-002: 認証基盤に Amazon Cognito User Pools を採用する

**ステータス**：承認（2026-09-12。[ADR-012](#adr-012) を受けて根拠を更新） ／ **関連**：FR-401・AC-B1〜B5・NFR-46・NFR-76・C6

### 文脈
本プロジェクトは個人開発・OSSであり、**専任の運用担当を置けない**（C6）。トークンの署名鍵の管理・失効・ローテーション・試行回数の制限を自前で持つのは、運用負荷の面で割に合わない。
加えて、家族のアクセスを**施設側から即時に失効できる**こと（AC-B5）が要件にある。

> **注**：本ADRは当初、記憶・入力を求めない認証（旧 AC-A1〜A4）を実現する基盤として Cognito を選んだ。その要件は [ADR-012](#adr-012) で MVP から外れたが、**Cognito を選ぶ判断自体は変わらない**（根拠3・4を参照）。以下は ADR-012 の決定を反映した現在の記述である。

### 決定
**Amazon Cognito User Pools を認証基盤として採用する。** ただし Cognito の Managed Login（ホストされたサインイン画面）は使わず、**API としてのみ利用し、画面はすべて自前で作る。**

### 根拠
1. **鍵管理・トークン発行・失効を自前で持たずに済む**（C6）。
2. **無料枠が要件に対して十分広い。** ユーザープールは Lite / Essentials の各プランで **10,000 MAU まで無料**。1施設あたり家族200名＋職員50名＝250 MAU 想定（NFR-36）なので、**単純計算で 40 施設まで認証費用が発生しない**。NFR-76（月額1万円上限）に対して余裕がある。
3. **標準機能だけで MVP の認証が成立する。** 管理者によるユーザー作成と招待、パスワードの初期設定と再設定、試行回数の制限、失効——[ADR-012](#adr-012) が必要とするものは、いずれも自前で作らずに済む。**実装難易度を下げるという ADR-012 の目的に、そのまま合致する。**
4. **次段で記憶・入力を求めない方式へ移る余地を残せる。** カスタム認証フロー（`DefineAuthChallenge` / `CreateAuthChallenge` / `VerifyAuthChallengeResponse`）により、任意のチャレンジ方式を後から実装できる。次段で [ADR-004](#adr-004) を再開するとき、**認証基盤を載せ替えずに済む**——これは Cognito を選ぶ理由のうち、ADR-012 の後に**かえって重みを増した**点である。
5. **Managed Login（ホストされたサインイン画面）を使わない理由**：NFR-1群（文字サイズ・語彙・タップ領域）を家族向けの全画面で一貫させるため、および OAuth のリダイレクト往復をアプリに持ち込まないため。ログイン画面の実装コスト自体は小さい。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 自前でセッションを実装（Cookie＋DB） | 最も自由だが、失効・監査・鍵管理・セッション固定攻撃対策をすべて自前で持つ。C6（運用担当を置けない）に反する |
| Auth0 | マジックリンクが標準機能で最も楽。ただし MAU 課金が施設数に比例して重くなり、NFR-76 の上限に早期に到達する |
| Firebase Authentication | 無料枠は広くマジックリンクも標準。ただし他の構成要素（DB・ストレージ）と合わせると実質 Google Cloud 前提になり、ADR-003 のテナント設計と噛み合わせにくい |
| Auth.js（NextAuth） | ライブラリであり、結局セッションストア・失効・監査を自前で設計することになる。自前実装と同じ問題 |

### 結果（引き受けた代償）
- **AWS への依存が生じた。** OSSとして公開したとき、施設が自前で運用する選択肢（[04_to-be.md](04_to-be.md) 4章）は「AWS 上で」に狭まる。**引き受ける**——自前運用は元々の主眼ではなく、ロックイン回避の主目的（データを取り出せること＝FR-601）は満たせる。
- Cognito 側のエラーメッセージ・文言は英語ベースだが、**画面は自前なので NFR-13 には影響しない**。Cognito 由来のエラーをそのまま露出させないことを設計時の注意点とする。
- ~~Lambda 関数3本が運用対象に加わった~~ — [ADR-004](#adr-004) の撤回により**解消**。MVP は Cognito の標準機能のみを使い、カスタムの Lambda トリガーを持たない。

## ADR-003: 全施設を単一のユーザープールに収容する

**ステータス**：承認（2026-09-12） ／ **関連**：ADR-001・NFR-41・NFR-42・NFR-47・NFR-71

### 文脈
ADR-001 により複数施設が1つの共有環境に同居する。Cognito では、**施設ごとにユーザープールを分ける**構成も、**1つのプールに全施設を収容する**構成も取れる。前者は分離をインフラの境界で担保でき、後者はアプリ側の実装で担保することになる。

### 決定
**単一のユーザープールに全施設のユーザーを収容する。** 施設は属性（テナント識別子）で区別し、**施設間の分離はアプリケーション側で担保する。**

### 根拠
1. **施設ごとにプールを分けると、施設を1つ増やすたびにプール作成が必要**になる。これは NFR-71（施設は環境構築を行わない）を提供側の運用作業として吸収することを意味し、C6（専任の運用担当を置けない）と衝突する。
2. **無料枠はプール単位ではなくアカウント単位の 10,000 MAU** であるため、プールを分けても費用面の利得がない。
3. ADR-001 で**分離はアプリケーション側の責任**と決めている（NFR-47）。認証だけインフラ境界に頼ると、**分離の担保箇所が2系統に分かれ、どちらが正なのかが曖昧になる。** 一系統に寄せる。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 施設ごとにユーザープールを分ける | 分離は強くなるが、施設追加のたびに環境操作が発生し運用が重い。上記1・3 |
| プールは1つ、アプリはテナントごとに分けて配置 | MVPの規模に対して過剰。デプロイ対象が施設数に比例する |

### 結果（引き受けた代償）
- **テナント越境の防止が、アプリ実装の正しさに全面的に依存する。** 1箇所の実装漏れが越境事故に直結する。
- 緩和策を設計に持ち込むことを必須とする：**トークンにテナント識別子を載せ、データアクセスを一箇所（DAL）に集約して、テナント条件の付与を個々のクエリの書き手に委ねない。** 実装方式は step5（U6）で決める。
- あわせて、**越境を検出できるようにする**（NFR-45 の操作記録）。防止だけに賭けない。

**ステータス**：**撤回**（2026-09-12、[ADR-012](#adr-012) による） ／ **関連**：旧 AC-A1〜A3・論点2

> **本ADRは撤回された。** 記憶・入力を求めない認証そのものが MVP の必須要件から外れたため、その実現方式を決める本ADRも効力を失う。
> **消さずに残す理由**：本ADRの**代替案の比較（メールOTP／パスキー／SMS／LINEログイン）は、次段で AC-A を復活させるときにそのまま使える**。[05_要件定義.md](05_要件定義.md) U10 はここを参照している。
> 以下は撤回時点の記述をそのまま残す。

### 文脈
AC-A1 は「**最初の投稿を見るまでに文字入力が0回**」を求める。この1行が、一般的な認証方式のほとんどを落とす。
Cognito がネイティブに提供するパスワードレス方式は **メールOTP / SMSOTP / パスキー**だが、OTP は6桁のコード入力を伴うため AC-A1 を満たさない。
さらに P2（82歳）は「**メールアドレスは持っているが使えない**」（[01_ペルソナ.md](01_ペルソナ.md)）。**メール配信を必須経路に置いた時点で、最重要ユーザーに届かない。**

### 決定
1. Cognito の**カスタム認証フロー**（`DefineAuthChallenge` / `CreateAuthChallenge` / `VerifyAuthChallengeResponse`）で、**マジックリンク**方式を実装する。
2. **リンクの配信経路をシステムが持たない。** 施設管理者が家族ごとに一度きりのリンク（QRコード／短縮URL）を発行し、**渡し方は施設の運用に委ねる**。システムはメールもSMSも送らない。

### 根拠
- **「システムが配信しない」ことが、P2 に届く唯一の現実解である。** 実際に P2 に到達する経路は、(a) 施設が面会・郵送で紙のQRコードを渡す、(b) 息子（P1）が LINE でリンクを送る——のどちらかである。どちらも**P2 がすでに到達できる手段**であり（FR-402）、システムが新しいチャネルを増やす必要がない。
- **メール到達性の問題を丸ごと回避できる。** 迷惑メール判定・送信ドメイン認証・バウンス処理は、個人開発の運用負荷（C6）として無視できない大きさがある。それを設計から消せる。
- **家族の連絡先の正確さに依存しない。** C5（家族の連絡先は施設長が Excel 管理、**仮定・要検証**）が崩れても、対面で渡せば届く。
- リンクをタップするだけなので、**文字入力0回（AC-A1）・3ステップ以内（AC-A2）**を満たす。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| メールOTP（Cognito ネイティブ） | 6桁コードの入力が必要。**AC-A1 違反**。加えて P2 はメールを使えない |
| パスキー / WebAuthn | 入力は0回になるが、**初回登録の導線が P2 には重い**（生体認証の設定・OSの同意ダイアログ）。NFR-31（発売5年程度の端末）で挙動が読みにくい。**次段で「2台目以降の端末を追加する手段」として再検討する** |
| SMS でマジックリンクを配信 | 有効だが、電話番号を名簿で正確に持つ必要があり C5 に依存する。1通ごとの費用も乗る。**本決定と両立するため、必要になれば後から配信経路として追加できる** |
| LINE ログイン連携 | P2 が唯一使いこなせるUIで魅力的。ただし**特定事業者のアカウント保有が入口の必須条件になる**のは避ける（家族全員が LINE 利用者とは限らない）。将来の追加経路の候補 |
| ID／パスワード | 論点2そのもの。P2 が初回で脱落する |

### 結果（引き受けた代償）
- **リンクを「渡す」瞬間が、この設計で最も弱い点である。** 紙を落とす、LINE の誤送信で第三者に渡る——いずれも起こりうる。次で緩和するが、**ゼロにはならない**。
  - リンクは**一度きり**（引き換え済みのリンクは無効）
  - 発行から**短期間で失効**（7日を初期値とする）
  - 引き換え後は**その端末でのみ有効**
  - 施設管理者が**いつでも失効**できる（FR-405）
  - 万一到達しても、見えるのは**その入居者の日常の様子のみ**（NFR-41・NFR-53）
- **端末の買い替え・故障のたびに再発行が必要**になる。施設の運用手間として残る。発生頻度は低いと判断して MVP では自動化しない。
- **施設管理者に「リンクを渡す」という運用作業が増える**。初期設定（NFR-74：4時間以内）に含めて見積もる必要がある。
- **実装上の注意（step5 への申し送り）**：Cognito で管理者が作成した直後のユーザーはパスワード変更待ちの状態にあり、そのままではカスタム認証フローに進めない。**ランダムな恒久パスワードを設定して確認済み状態にする**手順が要る。このパスワードは**どこにも表示せず、誰も知らない**（家族が入力することは一度もない）。

## ADR-005: 家族に再認証を求めない（長期リフレッシュトークン＋明示的失効）

**ステータス**：**撤回**（2026-09-12、[ADR-012](#adr-012) による） ／ **関連**：旧 AC-A4・AC-B3・NFR-46

> **本ADRは撤回された。** 「端末に実質無期限の資格情報を残す」という本ADRの核心は、**まさに [ADR-012](#adr-012) が引き受けないと決めたセキュリティ上のリスクそのもの**である。MVPは通常のセッション期限を持つ（AC-B3 は期限切れによる再認証を許容する）。
> **消さずに残す理由**：次段で AC-A4（ログイン操作なしで到達）に戻る際、**ここで検討した「期限切れ＝サイレントな離脱」という論点は再び効いてくる**。
> 以下は撤回時点の記述をそのまま残す。

### 文脈
AC-A4 は「2回目以降は**ログイン操作なしで**内容に到達できること」を求める。P2 にとって、セッション切れの再ログインは**利用の終わり**を意味する（誰かが助けに来るまで復旧しない）。
Cognito のリフレッシュトークンの有効期間は **60分〜10年**の範囲で設定できる（既定は30日）。**使用しても期限は延長されない**（利用のたびに伸びる方式ではない）。つまり設定値がそのまま「いつ家族が締め出されるか」になる。

### 決定
- **リフレッシュトークンの有効期間を最長（10年）に設定する。** 有効期限による自然失効を**放棄する**。
- **アクセストークンは短命にする**（15分を初期値とする）。
- **失効は、施設管理者による明示的な操作（FR-405）を唯一の手段とする。**

### 根拠
- 期限を1年などに置くと、その日を境に P2 が黙って使えなくなる。**復旧には施設からの再発行が要り、しかも「使えなくなった」ことを本人が申告できるとは限らない。**「期限切れ＝サイレントな離脱」は、K6 の再発にほかならない。
- 失効の必要は**期限ではなく事象**（端末紛失・退居・関係の変化）で生じる。**事象に対しては明示的な失効操作のほうが正確で、かつ即時である。**
- アクセストークンを短命にすることで、失効操作の反映の遅れを**最大15分**に抑える。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| リフレッシュトークン1年＋期限前に管理者へ通知 | 通知を受けた管理者が全家族に再発行して回る運用が毎年発生する。施設の負担が読めず、NFR-71 の思想に反する |
| アプリ側で独自の長期セッションを持ち、Cognito トークンはサーバー側に保持 | 実現可能だが、ADR-002 で避けたはずのセッション管理を自前で持つことになる |
| アクセストークンも長命にする | 失効の反映が遅れる。AC-A5（即時失効）を満たせない |

### 結果（引き受けた代償）
- **端末に、実質無期限の資格情報が残り続ける。** 端末を紛失し、かつ施設に申告されない場合、**アクセスは残り続ける**。これが本決定の最大のリスクであり、**AC-A4 を満たすために意図的に引き受ける**。
- 緩和は3点。**到達範囲を入居者単位に限る**（NFR-41）／**扱う情報を日常の様子に限り、要配慮個人情報を持たない**（NFR-53）／**閲覧の記録を残す**（NFR-45）。つまり、**破られたときの被害の上限を下げることで、破られる確率の高さを相殺する。**
- 家族向けの画面に「ログアウト」を置かない（NFR-13 の語彙制約とも整合する）。**端末を手放すときの手順は、施設への連絡（FR-405）に一本化する**——これは導入手順書（NFR-75）に明記すべき運用上の前提である。

## ADR-006: 1投稿の必須入力を写真1枚のみに固定する

**ステータス**：承認（2026-09-12） ／ **関連**：論点3・FR-101・FR-103・M2

### 文脈
論点3は、**P4（職員）の「1分以内。項目が増えるほど書かなくなる」**と、**P1・P2・P3（家族）の「情報は多いほど嬉しい」**が真っ向から対立する点である。

### 決定
- **1投稿の必須入力は「写真1枚」のみ。** テキスト・状態・カテゴリ等はすべて任意。
- テキストは**文例からの1タップ挿入**で代替できる（ゼロから書かせない）。
- **歯止めルールを要件として明文化する**：*家族側の要望を根拠に、職員の必須入力項目を増やす変更は行わない。*

### 根拠
- **価値が高く負荷が低いものを必須に、価値が低く負荷が高いものを任意にする。** P2 の Need は「夫の**顔**を毎日見たい」、P3 の Need は「**素**の様子」——どちらも一次情報は写真であって文章ではない。一方 P4 の Pain は「書く内容に気を遣う（クレーム化を恐れる）→ 結局書かなくなる」であり、**負荷と恐れの源は文章側にある。**
- 家族の情報量への要求は、**職員の入力を増やす以外の手段**（過去投稿の閲覧＝FR-201、反応のやり取り＝FR-301）で満たす。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| テキストも必須にする | P4 の Pain の中心を必須化することになり、K1（発信の入口が細い）が解けない |
| 状態（食事・機嫌など）の選択を必須にする | 項目が増えるほど書かなくなる（P4）。また健康状態に踏み込むと NFR-53（要配慮個人情報を扱わない）に抵触しうる |
| 写真も任意にする（テキストのみの投稿を許す） | P2 の中心的な Need が写真である以上、写真のない投稿が増えると価値が落ちる。**必須を1つ残すことで下限を守る** |

### 結果（引き受けた代償）
- **家族が受け取る情報量は、家族の希望には届かない。** これは意図した帰結である。
- **M1（週2回）と P2 の「毎日ひとつ見たい」の差分は、埋まっていない。** MVPでは過去投稿の閲覧（FR-201）で部分的に緩和し、実運用の頻度実績を見て次段で再検討する。**職員の入力負荷を上げて毎日を強制する解は採らない**（上記の歯止めルールに反するため）。
- 新しい入力項目の追加は、**M2（中央値60秒）の計測値を悪化させない範囲でのみ許す**。主観ではなく実測で判定する（NFR-22）。

## ADR-007: 共用端末は施設単位でサインインし、投稿者は選択で識別する

**ステータス**：**撤回**（2026-09-13、[ADR-047](#adr-047) による） ／ **関連**：FR-107・FR-302・C1・C2・NFR-33

> **本ADRは撤回された。** 本ADRは「端末は**施設の物理的な管理下**にあり、施設外に持ち出されない前提（C1）。この物理的な境界を、認証の一部として使う」を根拠の中心に置いていた。[ADR-046](#adr-046) が C1 を撤回したため、**根拠そのものが失われた。** 職員個人を認証主体とする（[ADR-047](#adr-047)）。**本ADRが代償として引き受けた「同一施設内でのなりすましが技術的に防げない」は、これにより解消する。**

### 文脈
ここには要件どうしの衝突がある。**FR-302**（反応が投稿した職員**本人**に戻る）は投稿者の識別を要求する。一方 **D軸・M2**（撮影から送信まで60秒）と **C1・C2**（発信は施設管理下の**共用**端末で行う）は、職員ごとのログイン操作を許さない。シフト制で、呼び出しによる中断が常時入る現場（P4）で、投稿のたびにサインイン／サインアウトを挟むことは現実的でない。

### 決定
- **共用端末は施設のアカウントでサインインしたままにする。**
- **投稿時に、職員が一覧から自分を選ぶ**ことで投稿者を識別する。
- **職員個人に認証資格情報（パスワード等）を持たせない。**

### 根拠
- 端末は**施設の物理的な管理下**にあり、施設外に持ち出されない前提（C1）。この物理的な境界を、認証の一部として使う。
- 職員の識別が必要なのは「**誰の投稿に対する反応か**」を結びつけるためであって、**職員を認証する**ためではない。要求されているのは*帰属*であり、*認証*ではない。
- 施設内の職員は、そもそも全入居者に業務上アクセスできる立場にある。職員間にアクセス境界を引くことは、ここでは保護すべき利益に対応していない（→ 担当割り当てをMVPから外した理由でもある）。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 職員ごとにID／パスワード | 現場で回らない（D軸・M2）。共用端末で毎回のサインインは、P4 の1分の大半を食う |
| 職員ごとに4桁PIN | 折衷案として妥当。入力1回で済む。**MVPでは省くが、なりすましが問題化したとき最初に足す候補**とする |
| NFCカード・職員バッジ | 端末とカードの調達コストが発生し、C2（新規端末の導入を前提としない）に反する |

### 結果（引き受けた代償）
- **同一施設内でのなりすましが、技術的には防げない。** 引き受ける理由は2つ——悪用の動機が薄いこと（全投稿は管理者が事後閲覧できる＝FR-505）、被害が施設内に閉じること（NFR-42）。
- 緩和：**全投稿・全反応の事後閲覧**（FR-505）と**操作記録**（NFR-45）。**防止ではなく追跡で抑える。**
- **端末を紛失したときの失効の粒度に注意が要る。** 施設で1つのアカウントを共有すると、失効が施設全体に及ぶ。**端末ごとに別のユーザーを発行し、端末単位で失効できるようにする**（step5 への申し送り）。
- 職員は自宅の私物端末から反応を見られない。C1（私物端末での入居者情報の扱いを避ける）と整合しているため、**制約ではなく仕様**として扱う。

## ADR-008: 宛先を投稿ごとに選ばせない。家族名簿を編集できるのは施設管理者のみ

**ステータス**：承認（2026-09-12） ／ **関連**：論点4・FR-104・FR-404・05_要件定義 9章

### 文脈
論点4は三者の要求が食い違う。**P4**「誰に見せるかを毎回選ぶのは負荷」、**P5**「運用が分岐すると事故る。一律が望ましい」、**P1**「親族間で共有したい。見せる相手を自分で増やしたい」。

### 決定
- **公開範囲を投稿ごとに決めない。** 宛先は入居者ごとの家族名簿によって自動的に決まる（FR-104）。
- **家族名簿を編集できるのは施設管理者のみ**（FR-404）。
- **家族代表による追加申請のフローは、MVPに入れない。**

### 根拠
- P4 の選択操作を**ゼロ**にし、P5 の求める**分岐のない運用**を実現する。この2つは同じ決定で同時に満たせる。
- P1 の「親族を増やしたい」は、**頻度の低い操作**である（家族構成は日々変わらない）。**低頻度の要求のために、申請画面・承認画面・状態管理を MVP に持ち込む必要はない。** 管理者への依頼で代替できる。
- 名簿を施設が握ることで、**誰が見ているかを施設が常に把握している**状態が保たれる。招待の発行元（AC-B1）と失効の実行者（AC-B5・FR-405）がどちらも施設である以上、**名簿の正確さは安全性の前提**になる。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 投稿ごとに公開範囲を指定 | P4 の入力負荷（論点3の決着）と P5 の一律運用に正面から衝突する |
| 家族代表が申請 → 管理者が承認 | 妥当だが MVP には重い。**次段の最有力候補**として9章に記録 |
| 家族が自由に他の家族を招待 | 施設が把握できない相手に個人情報が渡る。ADR-005 の前提が崩れる |

### 結果（引き受けた代償）
- **P1 の要求は MVP では満たされない。** 親族を増やすには施設への依頼が要り、施設の営業時間に律速される。
- 家族が増えるたびに**施設管理者の作業が発生する**。頻度が想定より高ければ、申請フローを次段で足す。
- 「家族代表」というロールが不要になり、**MVPのロールが3つに収まった**（05_要件定義 3-1）。

## ADR-009: 投稿は事前承認を経ずに家族へ届く

**ステータス**：承認（2026-09-12） ／ **関連**：FR-106・FR-505・K1

### 文脈
職員の投稿を管理者が事前に確認してから家族へ出す運用も考えられる。クレームの芽を事前に摘めるため、P5 の関心（家族対応の負担）には合致する。

### 決定
**投稿は事前承認なしで家族に届く。** 管理者は**事後に**全投稿を確認でき（FR-505）、必要なら削除できる。

### 根拠
- 事前承認を挟むと、**投稿が届くまでの時間が承認者の勤務時間に律速される。** 夜勤帯の投稿は翌朝まで出ない。これは P4 の即時性（D軸）と発信量（K1）を同時に殺す。
- **誤りは事後の削除（FR-106）と事後確認（FR-505）で回収できる。** 回収可能な誤りのために、回収不能な発信量の減少を招くのは割に合わない。
- **発信量の確保を、誤りゼロより優先する**——これが本決定の本体である。K1 が解けなければ、以降のすべてが成立しない。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 管理者の事前承認 | 上記のとおり即時性と発信量を失う。P5 の負担も増える（承認待ちが溜まる） |
| 一定時間の保留後に自動配信（訂正の猶予） | 即時性が落ちるわりに、その間に誰も見ない可能性が高い。複雑さに見合わない |

### 結果（引き受けた代償）
- **不適切な投稿が、削除されるまでの間は家族に見えている。** 通知も送られた後になる。
- 緩和：職員が自分の投稿を即座に削除できること（FR-106）、管理者が全投稿を事後閲覧できること（FR-505）、文例を用意して逸脱しにくくすること（FR-103）。
- **削除しても「通知は届いた後」である**という点は残る。MVPでは受け入れ、運用上の注意として導入手順書（NFR-75）に記載する。

## ADR-010: 通知は「投稿の都度」に固定し、頻度設定を持たない

**ステータス**：承認（2026-09-12） ／ **関連**：論点1・FR-202・FR-203

### 文脈
論点1では三者の要求が異なる。**P1**「まとめて1日数回。1件ずつだと埋もれる」、**P2**「都度知りたい。ただし設定を自分で変えることはできない」、**P3**「リアルタイムで可。頻度は自分で調整したい」。

### 決定
- **通知は「投稿の都度」に固定する。** 頻度の選択肢（まとめ配信）を MVP では持たない。
- 家族ができるのは**通知の停止のみ**。
- **代理変更の仕組みも持たない**（設定項目がないため不要になった）。

### 根拠
- **P1 が懸念する「連打」は、構造的に発生しない。** 論点3の決着（ADR-006）により入居者1人あたりの投稿は週2〜3件（M1）を想定している。P1 が受け取る通知は**週2〜3件**であり、埋もれるほどの量にならない。
- **最も弱いユーザーが設定を触らなくて済むデフォルトを選ぶ。** P2 は設定画面に到達できないため、**P2 の希望＝デフォルトである**ことが唯一の成立条件になる。P2 の希望は「都度」である。
- 設定項目そのものを持たないことで、**P2 のための代理変更機能が不要になり**、家族代表ロールも不要になった（ADR-008 と合わせて、MVPのロールが3つに収まった）。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 都度／1日1回まとめ／停止 の3択 | 想定投稿頻度では「まとめ」の価値が小さい一方、設定画面と配信ジョブが必要になる。**次段の候補**として9章に記録 |
| 既定を「1日1回まとめ」にする | P2 の希望（都度）から外れる。**P2 が変更できない以上、既定が P2 に合っていなければならない** |
| 家族ごとに個別最適化 | MVPの複雑さに見合わない |

### 結果（引き受けた代償）
- **P1 の要求は MVP では満たされない。** 通知が想定より増えれば（複数の入居者に紐づく場合など）、P1 の Pain が再発しうる。
- **前提が崩れたときに壊れる決定である。** 投稿頻度が想定を超えた瞬間、この決定の根拠は失われる。**M1（発信頻度）を監視し、超えたらまとめ配信を次段で足す**——これがこの決定に付随する監視義務である。
- 通知停止を選んだ家族は、**能動的に見に行かない限り情報に到達しない**。停止は「通知が来ない」であって「見られない」ではないことを、画面上の言葉で明確にする（NFR-13）。

## ADR-011: 家族の反応は「一押し」のみとし、コメントを持たない

**ステータス**：承認（2026-09-12） ／ **関連**：K3・FR-301・FR-302・05_要件定義 9章

### 文脈
K3（反応が職員に戻らない）を解くには、家族から職員への経路が要る。短いコメントを送れるようにすれば、P1・P3 の「軽く関わりたい」という Need にも応えられる。

### 決定
**MVPでは「一押し」（文章を書かない一度の操作）のみを提供し、コメント送信を持たない。**

### 根拠
- **P2 の Need は「ありがとうを伝えたい」であり、手段は「一押し」で足りる**（[01_ペルソナ.md](01_ペルソナ.md)：感謝を伝える手段は文章を書かせない形が現実的）。K3 の解消に文章は不要である。
- **コメントを許すと、職員の応答負荷が青天井になる。** 家族から文章が届けば、職員は返信すべきか判断を迫られる。これは K1（発信の入口が細い＝職員に時間がない）の解決を打ち消しかねない。**家族→職員の一般的なメッセージ機能を作らない**という方針（05_要件定義 1-2）と同じ理由である。
- K3 の本体は**誰に届くか**であって（FR-302）、反応の表現の豊かさではない。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 一押し＋短いコメント | P1・P3 には応えられるが、職員の応答負荷が読めない。**一押しの実績（M4）を見てから足す** |
| 定型文からの選択式コメント | 折衷案。ただし「堅い定型文はNG」（P3）で、選択肢の設計に手間がかかるわりに効果が読めない |
| 反応を施設宛てにする | K3 が解けない（FR-302 の根拠を参照） |

### 結果（引き受けた代償）
- **P1・P3 の「軽く関わりたい」は、一押しの範囲でしか満たされない。** P3 の「自分が知っている祖父のこと（好物・昔話）を施設に伝えたい」も MVP では満たされない（9章に記録）。
- 反応が一種類だけだと、**感情の濃淡が伝わらない**。M4（反応率50%）は測れても、*どれだけ喜ばれたか*は測れない。実運用で不足が見えたら、反応の種類を増やすか、コメントを足すかを次段で判断する。

## ADR-012: 記憶・入力を求めない認証をMVPの必須要件から外し、標準的な認証を採る

**ステータス**：承認（2026-09-12） ／ **置換対象**：[ADR-004](#adr-004)・[ADR-005](#adr-005)（ともに撤回）
**関連**：論点2・AC-B1〜B5（旧 AC-A1〜A5 は欠番）・FR-401〜403・FR-405・NFR-46・K6・C軸

### 文脈

[01_ペルソナ.md](01_ペルソナ.md) は P2（82歳・パスワードの記憶と入力が実質不可能）を最重要制約として置き、[04_to-be.md](04_to-be.md) 3-3 は「記憶・入力を求めない認証」を解決方針の柱の一つとした。[ADR-004](#adr-004)・[ADR-005](#adr-005) はその実現方式として、**自前実装のマジックリンク**と**実質無期限のセッション**を決めていた。

しかし、その2つのADRが引き受けた代償を並べると、MVPの初版としては重い。

| 出所 | 引き受けるはずだった代償 |
|---|---|
| [ADR-004](#adr-004) | リンクを「渡す」瞬間が最も弱く、紙の紛失・誤送信で第三者に渡りうる。緩和はできるが**ゼロにならない** |
| [ADR-004](#adr-004) | 認証の中核ロジックを**自前で実装する**（カスタムチャレンジの Lambda 3本）。認証は、自作した箇所がそのまま攻撃面になる領域である |
| [ADR-005](#adr-005) | **端末に実質無期限の資格情報が残る。** 端末を紛失し施設に申告されなければ、アクセスは残り続ける |
| [ADR-005](#adr-005) | 有効期限による自然失効を放棄し、**失効を施設の運用に全面的に依存**させる |

### 決定

1. **記憶・入力を求めない認証を、MVPの必須要件から外す。** 受け入れ基準 AC-A1〜A5 を撤回し（欠番）、標準的な認証を前提とした **AC-B1〜B5** に置き換える。
2. **MVPの家族認証は、メールアドレス＋パスワード**とする。招待は**施設管理者によるユーザー作成と招待の送付**から始まり、家族は初回に自分のパスワードを設定する。以降は通常のセッション期限を持つ（[ADR-002](#adr-002) の Cognito 標準機能で完結し、カスタム実装を持たない）。
3. **この要件は捨てるのではなく、次段へ送る。** [ADR-004](#adr-004) の代替案比較は撤回後も残し、[05_要件定義.md](05_要件定義.md) U10 から参照する。

### 根拠

1. **認証は、自作した部分がそのまま攻撃面になる。** 個人開発・専任の運用担当なし（C6）という条件で、初版から認証の中核を自前で持つのは、リスクの取り方として順序が逆である。**標準機能で成立する範囲に留め、枯れた実装に乗る。**
2. **実装難易度が、検証したい仮説に対して不釣り合いに高い。** MVPで最初に検証すべきは「**職員の発信が続くか**（M1・M2）」「**反応が職員に戻るか**（M4）」であり、どちらも認証方式に依存しない。**認証に初版の実装予算を集中させると、検証したい部分に届く前に息切れする。**
3. **P2適合は、認証だけの問題ではない。** C軸は「記憶・入力を求めない認証」と「迷わない操作」の2つからなる（[03_既存サービス比較.md](03_既存サービス比較.md) 1章）。後者（NFR-1群：文字サイズ・語彙・タップ領域・縦スクロールのみ）は**認証方式と独立に MVP で実装でき、実装難易度も低い**。**C軸のうち安く取れる半分を先に取り、高い半分を次段に回す**、という分割である。
4. **失効（AC-B5）は維持される。** MVPで手放したのは*到達のしやすさ*であって、*施設が制御を握っていること*ではない。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| **メールOTP**（Cognito ネイティブのパスワードレス） | 有力。パスワードの記憶が不要でセキュリティ上も遜色なく、実装難易度も同程度。**却下理由は再訪のコスト**——ログインのたびにメールを開く往復が生じ、P1 の「通勤電車内・寝る前の隙間時間に見る」という使い方と相性が悪い（AC-B3 の趣旨）。**方針を変えるなら最初に検討すべき代替案**であり、切り替えコストは小さい |
| ADR-004・005 をそのまま維持 | 上記の代償を初版で引き受けることになる。本ADRの否定対象 |
| パスキー / WebAuthn を MVP の主方式にする | セキュリティは最も高いが、**家族側の端末差異への対応が読めず**、初版の実装難易度が上がる。[ADR-004](#adr-004) の代替案として次段で再検討する |
| 認証を持たず、推測不能なURLだけで閲覧させる | 入力は0回になるが、**URLの漏洩が即座にアクセス漏洩になる**。NFR-44 の趣旨に正面から反する。**「記憶・入力なし」を安く実現しようとすると、ここに落ちる**——それを避けるのが本ADRの動機でもある |

### 結果（引き受けた代償）

**この決定の代償は、他のどのADRよりも大きい。** 明示しておく。

- **K6（最も情報を必要とする層が、届いても受け取れない）は、MVPでは解けない。** P2 は自力で利用を開始できず、介助が要る。介助が得られなければ、P2 は**太郎経由のまま**であり、P2 個人にとっては K2 も解けていない。
- **[03_既存サービス比較.md](03_既存サービス比較.md) 5-1 が「差別化の中心」とした C軸を、MVPは握っていない。** 比較表に照らすと、MVPの位置は「市販の家族連絡アプリ（A○ B○ **C×** D△ E△ G△）を D・E・G で上回ったもの」である。**「LINE並みにP2が使えて、ほのぼの並みに個別に届く」という空白地帯には、まだ立っていない。**
- **成功指標 M3（高齢家族の自力閲覧）は測れない**ため欠番とした。**MVPは本システムの賭けを検証しない**——検証するのは発信と反応の持続性（M1・M2・M4）だけである。
- 家族の**メールアドレスを名簿に持つ必要が生じた**。これは C5（家族の連絡先は施設長が Excel 管理、**仮定・要検証**）に依存する。P2 は「メールアドレスは持っているが使えない」ため、**名簿に載っても到達しない家族が存在する**ことを、施設に対して前提として説明する必要がある。
- NFR-13（技術用語を使わない）に**認証画面という例外**が生じた。「ログイン」「パスワード」が家族の目に触れる。認証後の画面には持ち込まないことで影響を限定する。

### 次段への申し送り（この決定を戻すときの条件）

本ADRは**期限付きの判断**である。次のいずれかが観測されたら、[ADR-004](#adr-004) の再開を検討する。

1. **M1・M2・M4 が達成された**（＝発信と反応の仮説が検証され、次に C軸を取りに行ける状態になった）
2. **高齢家族の利用開始の脱落が、実運用で観測された**（＝ K6 が仮説ではなく事実として確認された）
3. 標準機能の範囲で、記憶・入力を求めない方式が利用可能になった（自前実装せずに AC-A を満たせるなら、本ADRの根拠1・2が消える）

## ADR-013: リソースの所有を施設に一本化し、テナント識別子を経路に露出させない

**ステータス**：承認（2026-09-12） ／ **関連**：[ADR-001](#adr-001)・[ADR-003](#adr-003)・NFR-41・NFR-42・NFR-47・[06_リソース設計.md](06_リソース設計.md) 2章

### 文脈
[ADR-003](#adr-003) は「分離の担保箇所を一系統に寄せる」と決めたが、**どこに寄せるか**は決めていない。リソース設計では2つの形がありうる。**(a) 経路に施設を含める**（`/施設/{id}/入居者/{id}` のように、操作のたびにクライアントが施設を指定する）。**(b) 経路に含めない**（施設は常にトークンから解決する）。

### 決定
1. **文例を除くすべてのリソースは、ちょうど1つの施設に属する。** 関連はすべて同一施設内で閉じる。
2. **施設の識別子を経路・パラメータに露出させない。** 操作対象の施設は、常に認証トークンのテナント識別子から解決する。**クライアントが施設を指定できる経路を作らない。**

### 根拠
1. **クライアントが送れない値は、検証を忘れても破られない。** (a) では「送られてきた施設IDが本当に自分の施設か」を毎回検証する必要があり、**検証を1箇所書き忘れると越境する**。(b) にはその検証自体が存在しない。[ADR-003](#adr-003) が記録したリスク（1箇所の実装漏れが事故に直結）を、**構造的に減らせる形を選ぶ。**
2. **MVPの主体は必ず1施設にのみ属する**（[05_要件定義.md](05_要件定義.md) 3-1）。経路に施設を書かせても情報が増えない。
3. 所有を施設に一本化することで、**テナント条件の付与がデータアクセス層の1箇所で完結する**（U6 の前提）。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 経路に施設識別子を含める | 上記1。**多施設を横断する管理者**（法人本部）を将来入れるときには有利だが、MVPに該当者がいない |
| 施設ごとにサブドメインを分ける | 分離は分かりやすくなるが、施設を増やすたびに DNS・証明書の操作が発生し、NFR-71 を提供側の運用作業として吸収することになる（[ADR-003](#adr-003) 根拠1と同じ問題） |

### 結果（引き受けた代償）
- **法人本部のような「複数施設を横断する主体」を後から入れるとき、経路の設計を変えることになる。** MVP の想定（[05_要件定義.md](05_要件定義.md) 3-1）にいないため引き受ける。
- **家族の到達範囲は、テナント条件だけでは絞りきれない。** 家族は施設単位ではなく**入居者単位**で切れる（NFR-41）。テナント条件に加えて「紐づく入居者」の条件が必ず要る（[06_リソース設計.md](06_リソース設計.md) INV-4）。**この二段の絞り込みを、実装で片方だけ書ける形にしない**ことを設計上の必須とする。
- 越境の**試行**が経路に現れなくなるため、検出は「拒否された操作」を記録する側で担保する（NFR-45）。

## ADR-014: 外部に出る識別子を UUIDv7 に統一し、連番を露出させない

**ステータス**：承認（2026-09-12） ／ **関連**：NFR-44・[ADR-013](#adr-013)・[06_リソース設計.md](06_リソース設計.md) INV-12

### 文脈
リソースの識別子には、連番（1, 2, 3…）と、推測不能な値（UUID 等）の選択がある。本システムでは NFR-44 が「推測可能なURLで第三者が到達できないこと」を求めており、加えて [ADR-013](#adr-013) により**越境の防止がアプリ実装の正しさに依存している**。

### 決定
**外部に出るすべての識別子を UUIDv7 とする。** 連番を外部に露出させない。

### 根拠
1. **連番は、実装漏れを事故に変える。** 認可の抜けがあったとき、連番なら `.../投稿/1235` と打つだけで他人のデータに届く。推測不能な識別子は、**認可の実装漏れが即座に被害にならない**ための二重化である（防御そのものではない——[ADR-013](#adr-013) の検証を代替するものではない）。
2. **UUIDv4 ではなく v7 を採るのは、時系列順に並ぶため。** 生成順に単調増加するので、B木インデックスの断片化と挿入位置の分散が抑えられる。投稿の一覧は常に新しい順（FR-201）であり、**識別子の順序が表示順とおおむね一致する**のは実装上も好都合である。
3. 規模（NFR-36：1施設あたり月800投稿程度）に対して、識別子の大きさが問題になる水準ではない。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 連番（自動採番） | 上記1。加えて**施設ごとの利用量が外部から推測できてしまう**（投稿IDの差分で件数が分かる） |
| UUIDv4 | 推測不能性は同じだが、ランダムなためインデックスの局所性が失われる |
| ULID | v7 とほぼ同じ性質。**標準（RFC 9562）に入っている v7 を採る**ほうが、ライブラリとDBの支援を受けやすい |
| 連番＋外部公開用の別トークン | 二重管理になる。MVPの規模で払うコストではない |

### 結果（引き受けた代償）
- **UUIDv7 は生成時刻を内包するため、識別子から作成時刻が読める。** 本システムでは投稿日時をもともと家族に見せており（FR-201）、隠すべき情報ではないと判断して引き受ける。
- **人が読んで扱いにくい。** 障害調査で識別子を口頭・チャットでやり取りする場面では不便になる。施設コード・端末番号のような**人が扱う識別子は別に持つ**ことで補う（[ADR-015](#adr-015)）。
- 識別子の桁数が増え、保存量とインデックスが連番より大きくなる。規模から許容する。

## ADR-015: 認証主体の識別子を、主体の種類で分ける（人＝メールアドレス／端末＝ユーザー名）

**ステータス**：**撤回**（2026-09-13、[ADR-048](#adr-048) による） ／ **関連**：[ADR-003](#adr-003)・[ADR-012](#adr-012)・[ADR-018](#adr-018)・NFR-46

> **本ADRは撤回された。** 本ADRは「端末にメールアドレスは存在しない」ことを理由に、識別子を主体の種類で分けていた。[ADR-047](#adr-047) で端末が認証主体から外れ、**メールアドレスを持たない主体が消えた。** 全主体をメールアドレスで識別する（[ADR-048](#adr-048)）。**ただし本ADRが記録した代償（1メールアドレス＝1主体）は撤回されておらず、[ADR-048](#adr-048) がそのまま引き継いでいる。**

### 文脈
[ADR-012](#adr-012) は家族の認証をメールアドレス＋パスワードと決めた。管理者も同様である。一方、[ADR-018](#adr-018) により**共用端末も認証主体になる**が、端末にメールアドレスは存在しない。[ADR-003](#adr-003) により全主体が**単一のユーザープール**に入るため、識別子は**全体で一意**である必要がある。

### 決定
1. **人（管理者・家族）はメールアドレスで識別する。** パスワードの再設定を本人が行える（NFR-46）。
2. **端末はユーザー名で識別する。** 形は `施設コード＋端末番号`。メールアドレスを持たせない。
3. ユーザープールは、**メールアドレスとユーザー名の両方をサインイン方法として有効にする。**

### 根拠
1. **端末にダミーのメールアドレスを割り当てない。** 到達しないアドレスを本物のように置くと、パスワード再設定・通知・バウンスの扱いが静かに壊れる。**「メールを持たない主体」は、持たないまま扱う。**
2. **端末の識別子は、人が読めて現場で扱えるほうがよい。** 職員が「この端末はどれか」を照合する場面（機種変更・紛失時の失効）で、UUID（[ADR-014](#adr-014)）は使えない。施設コードを含めることで、**どの施設の端末かが識別子だけで分かる。**
3. 端末のパスワード再設定は**管理者の操作**で行う。端末は施設の物理的な管理下にあり（C1）、本人による再設定の経路を持つ必要がない。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 端末にもダミーのメールアドレスを割り当てる | 上記1。`device1@example.invalid` のような値が名簿に紛れ、**本物のアドレスと区別できない状態**を作る |
| 全主体をユーザー名で識別し、メールは属性として持つ | 家族が**自分のユーザー名を覚える**必要が生じる。[ADR-012](#adr-012) が「標準的な認証」に留めた趣旨（覚えるものを増やさない）に反する |
| 端末を Cognito の外で認証する（アプリ独自のトークン） | [ADR-002](#adr-002) で避けたはずの自前のセッション管理が復活する |

### 結果（引き受けた代償）
- **1メールアドレス＝1家族＝1入居者になる。** 単一プール（[ADR-003](#adr-003)）でメールアドレスが全体一意であるため、**同じ人が2人の入居者（夫婦入居など）や2つの施設に紐づけない。** [05_要件定義.md](05_要件定義.md) 9章が「1人の家族が複数の入居者に紐づく」をMVP対象外としているため今は表面化しないが、**次段でそれを許すときは、ここが最初に壊れる。**
- 管理者は、重複したメールアドレスの登録を**拒否される**。「別の施設で既に使われている」ことは他施設の情報であり、**理由を明かさずに拒否するしかない**（NFR-42）。管理者に何と表示するかは画面設計で決める。
- サインイン方法を2種類有効にするため、**ユーザープールの設定が後から変更できない項目に触れる**（サインイン方法はプール作成時に決まる）。作り直しになるため、設計時点で確定させておく必要がある。

## ADR-016: 招待の引換は Cognito に委ね、アプリは招待の記録だけを持つ

**ステータス**：承認（2026-09-12） ／ **関連**：[ADR-012](#adr-012)・FR-401・FR-404・AC-B1・AC-B2・NFR-45

### 文脈
[ADR-012](#adr-012) は「管理者によるユーザー作成と招待の送付」から利用開始が始まると決めた。これは Cognito の標準機能（ユーザー作成時の招待メールと仮パスワード）でそのまま実現できる。
一方で、**アプリ側に招待の情報を一切持たない**と、「いつ誰が誰を招待したか」「何度送り直したか」が残らない。

### 決定
1. **引換の仕組みを自前で持たない。** 仮パスワードの発行・有効期限・初回のパスワード設定は Cognito の標準機能に委ねる。**アプリは引換コードを保持しない。**
2. **招待を独立したリソースとして持つ。** ただし中身は**記録**（誰が・いつ・どのアドレスへ・初回か再送か・結果）であり、認証の状態そのものではない。
3. 家族の状態（招待前／招待済／利用中／失効）は**アプリ側で持つ**。

### 根拠
1. **[ADR-012](#adr-012) の目的は「認証の中核を自作しない」ことである。** 引換コードの生成・保管・有効期限・使い捨ての管理は、まさにその中核にあたる。**記録を持ちたいという理由で、認証ロジックを自前に戻さない。**
2. **招待の履歴は、名簿の正確さを保つための材料になる。** [ADR-008](#adr-008) は「名簿を施設が握ることで、誰が見ているかを施設が常に把握している」ことを安全性の前提に置いた。**送ったが引き換えられていない家族**が見えなければ、その前提は絵に描いた餅になる。
3. 家族の状態をアプリ側に持つのは、**管理画面（FR-404）が Cognito に問い合わせずに名簿を一覧できるようにする**ため。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 招待コードを自前で発行・検証する | 上記1。[ADR-012](#adr-012) の否定対象そのもの |
| 招待の記録を持たない（Cognito の状態だけを見る） | 再送の回数・送付先の履歴が残らず、NFR-45（誰がいつ何をしたか）に届かない。管理画面のたびに Cognito へ問い合わせる必要も生じる |
| 家族の状態を持たず、毎回 Cognito から取得する | 名簿の一覧表示が外部呼び出しに律速される。また Cognito の状態語（`FORCE_CHANGE_PASSWORD` 等）を管理画面の語彙に持ち込むことになる |

### 結果（引き受けた代償）
- **状態が2箇所に存在する**（Cognito＝真実、アプリ＝写像）。**ズレうる**——たとえば Cognito 側で期限切れになっても、アプリ側の「招待済」は自動では変わらない。**Cognito を真実とし、アプリ側は表示のための写像である**と位置づけ、食い違ったときは Cognito に合わせる。同期の具体は [07_API設計.md](07_API設計.md) で決める。
- **引き換えの瞬間をアプリが観測できない。** 「パスワードを設定した」ことは、その家族が最初にアプリへアクセスした時点で初めて分かる。利用開始日時はその近似値になる。
- 仮パスワードの有効期限（既定7日）は Cognito の設定に従う。**期限を独自に決められない**が、MVPで困らない。

## ADR-017: 写真を投稿から独立させ、アップロードと投稿を2段階にする

**ステータス**：承認（2026-09-12） ／ **関連**：FR-101・NFR-34・NFR-35・NFR-44・M2

### 文脈
NFR-35 は「施設内の回線品質が低い場合でも、写真の送信が失敗したまま**失われない**こと」を求める。M2 は撮影開始から送信完了までの中央値60秒を求める。
写真と投稿を1回の送信でまとめて送る形（1段階）と、写真を先に送ってから投稿を作る形（2段階）がある。

### 決定
1. **写真を、投稿とは独立したリソースにする。**
2. **①写真をアップロードする → ②投稿を作成して写真を指定する**、の2段階にする。
3. アップロードは**ストレージへ直接**行い、アプリのサーバーを経由させない。
4. **確定しないまま一定期間を過ぎた写真は削除する。**

### 根拠
1. **再試行の単位を分けられる。** 1段階だと、送信が途中で切れたときに**写真を含む全体を送り直す**ことになる（施設の回線で最も重い部分を、最も失敗しやすい条件下で繰り返す）。2段階なら、失敗したのがアップロードなら写真だけを再試行でき、投稿の作成は軽い操作として確実に通る。
2. **投稿の作成が速くなる**（M2）。写真の転送は撮影直後に裏で始められる。職員が職員名を選び、文例を選んでいる間に転送が進む。
3. **サーバーを経由させないことで、転送の費用と時間が減る**（NFR-34・NFR-76）。
4. 配信も保存も**推測不能な経路**で行う（NFR-44）。写真の識別子とストレージ上の位置を分けて持つ。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 写真と投稿を1回で送る（multipart） | 実装は単純だが上記1・2・3をすべて失う。**現場の回線が本システムの前提条件**（NFR-35）である以上、ここは単純さを優先できない |
| 写真をアプリのサーバー経由でアップロードする | 実装は素直だが、転送量とメモリがサーバーに乗る。規模が小さいうちは動くが、**NFR-76 のコスト上限に効いてくる**のは転送量である |
| 投稿を先に作り、後から写真を付ける | 写真のない投稿が一時的に存在する。[ADR-006](#adr-006)（必須は写真1枚）の不変条件が崩れ、**通知が先に飛ぶ**危険がある |

### 結果（引き受けた代償）
- **孤児になった写真の掃除が必要になる。** アップロードしたが投稿が作られなかった写真が残る。**期限付きの自動削除**を運用に持ち込むことになり、C6（運用担当を置けない）の観点では純増である。
- **2段階の失敗を画面で扱う必要がある。** 「写真は送れたが投稿が作れなかった」状態が存在する。職員には1つの操作に見せる（NFR-17：片手で完結）ことが画面設計の要件になる。
- 写真の削除は投稿の削除と連動しない（[ADR-019](#adr-019) の論理削除により、投稿が削除されても写真の実体は残る）。**物理的な削除は退居時の削除操作でまとめて行う。**

## ADR-018: 認証主体を端末単位にする（施設で1アカウントを共有しない）

**ステータス**：**撤回**（2026-09-13、[ADR-047](#adr-047) による） ／ **関連**：[ADR-007](#adr-007)・FR-107・FR-405・NFR-45

> **本ADRは撤回された。** 本ADRは [ADR-007](#adr-007) が申し送った「端末単位の失効」に答えるものであり、**[ADR-007](#adr-007) の撤回とともに前提を失った。** [ADR-047](#adr-047) により端末は認証主体ではなくなり、端末リソースそのものを持たない。

### 文脈
[ADR-007](#adr-007) は「共用端末は施設のアカウントでサインインしたままにする」と決めたうえで、その結果として次を申し送っていた——**「端末を紛失したときの失効の粒度に注意が要る。施設で1つのアカウントを共有すると、失効が施設全体に及ぶ。端末ごとに別のユーザーを発行し、端末単位で失効できるようにする（step5 への申し送り）。」**
本ADRはこの申し送りに答えるものであり、[ADR-007](#adr-007) を否定しない。

### 決定
1. **端末をリソースとして持ち、1台ごとに認証主体を発行する。**
2. **失効は端末単位**で行う。
3. 投稿に**どの端末から投稿されたか**を記録する。
4. 端末は**サインインしたままにする**（[ADR-007](#adr-007) の決定を維持する）。

### 根拠
1. **失効の粒度が、そのまま事故時の被害範囲になる。** 1台を紛失したときに施設の全端末が止まると、**発信が止まる**（K1 の再発）。施設は紛失を報告しにくくなり、[ADR-007](#adr-007) が防御として頼った「追跡」も効かなくなる。
2. **どの端末から投稿されたかが記録に残る**（NFR-45）。[ADR-007](#adr-007) は職員のなりすましを「防止ではなく追跡で抑える」と決めた。**追跡できる軸は多いほうがよい**——職員は自己申告（選択）だが、端末は申告ではない。
3. 端末の登録は**施設あたり1〜数台**であり、管理の手間は小さい（NFR-36 の規模）。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 施設で1アカウントを共有する（[ADR-007](#adr-007) の素直な読み） | 上記1。失効が施設全体に及ぶ |
| 端末ごとに**職員のアカウント**を割り当てる | [ADR-007](#adr-007) の否定になる（職員に資格情報を持たせない） |
| 端末を認証せず、施設内ネットワークからのアクセスだけを許す | 施設のネットワーク構成に依存する。NFR-33（既にある共用端末を使う）と噛み合わず、持ち出し時に無防備 |

### 結果（引き受けた代償）
- **端末の追加・機種変更が管理者の作業になる。** 頻度は低い（施設あたり数台）ため引き受ける。導入手順書（NFR-75）に記載する。
- **端末が長期間サインインしたままになる。** [ADR-005](#adr-005) が家族について引き受けようとして撤回されたリスクと、形の上では同じである。**端末について引き受ける理由が違う**——端末は施設の物理的な管理下にあり（C1）、紛失が施設にとって可視であり、失効が1台に閉じる。**家族の端末と違い、施設が状態を把握している。**
- 端末のセッション期限をどう設定するかは未決（[06_リソース設計.md](06_リソース設計.md) V4）。**期限切れで現場が止まる**ことと、**紛失時にいつまでも有効**であることの折り合いを、家族とは別に決める。

## ADR-019: 削除は論理削除に統一し、物理削除は退居時の削除操作に限る

**ステータス**：承認（2026-09-12） ／ **関連**：FR-106・FR-405・FR-505・FR-602・NFR-45・[ADR-009](#adr-009)

### 文脈
本システムには「消す」操作が3種類ある。**投稿の削除**（FR-106）、**家族のアクセスの失効**（FR-405）、**退居時のデータの削除**（FR-602）。これらを同じ「消す」として扱うか、区別するかを決める必要がある。

### 決定
1. **投稿の削除と家族の失効は、論理削除（状態の変更）とする。** 実体は残る。
2. **物理削除は、退居時にデータの削除を選んだ場合に限る**（FR-602）。
3. 職員・入居者の「利用停止」「退居」も同様に状態の変更であり、関連するデータの帰属を壊さない。

### 根拠
1. **[ADR-009](#adr-009)（事前承認なし）の緩和策が、事後の確認（FR-505）に乗っている。** 不適切な投稿が物理削除されると、**管理者が確認すべきまさにそのものが消える**。事前承認を捨てた代わりに事後の確認を置いた以上、削除された投稿こそ管理者に見えなければならない。
2. **失効した家族を消すと、誰が見ていたかが消える。** [ADR-008](#adr-008) は「名簿を施設が握ることで、誰が見ているかを施設が常に把握している」を安全性の前提に置いた。**過去形の把握も含まれる。**
3. **法令上の要請は、退居時の明示的な操作（FR-602）で満たす。** 「消えてほしい」という要求は、投稿単位ではなく**入居者単位**で発生する。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| すべて物理削除 | 上記1・2。NFR-45（操作記録）も対象を失う |
| 投稿はすぐ物理削除し、操作記録にメタ情報だけ残す | 「何が投稿されたか」が残らない。FR-505 の事後確認が**内容の確認にならない** |
| 一定期間後に自動で物理削除する | MVP に削除の期限を決める材料がない。**保持期間は次段で決める**（[06_リソース設計.md](06_リソース設計.md) V6） |

### 結果（引き受けた代償）
- **「削除したのに残っている」状態を、施設と家族に対して説明する責任が生じる。** 家族から見えなくなるが、管理者からは見える——この差を導入手順書（NFR-75）と責任分界の文書（NFR-56）に明記する必要がある。
- **保持期間を決めない限り、データは増え続ける。** 個人情報を必要な期間を超えて保持しないという原則（NFR-51）に対して、**現時点では期限の定義がない**。これは未決事項として残す（V6）。
- 写真の実体も残るため、ストレージの費用に効く（NFR-76）。規模（NFR-36）では小さいが、**保持期間の決定が費用の決定でもある**。

## ADR-020: 反応を「1家族×1投稿＝1件」の冪等な存在として表す

**ステータス**：承認（2026-09-12） ／ **関連**：[ADR-011](#adr-011)・FR-301・M4・NFR-15

### 文脈
[ADR-011](#adr-011) は反応を「一押し」のみと決めたが、**同じ家族が同じ投稿に何度も押せるか**は決めていない。押すたびに1件増える（追記型）か、押した／押していないの2状態か（冪等）で、リソースの形が変わる。

### 決定
1. **1家族×1投稿につき、反応は最大1件。** 同じ投稿に2回送っても2件にならない。
2. **取り消しを許す**（押し直しで消える）。
3. 職員に見えるのは「**誰が反応したか**」であり、回数ではない。

### 根拠
1. **押し間違いが起きる。** 家族向けの操作は大きなタップ領域（NFR-14）で、高齢の利用者が指を置いたまま動く状況を想定している。**取り消せない操作を、最も押しやすい場所に置かない。**
2. **通知の重複を構造的に防げる。** 追記型だと、押すたびに職員側の一覧が伸びる。悪意がなくても（接続が不安定で二重送信、孫が面白がって連打）起こりうる。
3. **M4（反応率50%）の定義が素直になる。** 測りたいのは「反応がついた投稿の割合」であって、反応の総数ではない。追記型だと**1人の連打が指標を押し上げる**。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 追記型（押すたびに1件） | 上記2・3。「何度もありがとうを伝えたい」という気持ちは尊いが、**それを表現する手段としては回数より言葉が適切**であり、それは [ADR-011](#adr-011) で次段に送った |
| 取り消しを許さない | 押し間違いが回収できない。家族に「取り消せません」の確認を出すのは NFR-11（説明を読まずに達成できる）に反する |
| 反応の種類を複数持つ（いいね／ありがとう等） | [ADR-011](#adr-011) の決定範囲外。種類を増やす判断は M4 の実績を見てから |

### 結果（引き受けた代償）
- **感情の強さが伝わらない。** [ADR-011](#adr-011) が既に引き受けた代償（濃淡が伝わらない）を、リソースの形としても固定することになる。
- **取り消しが職員に見える形になる。** 一度届いた反応が消えることがある。職員の一覧では「今ついている反応」だけを見せ、**消えたことを通知しない**（がっかりさせる通知を作らない）。
- 取り消しの記録は操作記録に残る（NFR-45）が、**職員には見せない**。

## ADR-021: 職員への反応の到達を、通知ではなく共用端末上の一覧で担保する

**ステータス**：承認（2026-09-12） ／ **関連**：[ADR-007](#adr-007)・FR-302・FR-303・K3・P4

### 文脈
FR-302 は「反応は、その投稿を行った**職員本人**に届く」を求める。一方 [ADR-007](#adr-007) により、**職員は認証主体ではない**（個人の資格情報を持たない）。つまり**職員個人に届ける宛先が存在しない。** K3（反応が戻らない＝P4のやりがい）の解決は本システムの中核の一つであり、ここは曖昧にできない。

### 決定
1. **職員に反応をプッシュしない。** 職員個人への通知経路を作らない。
2. **共用端末で職員が自分を選び、自分の投稿への反応を一覧で見る**（FR-303）。
3. 一覧は、**投稿ではなく反応の新しい順**で並べる（前回見てから何が届いたかが分かる形にする）。

### 根拠
1. **職員個人への通知は、私物端末への通知を意味する。** C1（私物スマートフォンでの入居者撮影は禁止）の趣旨は、入居者の情報を私物端末に載せないことにある。**反応の通知には入居者名と家族名が伴う**ため、同じ線を越える。[ADR-007](#adr-007) が「職員は自宅から反応を見られない。これは制約ではなく仕様である」と記録したことと同じ判断である。
2. **職員は必ず端末に触れる。** 発信のたびに共用端末を使う（D軸）以上、**次に投稿するときに必ず反応が目に入る**。反応を見るための特別な動線を作らなくてよい。
3. 個人への通知を作るには職員を認証する必要があり、**[ADR-007](#adr-007) の再検討に戻る**。MVPでそこは開けない。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 職員個人に通知する | 上記1・3。職員の認証（[ADR-007](#adr-007)）と私物端末（C1）の両方に触れる |
| 共用端末に施設宛ての通知を出す | 誰の投稿への反応か分からないまま鳴る。FR-302 が求めるのは**誰に届くか**であり、施設宛ての通知は [ADR-011](#adr-011) が却下した「反応を施設宛てにする」と同じ形になる |
| 反応を紙で出力して職員に配る | 運用が増え、即時性も失う |

### 結果（引き受けた代償）
- **職員が反応に気づくまでに時間差が出る。** 次に端末を触るまで気づかない。**K3 の解決が「即時の喜び」ではなく「次に使うときの積み重ね」になる。**
- **端末を触らない職員には届かない。** 発信しない職員は反応も受け取らないが、そもそも反応は自分の投稿に対するものであり、矛盾しない。
- 一覧を**職員の選択**の後ろに置くため、**他の職員の反応も技術的には見える**（[ADR-007](#adr-007) の代償と同じ性質）。施設内に閉じるため引き受ける。

## ADR-022: 写真掲載同意を入居者の属性として持ち、履歴は操作記録で担保する

**ステータス**：承認（2026-09-12） ／ **関連**：FR-504・NFR-51・NFR-52・C4

### 文脈
FR-504 は「管理者は入居者ごとに写真掲載同意の有無を記録でき、同意がない入居者には投稿できない」を求める。同意は法令に関わる情報（NFR-51）であり、「いつ・誰が・どう変えたか」が問われうる。**入居者の属性として持つ**か、**履歴を持つ独立したリソースにする**かの選択がある。

### 決定
1. **同意の有無を入居者の属性として持つ**（有／無、記録日時、記録者）。
2. **変更の履歴は操作記録（NFR-45）で担保する。** 同意専用の履歴リソースを作らない。
3. **同意が「無」の入居者には投稿を作成できない**という不変条件を、投稿の作成時に必ず評価する。

### 根拠
1. **同意は入居契約時に紙で一括取得されている**（C4）。システムが記録するのは**紙の状態の写し**であり、同意そのものの取得手段ではない。**原本は紙にある。**
2. **変更の頻度が極めて低い。** 入居時に1回、以降はほぼ変わらない。履歴リソースを立てるほどの情報量が生まれない。
3. 「誰がいつ変えたか」は NFR-45 が全操作について既に要求している。**同意のためだけに二重の仕組みを持たない。**

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 同意を履歴付きの独立リソースにする | MVPの変更頻度に対して過剰。次段で同意の種類（写真／動画／対外公開など）が増えたら、そのときに切り出す |
| 同意を投稿ごとに確認する | 職員の入力が増える（[ADR-006](#adr-006) の歯止めに反する） |
| 同意を家族から取得する仕組みを作る | 原本は紙であり（C4）、システムが取得の経路になると責任分界（NFR-56）が複雑になる |

### 結果（引き受けた代償）
- **「ある投稿の時点で同意があったか」の再現が、操作記録の読み解きに依存する。** 属性は現在値しか持たないため、過去のある時点の状態は記録を遡って構成することになる。**法的な問い合わせが来たときの手間**として引き受ける。
- **C4 は未検証の仮定である。** 紙で一括取得されていない施設では、この設計は前提から成り立たない。実施設へのヒアリングで検証する項目（[05_要件定義.md](05_要件定義.md) 脚注）。
- **同意を「無」に変えたとき、既存の投稿をどう扱うか**が決まっていない（[06_リソース設計.md](06_リソース設計.md) V5）。**属性を1つ変えるだけで過去が変わる**設計にはしないほうがよい、という点だけを本ADRの範囲とし、具体は [07_API設計.md](07_API設計.md) に送る。

## ADR-023: 発信状況を保存せず、投稿からの派生として都度求める

**ステータス**：承認（2026-09-12） ／ **関連**：FR-503・M1・NFR-36・C6

### 文脈
FR-503 は「管理者は、入居者ごとの最終投稿日と投稿件数を一覧で把握できる」を求める。これは**発信が止まっている入居者に気づく**ための機能であり、M1（週2回以上を80%の入居者で継続）の監視にも使う。
集計値を保持する（投稿のたびに更新する）か、必要なときに投稿から求めるかの選択がある。

### 決定
**保存しない。投稿から都度求める。** 発信状況は読み取り専用の派生であり、書き込みの入口を持たない。

### 根拠
1. **規模が小さい。** 1施設あたり入居者80名・月10投稿（NFR-36）＝**年間1万件程度**。都度の集計で困る量ではない。
2. **保持すると、更新漏れが静かなバグになる。** 投稿の作成・削除の両方で集計を更新する必要があり、**片方を忘れても誰も気づかない**（画面は正しそうな数字を出し続ける）。C6（運用担当を置けない）の条件で、**気づけないバグを作らない**ことを優先する。
3. **正しさの出どころを1箇所にする。** 投稿が唯一の真実であり、集計はその関数である。[ADR-016](#adr-016)（状態を2箇所に持つ）とは違い、**ここには分ける理由がない。**

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 入居者に最終投稿日・件数を持たせる | 上記2。更新漏れが検出できない |
| 日次のバッチで集計する | 「今日まだ発信していない入居者」に気づけるのが翌日になる。管理者が見る意味が薄れる |
| 集計用の別の仕組みを持ち込む | C6 に対して過剰。MVPの規模で正当化できない |

### 結果（引き受けた代償）
- **施設数と投稿数が増えると、一覧の表示が重くなる。** 代償を引き受ける代わりに、**M1 の監視と同じ場所でこの画面の応答時間も見る**ことにする。遅くなったら集計の保持に切り替える——そのときは本ADRを置換する。
- 集計の条件（何日分を数えるか）を画面ごとに書くことになるため、**定義がぶれないよう1箇所にまとめる**ことを実装上の注意とする。

## ADR-024: 読み取りはサーバコンポーネントから、状態変更は Route Handler で行う

**ステータス**：承認（2026-09-12） ／ **関連**：[07_API設計.md](07_API設計.md) 0-4・C6・NFR-34

### 文脈

App Router には、クライアントからサーバ側の処理を呼ぶ手段が3つある——サーバコンポーネントからのデータ取得、Route Handler（HTTP エンドポイント）、Server Actions。**どれか1つに寄せるか、役割で使い分けるか**を決める必要がある。

Next.js の指針は明確で、**サーバコンポーネントのデータ取得を Route Handler 経由で行ってはならない**（ビルド時のプリレンダリングでは受け側のサーバが存在せずビルドが落ち、実行時でも HTTP の往復が1つ余計に挟まる）。また Server Actions は**直列に順序づけて実行される**ため、データ取得に使うと並行性を失う。

### 決定

**役割で使い分ける。**

1. **画面の初期表示に必要な読み取りは、サーバコンポーネントが DAL を直接呼ぶ。** Route Handler を経由しない。
2. **状態を変える操作と、初期表示のあとの追加取得は、Route Handler の HTTP エンドポイントで行う。**
3. **Server Actions を使わない。**
4. どちらの経路も、**データには必ず同じ DAL を通して触れる**。

### 根拠

1. **1と2は Next.js の指針そのままである。** ここで独自の判断をする理由がない。
2. **Server Actions を使わない理由は3つ。** (a) 直列実行のため、追加取得に使うと遅くなる。(b) レート制限（NFR-46）・`Idempotency-Key`（[ADR-028](#adr-028)）・`Origin` 検証・問題詳細形式のエラー（[ADR-029](#adr-029)）といった規約を、**HTTP の語彙で一度だけ決めれば全操作に効く**——Server Actions を混ぜると同じ規約を2つの語彙で二重に用意することになる。(c) **OSS として公開する以上、外から見える契約があること自体が価値**である（FR-601 のロックイン回避と同じ筋で、API が読めれば別のクライアントを作れる）。
3. **経路が2系統になっても、担保箇所は1つに保てる。** 分かれるのは入口だけで、認可とテナント条件は DAL に集約される（[ADR-003](#adr-003)）。**「入口が2つ」と「担保が2系統」は別の問題である。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| すべて Route Handler に寄せる（読み取りも） | 上記の指針に反する。ビルドが落ち、実行時も往復が増えて NFR-34（3秒）に逆風。**画面の数だけ無駄な HTTP 往復を作る** |
| すべて Server Actions に寄せる | 直列実行で追加取得が遅い。外から見える契約が無くなり、レート制限・冪等性の規約を置く場所が曖昧になる |
| GraphQL / tRPC を導入する | 型の共有は魅力だが、クライアントは自前の1つだけであり、**スキーマ層を1つ増やす価値がない**。C6（運用対象を増やさない）に反する |

### 結果（引き受けた代償）

- **同じ操作に2つの入口があるように見える。** 「一覧はサーバコンポーネントで、さかのぼりは HTTP で」という重複が、投稿一覧などで実際に発生する。**緩和は、DAL の関数を唯一の実体にして両方から呼ぶこと**——重複するのは呼び出し側だけにする。
- **どちらの経路を使うかの判断が、実装者に残る。** 判断基準を [07_API設計.md](07_API設計.md) 0-4 に3行で固定し、都度考えない形にした。
- Server Actions を使わないため、フォーム送信は自前で `fetch` を書くことになる。**記述量は増えるが、規約を1箇所に保てる利得のほうが大きい**と判断した。

## ADR-025: Cognito のトークンをブラウザに渡さず、サーバ側セッションに封じる

**ステータス**：承認（2026-09-12） ／ **関連**：NFR-46・FR-405・AC-B5・INV-7・[ADR-002](#adr-002)

### 文脈

Cognito を使う一般的な構成では、発行された ID／アクセス／リフレッシュトークンを**ブラウザ側で保持する**（SDK が `localStorage` などに置く）。この構成では、**XSS が1つでも成立するとトークンごと持ち出される**。

一方、本システムの家族は認証の再実行が難しい層を含み（[ADR-012](#adr-012)）、**失効（FR-405）を施設が確実に握っていること**が安全性の柱になっている。

### 決定

**ブラウザには不透明なセッションID（`HttpOnly` Cookie）だけを渡し、Cognito のトークンはサーバ側に保持する。**

- Cookie は `__Host-session`（`HttpOnly` / `Secure` / `SameSite=Lax` / `Path=/`）。
- トークンの更新はサーバ側で完結し、ブラウザは関与しない。
- 招待直後のチャレンジも、Cognito のセッション文字列をそのまま返さず、**サーバ側の状態に紐づく短命の不透明な値**に置き換える。

### 根拠

1. **JS から読めない資格情報は、XSS で盗まれない。** 認証を自作しない（[ADR-002](#adr-002)・[ADR-012](#adr-012)）という方針の延長にある——**自作しないだけでなく、露出も減らす。**
2. **失効が即時に効くようになる**（FR-405・AC-B5・INV-7）。サーバがセッションの実体を持つため、DAL が毎リクエストで主体の有効状態を確認でき、**トークンの残存期間に関係なく次のリクエストから拒否できる**。ブラウザ保持だと、アクセストークンの寿命だけ失効が遅れる。
3. **Cognito 由来の英語メッセージがブラウザに届かない。** [ADR-002](#adr-002) が「Cognito のエラーをそのまま露出させない」を設計時の注意点として申し送っていたが、**トークンごと隠してしまえば、注意ではなく構造で担保される**（NFR-13）。
4. Cookie に暗号化したトークンを詰める（ステートレス）案は、**Cognito のリフレッシュトークンが長く、暗号化するとCookieの上限に近づく**ため採らない。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| ブラウザがトークンを保持（一般的な構成） | XSS で資格情報ごと持ち出される。失効の反映がアクセストークンの寿命だけ遅れ、AC-B5 の「即時」が満たせない |
| Cookie に暗号化したトークンを入れる（サーバ側に状態を持たない） | Cookie のサイズ上限に近づく。分割すれば回避できるが、**構成が読みにくくなるわりに得るものが「テーブル1つ減る」だけ** |
| Cognito の Managed Login に寄せる | [ADR-002](#adr-002) で却下済み（NFR-1群を全画面で一貫させるため、画面は自前） |

### 結果（引き受けた代償）

- **サーバ側にセッションの保管が必要になった。** [ADR-002](#adr-002) が避けたかった「自前のセッション管理」に半歩戻っている。**線引きを明示しておく**——自前で持つのは**発行済みトークンの保管と紐づけ**だけであり、**資格情報の検証・パスワードの保管・試行回数の制限・パスワードの再設定は依然すべて Cognito** にある。認証の中核は自作していない。
- セッションの掃除（期限切れの削除）が運用項目に加わった。[ADR-035](#adr-035) の定期実行に寄せて、**新しい運用対象を増やさない**形にした。
- サインインの往復に、アプリのサーバが1つ挟まる。**レート制限をアプリ側にも置ける**という利点と表裏である（NFR-46）。

## ADR-026: エンドポイントを主体別の名前空間に分ける

**ステータス**：承認（2026-09-12） ／ **関連**：NFR-41・NFR-42・INV-4・[06_リソース設計.md](06_リソース設計.md) 6-2

### 文脈

投稿（R8）は、家族・職員・管理者の3者が触れるリソースである。**同じ `/api/posts` を3者で共有し、主体によって振る舞いを変える**設計も、**`/api/family/posts` `/api/staff/posts` `/api/admin/posts` に分ける**設計も取れる。

### 決定

**`/api/auth` `/api/staff` `/api/family` `/api/admin` の4つに分ける。** 同じリソースでも、主体が違えばパス・表現・認可がすべて別になる。

### 根拠

1. **「同じURLなのに、見る人によって中身が変わる」構造は、認可の漏れが読んで分からない。** 家族向けの投稿一覧は入居者条件（INV-4）を必ず伴い、管理者向けは削除済みを含む（FR-505）。これを1つのハンドラの中の分岐で表すと、**分岐を1つ足し忘れた瞬間に越境する**。[ADR-003](#adr-003) が「1箇所の実装漏れが越境事故に直結する」と記録したリスクを、**分岐の数を減らすことで下げる。**
2. **表現が実際に違う。** 家族向けの投稿は職員の識別子も状態も持たない（[07_API設計.md](07_API設計.md) 2-3）。同じリソースの別の見え方を1つの型で表そうとすると、**「この主体のときは `null`」というフィールドが増える**——これは家族向けの表現に余計な概念を持ち込むことでもある（NFR-16）。
3. **経路の構造が、そのまま要件の固定になる。** 管理者が `/api/staff/*` に入れないことで、「管理者は投稿を作成できない」（[05_要件定義.md](05_要件定義.md) 3-2）が構造として成立する。**画面に出さないだけでは、要件を固定したことにならない。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| `/api/posts` を共有し、主体で分岐 | 上記1・2。認可の条件がハンドラ内の分岐に散る |
| リソースごとに分け、認可はミドルウェアの表で宣言 | 宣言と実装が離れる。**表の更新漏れが検出できない**——分岐と同じ問題が場所を変えて残る |

### 結果（引き受けた代償）

- **似たエンドポイントが並ぶ。** 投稿の取得が3つ、写真のリダイレクトが3つある。
- 緩和は [ADR-024](#adr-024) と同じ——**重複するのはハンドラの薄い層だけで、実体は DAL の関数1つ**にする。ハンドラが厚くなり始めたら、それは DAL に置くべきものが漏れている合図とする。
- 家族が複数の役割を兼ねる場合（職員でもある家族など）は、**別々にサインインすることになる**。MVPの想定には該当者がいないため引き受ける。

## ADR-027: 写真のバイト列を API に通さない

**ステータス**：承認（2026-09-12） ／ **関連**：[06_リソース設計.md](06_リソース設計.md) V2・NFR-34・NFR-44・NFR-76・[ADR-017](#adr-017)

### 文脈

[ADR-017](#adr-017) が写真を独立したリソースにし、アップロードと投稿を2段階にした。残っていたのは **V2：写真をどう配信するか**である。NFR-44 は「推測可能なURLで第三者が到達できない」ことを、NFR-34 は「写真の初期表示を含めて3秒以内」を求める。

### 決定

**写真のバイト列はアプリケーションサーバを通らない。**

1. **送信**：アプリは時限付き（5分）の送信先URLを発行し、**端末がストレージへ直接送る**。
2. **配信**：`<img src>` に置くのは `/api/{role}/photos/{id}` という**安定したAPIのURL**。ハンドラは到達可否を判定し、**`302` で5分の時限付きURLへ渡す**。リダイレクト自体はキャッシュさせない。

### 根拠

1. **写真の実体をアプリが中継すると、帯域と実行時間をアプリが負担する。** 1施設で入居者80名・月10投稿（NFR-36）の写真が、閲覧のたびにアプリを経由する。NFR-34（3秒）にもNFR-76（月額1万円）にも逆風で、**得るものが何もない**。
2. **時限付きURLを表現に直接埋めない理由**：埋めると、画面を開いたまま放置した家族の写真が静かに表示されなくなる。**安定したURLを挟むと、ブラウザの再取得がそのまま再発行になる**——期限の管理がクライアントから消える。
3. **到達可否の判定は、リダイレクトの前に必ず通る。** 家族なら INV-4、職員・管理者ならテナント条件。**判定を通らずに実体へ到達する経路が存在しない**ことが NFR-44 の担保になる。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| アプリが実体を読んで返す | 上記1。実装は最も簡単だが、帯域・実行時間・コストをすべてアプリが負う |
| 時限付きURLを投稿の表現に直接埋める | 上記2。期限切れの扱いがクライアント側の問題になり、家族に「読み込めない写真」が見える |
| 配信基盤に署名付きの Cookie を使う | 到達制御としては有効だが、**入居者単位の絞り込み（INV-4）を配信基盤の設定で表現することになる**。[ADR-003](#adr-003) の「担保箇所を一系統に寄せる」に反する |
| 推測不能なURLだけで守る（判定なし） | [ADR-012](#adr-012) が「URLの漏洩が即アクセス漏洩になる」として却下した形そのもの |

### 結果（引き受けた代償）

- **写真1枚につき往復が1つ増える**（`302` の分）。NFR-34（3秒）の予算を消費する。緩和は、端末側で縮小してから送ること（長辺1600px程度）と、寸法を表現に含めてレイアウトのずれを防ぐこと。
- **時限付きURLは、その5分のあいだ誰にでも渡せる。** 家族が意図的に転送すれば防げない。**5分という短さで被害の窓を絞り、扱う情報を日常の様子に限る**（NFR-53）ことで上限を下げる——[ADR-005](#adr-005) が採った「確率ではなく被害の上限を下げる」と同じ考え方である。
- **ストレージの設定が安全性の一部になった。** 実体に誰でも到達できる設定になっていれば、この設計は無意味になる。**08 と運用手順（NFR-75）で、公開設定を持たないことを明示する。**

## ADR-028: 投稿の作成に `Idempotency-Key` を必須にする

**ステータス**：承認（2026-09-12） ／ **関連**：NFR-35・FR-105・M2・[ADR-020](#adr-020)

### 文脈

NFR-35 は「施設内の回線品質が低い場合でも、写真の送信が失敗したまま**失われない**こと（再送・保留）」を求める。再送を前提にすると、**応答が届かなかっただけで実は成功していた**場合に、同じ投稿が2件できる。

家族には同じ写真の通知が2回届き（FR-202）、[ADR-010](#adr-010) が「連打は構造的に発生しない」と置いた前提が、**通知ではなく再送の側から崩れる。**

### 決定

- **`POST /api/staff/posts` は `Idempotency-Key` ヘッダを必須とする。** 同じキーでの再送には、最初の結果をそのまま返す。
- キーはクライアント生成の UUIDv7。保持期間は **24時間**。
- 反応にはキーを要求しない——[ADR-020](#adr-020) により `PUT` / `DELETE` で自然に冪等であるため。

### 根拠

1. **再送できることと、再送しても壊れないことは別の要件である。** NFR-35 は前者しか書いていないが、前者だけを実装すると後者が壊れる。
2. **任意ではなく必須にする。** 任意にすると、付け忘れた経路だけが二重投稿を起こし、しかも**低速回線の施設でしか再現しない**——最も気づきにくい形の不具合になる。
3. **キーの生成を投稿画面を開いた時点で行う。** 送信ボタンを押すたびに生成すると、二重タップが別のキーになり意味をなさない。
4. **写真の2段階（[ADR-017](#adr-017)）だけでは足りない。** 写真の再送は安全だが、投稿の作成そのものは1回の書き込みであり、ここを守るものが別に要る。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| クライアントが投稿の識別子を生成し `PUT` で作る | 冪等にはなるが、**外に出る識別子の生成をクライアントに委ねる**ことになる（INV-12・[ADR-014](#adr-014) と噛み合わない） |
| `photoId` の重複で二重投稿を弾く | 実は成立する（INV-8：写真は1投稿にしか属せない）。ただし**エラーとして弾くだけで、最初の結果を返せない**——クライアントは成功したのか失敗したのか分からない |
| 何もしない（再送は運用で吸収） | 職員が二重投稿に気づいて削除する運用になる。M2（60秒）とK1（発信の入口を太く）に逆行する |

### 結果（引き受けた代償）

- **キーの保存先が必要になった**（保存期間24時間）。実体は [07_API設計.md](07_API設計.md) W3 として 08 へ送る。
- 24時間を過ぎたキーの再利用は新規作成になる。**1日以上経ってからの再送で二重投稿が起きうる**が、現場の再送がその時間差で起きることは考えにくい。
- クライアント側に「キーをいつ作り、いつ捨てるか」の規律が要る。**下書きの保持（V10）と同じ寿命に揃える**ことで、規律を1つにまとめる。

## ADR-029: API は機械可読なコードのみ返し、日本語の表示文言を持たない

**ステータス**：承認（2026-09-12） ／ **関連**：NFR-13・FR-204・[ADR-002](#adr-002)・[ADR-012](#adr-012)

### 文脈

NFR-13 は、家族向けの文言に技術用語・カタカナ語・システム用語を使わないことを求める。[ADR-012](#adr-012) はここに「認証画面に限って認証の語を許す」という例外を1つ作った。**例外が1つある規約は、例外が増えやすい。**

一方、エラーの文言は**API が返すこともできるし、クライアントが持つこともできる**。

### 決定

**API は表示用の文言を一切返さない。**

- エラーは問題詳細形式（RFC 9457）で返し、**`code` が唯一の機械可読な契約**とする。`title` は英語（開発者・ログ向け）。
- 日本語の文言は**クライアント側の辞書**で `code` から引く。
- 成功時の応答にも、表示用の文字列を含めない。

### 根拠

1. **語彙の統制を1箇所に集める。** NFR-13 を守っているかどうかを確かめるには、**家族の目に触れる日本語がどこにあるかが1箇所に集まっている**必要がある。API とクライアントに散ると、レビューの対象が2箇所になり、例外が増えたときに追えない。
2. **Cognito 由来の英語メッセージを構造的に遮断できる。** [ADR-002](#adr-002) が申し送った「そのまま露出させない」を、注意ではなく構造で担保する（[ADR-025](#adr-025) と同じ狙い）。
3. **同じ `code` を、主体によって違う言葉で見せられる。** 「失効している」は、家族には別の言い方が要り、管理者にはそのままでよい。**文言が API にあると、主体ごとの言い換えが API の関心事になってしまう。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| API が日本語のメッセージを返す | 上記1〜3。特に、家族向けの語彙統制（NFR-13）が API 側にも要求されることになる |
| API が `code` と日本語の両方を返す | 二重管理。どちらが正なのかが曖昧になり、片方だけ直る |
| 多言語化の枠組みを入れる | 表示言語は日本語のみ（NFR-81）。MVPで必要ない |

### 結果（引き受けた代償）

- **`code` と日本語文言の対応表を、クライアント側に持つ必要がある。** 対応の漏れは「知らない `code` が来たときの既定の文言」で受けるが、**そこに落ちた時点で NFR-13 を満たしているとは言えない**。対応表は画面設計と同時に作る（[07_API設計.md](07_API設計.md) W5）。
- API 単体を叩いた開発者には英語の `title` しか見えない。**OSS として公開する以上むしろ都合がよい**と判断する。
- 新しいエラーを追加するとき、**API と辞書の2箇所を触る**ことになる。`code` を型として1箇所で定義し、辞書側に網羅の検査を置くことで防ぐ。

## ADR-030: 到達範囲の外には `403` ではなく `404` を返す

**ステータス**：承認（2026-09-12） ／ **関連**：NFR-41・NFR-42・NFR-45・INV-4・[ADR-003](#adr-003)

### 文脈

家族が、自分に紐づかない入居者の投稿の識別子を指定したとき——`403`（見る権限がない）と `404`（無い）のどちらを返すか。`403` は「**その識別子のものは存在する**」を伝えてしまう。

### 決定

- **到達範囲の外にあるリソースには `404` を返す。** 他施設・他の入居者・削除済みを区別しない。
- **ただし、主体の種類と名前空間の不一致は `403`**（家族セッションで `/api/admin/*` を叩いた等）。
- **`404` を返したアクセスも操作記録に残す**（NFR-45・[06_リソース設計.md](06_リソース設計.md) R12）。

### 根拠

1. **NFR-41 の「到達する経路が存在しないこと」を、存在の有無まで含めて解釈する。** 識別子は UUIDv7 で推測できない（INV-12）ため総当たりは現実的でないが、**識別子が何らかの経路で漏れた場合に、それが有効かどうかを確かめられる状態を作らない。**
2. **`403` と `404` の区別は、攻撃側にとっては情報で、利用者にとっては何でもない。** 家族が他の入居者の識別子を手で入力する状況は存在しない（そもそも画面に出ない）。**区別が役に立つ相手がいない。**
3. **見えなくすることと、気づかないことは違う。** `404` で黙って返すと運用側も気づけないため、記録は必ず残す。[ADR-003](#adr-003) の「防止だけに賭けない。越境を検出できるようにする」に対応する。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 権限不足は一律 `403` | 存在の有無を漏らす。上記1 |
| `404` を返し、記録も残さない | 越境の試行が検出できない。[ADR-003](#adr-003) の緩和策が成立しなくなる |
| 名前空間の不一致も `404` | 誤りの原因が利用者にも開発者にも分からなくなる。**ここで隠すべき情報は無い** |

### 結果（引き受けた代償）

- **開発中の切り分けが難しくなる。** 「権限が無い」のか「本当に無い」のかが応答から分からない。`traceId` と操作記録で追える形にして補う（[07_API設計.md](07_API設計.md) 3-10・3-11）。
- **記録の量が増える。** 誤操作による `404` も残るため、越境の試行との区別がつきにくい。MVPでは区別せずに記録し、量が問題になったら絞る。

## ADR-031: MVPの通知はメールで送り、本文に投稿の内容を含めない

**ステータス**：承認（2026-09-12） ／ **関連**：[05_要件定義.md](05_要件定義.md) U4・[06_リソース設計.md](06_リソース設計.md) V1・FR-202・NFR-32・NFR-55・[ADR-012](#adr-012)

### 文脈

U4（通知をどの経路で届けるか）は要件定義から設計へ送られた未決事項である。判断の材料は3つ。**NFR-32**（家族側はアプリのインストールを必須としない）、**NFR-34**（通知から表示まで3秒）、そして [ADR-012](#adr-012) が**家族のメールアドレスを名簿の必須項目にした**こと。

### 決定

1. **MVPの通知はメールで送る。** 通知先（R11）の方式は `email`、宛先は家族のメールアドレスと常に一致する。
2. **本文に投稿の内容（写真・本文）を含めない。** 「新しいお知らせがあります」と、投稿1件への直接リンクのみ。
3. **投稿の作成が確定したあと、トランザクションの外で送る。** 送信の失敗で投稿の作成を取り消さない。

### 根拠

1. **ブラウザのプッシュ通知は NFR-32 と衝突する。** iOS でプッシュを受け取るにはホーム画面への追加が要る。これは実質的にインストールであり、**P2 の Pain（インストールでつまずく）にそのまま当たる**。最も弱いユーザーが受け取れない通知経路は、[04_to-be.md](04_to-be.md) 3-3 の原則に反する。
2. **メールの到達性という運用負荷は、すでに引き受け済みである。** [ADR-004](#adr-004) はこれを避けるために「システムが配信しない」設計を採ったが、そのADRは撤回され、**[ADR-012](#adr-012) が招待メールという形でメール配信を必須経路に組み込んだ**。通知をメールにしても、**新たに増える負荷は無い**——同じ配信経路を使い回すだけである。
3. **SMS は名簿の正確さに依存し、費用も乗る**（[ADR-004](#adr-004) の代替案比較と同じ理由）。MVPでは採らない。
4. **本文に内容を含めない理由は NFR-55。** メールは転送・共有の経路になる。写真をメールに載せると本システムの外に個人情報の複製が残り、**失効（FR-405・INV-7）が効かなくなる**——施設が制御を握っているという [ADR-012](#adr-012) の柱が、通知経路の側から崩れる。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| ブラウザのプッシュ通知 | 上記1。ホーム画面への追加が必要で NFR-32・P2 に反する |
| SMS | 上記3。電話番号を名簿で正確に持つ必要があり、C5（仮定・要検証）に依存する。1通ごとの費用も乗る |
| LINE への配信 | P2 が唯一使いこなせるUIだが、**特定事業者のアカウント保有が受信の必須条件になる**（[ADR-004](#adr-004) と同じ理由で却下）。将来の追加経路の候補 |
| メール本文に写真を載せる | 上記4。**メールを開くだけで見られる**のは家族には親切だが、NFR-55 と失効の担保を同時に壊す |
| 通知を送らない（見に行く方式） | FR-202 が「通知される」ことを要求している。K2（太郎ボトルネック）の解消に、届くことが要る |

### 結果（引き受けた代償）

- **通知を受けた家族に「サインインして見る」往復が生じる。** P2 にとっては壁である。ただし**これは [ADR-012](#adr-012) が引き受けた代償の一部**であり、本ADRが新たに増やした壁ではない——認証が標準的である以上、どの通知経路を選んでも同じ往復が生じる。
- **メールの到達性（迷惑メール判定・送信ドメイン認証・バウンス処理）が運用項目になった。** 招待メールと同じ経路なので**運用対象は増えない**が、**そこが詰まると招待も通知も同時に止まる**という単一障害点にはなる。
- **P2 は「メールアドレスを持っているが使えない」**（[01_ペルソナ.md](01_ペルソナ.md)）。通知は送られるが**届かない**。これは K6 が MVP で解けないことの別の現れであり、[ADR-012](#adr-012) の代償の範囲内である。
- 次段で [ADR-004](#adr-004) を再開する際、**通知経路も同時に見直す対象になる**（認証と通知が同じ「P2に届く経路」の問題であるため）。

## ADR-032: セッションの有効期間を主体ごとに変える

**ステータス**：承認（2026-09-12。2026-09-13 に AC-B4 との対応を追記。**2026-09-13、[ADR-047](#adr-047) を受けて「端末」を「職員」に改訂**） ／ **関連**：[06_リソース設計.md](06_リソース設計.md) V4・AC-B3・**AC-B4 ①**・FR-403・FR-406・[ADR-046](#adr-046)・[ADR-047](#adr-047)・[ADR-025](#adr-025)

### 文脈

V4 は「セッションの有効期間を家族・端末・管理者で別々に決める」を設計へ送っていた。3者は**置かれている条件がまったく違う**。

| 主体 | 条件 |
|---|---|
| 職員 | 私物・共用どちらの端末もありうる（[ADR-046](#adr-046)）。1日に何度も使う。サインインの手間が M2（60秒）を直接削る。**施設の全入居者に到達できる** |
| 家族 | 私物の端末。週2〜3回しか開かない。再認証できない層を含む（[ADR-012](#adr-012)） |
| 管理者 | 権限が最も重い（名簿・失効・全投稿・書き出し）。使う頻度は低い |

### 決定

| 主体 | 有効期間 | 延長 |
|---|---|---|
| 職員 | **30日** | アクセスのたびに延長する |
| 家族 | **30日** | アクセスのたびに延長する |
| 管理者 | **12時間** | 延長しない |

### 根拠

1. **職員を家族と同じ30日にするのは、物理的な境界が無くなったからである。** 旧版は端末を90日とし、その根拠を「端末は施設の管理下にあり外に持ち出されない」（[ADR-007](#adr-007)）に置いていた。**[ADR-046](#adr-046) の C1 撤回でこの境界は消え、職員の端末が施設の管理下にある保証はない。** 家族より長くする根拠が残っていないため、同じ値にする。
2. **職員の実用性は、期間の長さではなく延長で担保する。** 職員は1日に何度も使うため、延長する方式であれば**30日でも実質的に切れない**。M2 に効くのは期間そのものではなく、**延長が確実に働くこと**である。
3. **家族の30日は「見ている限り切れない」を狙った値である。** 想定投稿頻度は週2〜3件（M1）なので、通知を受けて開いている家族のセッションは延長され続ける。**切れるのは、1ヶ月見ていない家族だけ**になる。
4. **延長する方式を採るのは、[ADR-005](#adr-005) が指摘した「期限切れ＝サイレントな離脱」を減らすため。** 撤回されたのは「実質無期限にする」という決定であって、**論点そのものは生きている**。使っている人が黙って締め出されない形にはできる。
5. **管理者だけ延長しない。** 権限が重く、かつ使用頻度が低いため、放置された管理者のセッションが生き続ける状態を作らない。12時間は初期設定（NFR-74：4時間以内）を1セッションで通せる長さである。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 3者とも同じ期間にする | 管理者だけ条件が違う。管理者に合わせれば現場が回らず（M2）、職員・家族に合わせれば**最も重い権限が30日残る** |
| 家族も実質無期限にする | [ADR-005](#adr-005) そのもの。[ADR-012](#adr-012) で撤回済み |
| 家族を延長しない固定期限にする | 見ている家族も一律に締め出される。上記4 |
| 職員を旧版の90日のまま残す | 90日は端末の物理的境界（C1）を根拠にした値であり、[ADR-046](#adr-046) でその根拠が消えた。**根拠を失った数値を惰性で残さない** |

### 結果（引き受けた代償）

- **1ヶ月見ていない家族は、次に通知が来たとき再入力を求められる。** AC-B4 ①（一定期間の経過）が明示的に認めた契機なので要件違反ではないが、**最も見ていない＝最も再認証しにくい層に、最も再認証が必要になる**という逆向きの構造が残る。[ADR-012](#adr-012) の代償の一部であり、次段で AC-A に戻る際に消える。
- **本ADRの有効期間は、AC-B4 ① の実体である。** AC-B4 は再認証の契機を①一定期間の経過／②明示的なログアウト（FR-406）／③認証情報の失効（FR-405）の**3つに限定**しており、本ADRが決めるのは①だけである。**②③を理由にセッションが切れることは本ADRの数値と無関係**に起きる。また、**3つ以外の理由で切らない**——IP やユーザーエージェントの変化を検知して再認証を求める方式は採らない。家族は移動中に閲覧する（P1）ため、誤検知がそのまま「サイレントな離脱」（根拠3）になる。
- **職員の30日は、失効を明示操作に依存させる。** 職員が退職したとき、管理者の失効操作（FR-405）が漏れると最大30日アクセスが残る。しかも到達範囲は**施設の全入居者**である。旧版は同じ問題を「端末を手放すとき」として記録していたが、**入退職は端末の入れ替えよりはるかに頻繁に起きる**（[ADR-047](#adr-047) の代償）。**導入手順書（NFR-75）に、退職時の手順として明記する。**
- 数値はいずれも**実測ではなく設定値**である。[05_要件定義.md](05_要件定義.md) 脚注と同じ扱いで、実運用で見直す。

## ADR-033: 写真掲載同意の撤回は、既存の投稿にも遡って及ぶ

**ステータス**：承認（2026-09-12） ／ **関連**：[06_リソース設計.md](06_リソース設計.md) V5・FR-504・NFR-51・NFR-52・INV-3

### 文脈

V5 は「写真掲載同意を『無』に変更したとき、既存の投稿をどう扱うか」を設計へ送っていた。INV-3 は**新しい投稿を作れない**ことしか定めていない。

同意は入居者の属性として持ち、履歴は操作記録で担保する（[ADR-022](#adr-022)）。つまり**「いつまで同意があったか」は分かるが、投稿の側に同意の状態は写っていない。**

### 決定

**同意を「無」に変更すると、その入居者の既存の投稿はすべて家族から見えなくなる。**

- 投稿を削除はしない。管理者は引き続き事後に閲覧できる（FR-505）。
- 変更の応答に**影響を受ける件数**を含め、管理者が結果を把握できるようにする。
- 同意を「有」に戻すと、再び見えるようになる。

### 根拠

1. **同意の撤回は、将来の掲載だけでなく現在の掲載にも及ぶ**と解釈するのが、個人情報保護法の趣旨（NFR-51）に沿う。「これから撮らない」だけで「今出ているものはそのまま」は、撤回を申し出た側の期待と食い違う。
2. **撤回が起きる場面を考えると、遡及が要る。** 同意が「無」に変わるのは、本人または家族から申し出があったときである。**その申し出は、たいてい「今出ているもの」についてのものである。**
3. **削除ではなく非表示にする理由**は [ADR-019](#adr-019)（論理削除に統一）と同じ。撤回の判断が誤りだったときに戻せる必要があり、また操作記録との整合も要る。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 既存の投稿はそのまま見せる | 上記1・2。**撤回した側の期待と食い違う** |
| 既存の投稿を物理削除する | 戻せない。誤操作の影響が回復不能になる。[ADR-019](#adr-019) に反する |
| 投稿ごとに「投稿時点の同意」を持ち、それで判定する | 法的には筋が通る（撮影時に同意があった）が、**撤回が何の効果も持たなくなる**。[ADR-022](#adr-022) が「同意は入居者の属性であり、履歴は操作記録で担保する」と決めた構造とも噛み合わない |
| 管理者に「既存をどうするか」を選ばせる | 選択肢を増やすと、**急いでいる場面で誤った側が選ばれる**。P5 の「運用が分岐すると事故る」（[ADR-008](#adr-008)）に反する |

### 結果（引き受けた代償）

- **家族が見ていた写真が、予告なく見えなくなる。** 家族への説明は施設の運用に委ねることになる（システムは通知しない——通知すると、撤回の事実そのものを他の家族に伝えることになる）。
- **誤って「無」にすると、その入居者の全投稿が一斉に消える。** 影響件数を応答に含めるのはこのためで、**確認画面に出す値として使う**。戻す操作はあるが、その間に家族が見に来れば空の画面になる。
- 家族向けの一覧が**急に短くなる**場面が生じる。「消えた」ことを説明しない設計であり、NFR-13（技術用語を使わない）の範囲では説明のしようもない。**運用上の注意として導入手順書（NFR-75）に記載する。**

## ADR-034: 退居時に保存を選んだデータは1年で自動削除する

**ステータス**：承認（2026-09-12） ／ **関連**：[06_リソース設計.md](06_リソース設計.md) V6・FR-602・NFR-51・INV-11・[ADR-019](#adr-019)

### 文脈

V6 は「退居後のデータ保持期間」を設計へ送っていた。FR-602 は、退居時に**保存か削除かを管理者が選べる**ことだけを定めている。**「保存」を選んだ場合に、いつまで持つのか**が決まっていない。

INV-11 により、退居と同時に紐づく家族はすべて失効する。**つまり保存されたデータを見られるのは施設の管理者だけ**である。

### 決定

**「保存」を選んだ場合、退居日から1年で自動削除する。**

- 退居処理の応答に**削除予定日**を含め、管理者に明示する。
- 「削除」を選んだ場合は即時に削除する（従来どおり）。
- 自動削除は定期実行が行う（[ADR-035](#adr-035)）。

### 根拠

1. **「保存」は無期限を意味しない。** 個人情報は利用目的を達成したら遅滞なく消すのが原則（NFR-51）であり、退居して家族も失効した時点で、当初の利用目的（施設から家族へ日常を届ける）は終わっている。**無期限に持つことを正当化する根拠が無い。**
2. **それでも即時削除を既定にしない理由**は、退居直後に「最後の様子をもう一度見たい」という申し出が家族から来うること、および退居手続きの混乱の中で誤って削除を選んだ場合に取り返しがつかないことである。**1年は、その揺り戻しを吸収するための猶予**として置く。
3. **期間を管理者に選ばせない。** 選択肢を増やすと施設ごとに運用が分岐する（[ADR-008](#adr-008)：P5 の「一律が望ましい」）。**選ぶのは保存か削除かの二択までとし、期間は決め打ちにする。**
4. **削除予定日を明示する**ことで、「保存したつもりが消えていた」を防ぐ。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 無期限に保存する | 上記1。利用目的が終わったデータを持ち続ける根拠が無く、NFR-51 に反する |
| 退居と同時に必ず削除する | 上記2。誤操作と揺り戻しを吸収できない。FR-602 が「選択できる」と要求している以上、選択肢として成立しない |
| 保持期間を施設が設定できる | 上記3。設定項目が増え、運用が分岐する |
| 1年ではなく5年（記録の一般的な保存年限に合わせる） | **本システムは法定記録ではない**（[04_to-be.md](04_to-be.md) 3-1：法定記録の公開には踏み込まない）。介護記録の保存年限を持ち込む理由が無い |

### 結果（引き受けた代償）

- **1年という数値に実証的な根拠は無い。** 揺り戻しの猶予として置いた設定値であり、[05_要件定義.md](05_要件定義.md) 脚注と同じ扱いで実運用で見直す。**施設から「もっと短く」と言われる可能性のほうが高い**と見ている。
- **削除されたことに、施設が気づかない可能性がある。** 削除予定日を退居処理の応答に出すだけでは、1年後には忘れられている。**期限が近づいたときに管理者の画面で知らせるかは、画面設計で扱う**（本ADRでは決めない）。
- 自動削除が**写真の実体まで及ぶか**は、削除済み投稿の写真の扱い（[07_API設計.md](07_API設計.md) W7）と揃えて 08 で決める。**片方だけ消えてストレージに孤児が残る形にしない。**

## ADR-035: 定期実行の置き場を1つに集約する

**ステータス**：承認（2026-09-12） ／ **関連**：C6・[06_リソース設計.md](06_リソース設計.md) V3・INV-6・INV-8・[ADR-031](#adr-031)・[ADR-034](#adr-034)

### 文脈

設計を進めた結果、**リクエストの外で動く処理**がいくつも現れた。

| 処理 | 出所 |
|---|---|
| エクスポートの生成 | V3・FR-601（写真を含むため同期で返せない） |
| 仮のまま残った写真の掃除 | INV-8・[ADR-017](#adr-017) |
| 招待の期限切れ | INV-6・[06_リソース設計.md](06_リソース設計.md) R7 |
| 通知メールの再試行 | [ADR-031](#adr-031) |
| 期限切れセッションの掃除 | [ADR-025](#adr-025) |
| 退居後データの自動削除 | [ADR-034](#adr-034) |
| エクスポートの期限切れ | [06_リソース設計.md](06_リソース設計.md) R15 |

C6（専任の運用担当を置けない／運用負荷の低さが機能の豊富さより優先する）に照らすと、**これらに個別の仕組みを当てるのは最も避けたい形**である。

### 決定

**定期実行の置き場を1つだけ作り、上記をすべてそこに寄せる。**

- 1つの入口が、登録された処理を順に実行する。
- **処理の追加は、この1箇所に関数を1つ足すこと**で済む形にする。
- **何で動かすか**（スケジューラの実体）は本ADRで決めない（[07_API設計.md](07_API設計.md) W4）。決めるのは**置き場が1つであること**である。

### 根拠

1. **C6 に対して効くのは「処理を減らすこと」ではなく「運用対象を増やさないこと」である。** 7つの処理それぞれに仕組みを当てれば運用対象は7つ、1つに寄せれば1つになる。**処理の数は減らないが、見るべき場所の数は減る。**
2. **個々の処理は、どれも単独では仕組みを立てるほどの規模がない。** 掃除も期限切れも、実体は条件に合う行を消すだけである。**規模の小さい処理が多いときこそ、置き場を共有する価値が大きい。**
3. **失敗に気づく場所が1つになる。** 7箇所に散ると、どれか1つが静かに止まっていても気づけない。**INV-8（仮写真の掃除）が止まればストレージが膨らみ、[ADR-034](#adr-034) の自動削除が止まれば消えるはずの個人情報が残る**——どちらも静かに壊れる種類の不具合である。
4. **[ADR-023](#adr-023) と整合する。** 発信状況を保存せず都度求めると決めたのは、「更新漏れが検出できない」ことを避けるためだった。**定期実行も、止まったことが検出できる形に置く**という同じ考え方に立つ。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 処理ごとに個別の仕組みを当てる | 上記1・3。運用対象が処理の数だけ増え、C6 に正面から反する |
| ジョブキューの基盤を導入する | 再試行も優先度も扱えて筋はよいが、**MVPの処理はどれも「条件に合う行を消す」規模**であり、基盤に見合わない。C6 に対して過剰 |
| リクエストの処理のついでに実行する（アクセスがあったときに掃除する） | 仕組みは増えないが、**アクセスが無い施設では永久に実行されない**。退居後データの自動削除（[ADR-034](#adr-034)）がこれでは成立しない |
| エクスポートだけ同期で生成する | 写真を含むため実行時間の制限を超えうる。[06_リソース設計.md](06_リソース設計.md) R15 が「同期で返す設計にしない」と決めている |

### 結果（引き受けた代償）

- **1箇所が止まると、7つすべてが止まる。** 集約の裏返しである。緩和は、**各処理の最終実行時刻を記録し、管理者ではなく提供側が見られるようにする**こと（施設の関心事ではないため管理画面には出さない）。
- **実行の間隔を、最も急ぐ処理に合わせることになる。** 通知の再試行は数分単位で効いてほしいが、退居後データの削除は1日1回で足りる。**間隔を分けたくなった時点で、この決定は見直しの対象になる**——そのときは処理ごとの間隔を持たせる形へ拡張する（置き場は1つのまま）。
- 実行の途中で失敗したとき、**後続の処理まで巻き添えにしない**ようにする必要がある。1つの処理の例外が全体を止めない形にすることを、実装上の必須事項とする。

## ADR-036: 文字サイズと当たり判定を全画面で共通にし、管理者画面の密度は余白と列で作る

**ステータス**：承認（2026-09-13） ／ **関連**：NFR-12・NFR-14・NFR-16・01_ペルソナ P5・[09_画面設計.md](09_画面設計.md) 2-1

### 文脈

NFR-1群には**スコープの書かれていない要件**が混ざっている。NFR-11・13・15・17 は「家族向け」「職員の」と対象が明記されているが、**NFR-12（本文18px以上）・NFR-14（当たり判定48×48以上）・NFR-16（詰め込まない）・NFR-18（コントラスト）には対象の限定がない。**

一方 [01_ペルソナ.md](01_ペルソナ.md) は P5 について「管理者向けの画面は**情報密度が高くてよい**（P1〜P4と違い、業務時間にPCの前で見る）」と書いている。入居者80名・職員50名・家族200名（NFR-36）の名簿を 18px・48px の刻みで並べると、一覧は縦に伸び、Excel に慣れた P5 の作業感からは遠ざかる。

**要件を素直に読むと管理者画面にも 18px／48px が及び、ペルソナを素直に読むと及ばない。**

### 決定

**文字サイズと当たり判定は、管理者画面を含む全画面で共通の下限を守る**（本文18px以上・当たり判定48×48以上）。

- 管理者画面の密度は、**文字を小さくすることではなく、余白を詰め列を増やすことで作る。**
- 表の行は**行全体を当たり判定**にすることで、48pxの高さを確保しながら密度を保つ。
- 管理者画面は**幅1280px以上を主**とし、密度を横方向に逃がす。

### 根拠

1. **画面設計が要件を緩めるのは順序が逆である。** NFR-14 の対象を狭めたいなら、それは [05_要件定義.md](05_要件定義.md) を改訂する判断（step4）であって、設計工程が黙って例外を作る話ではない。**要件に書かれていない限定を、設計側で読み込まない。**
2. **密度を作っているのは、本当は文字の大きさではない。** Excel の作業感の正体は「1画面に多くの行が見えること」であり、それは**行の高さと余白**で決まる。18px の文字に 48px の行高を与えても、14px の文字に 44px の行高を与えるのと、見える行数はほとんど変わらない。**削る余地があるのは余白であって文字ではない。**
3. **管理者は PC で見る**（P5）。家族・職員がスマホの幅360〜430pxで戦っているのに対し、管理者には**横1280px という逃げ道がある。** 縦に詰めるより、列を増やすほうが素直である。
4. **例外を1つ作ると、どこまでが例外かの線引きが要る。** 「管理者画面は例外」と決めると、次は「管理者画面の中でも表だけ」「表の中でも補足列だけ」と広がる。**下限を1つにしておけば、線引きの議論そのものが発生しない。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| NFR-1群を「家族・職員向け」に限定し、管理者は別基準 | 上記1。**要件のスコープを設計工程が書き換えることになる。** どうしても必要なら [05_要件定義.md](05_要件定義.md) に差し戻すのが筋 |
| 全画面を家族と同じ寸法（20px・64px）にする | P5 の作業に耐えない。名簿80名の確認が縦スクロールの作業になり、NFR-74（初期設定4時間以内）を自ら苦しくする |
| 管理者が文字サイズを切り替えられるようにする | 設定項目が増え、施設ごとに運用が分岐する（[ADR-008](#adr-008)：P5 の「一律が望ましい」）。**しかも切り替えた先が要件違反になる** |

### 結果（引き受けた代償）

- **管理者画面は横に広い前提になった。** スマホから管理操作をするのは快適でない。P5 は業務PCで見る（01_ペルソナ）ため引き受けるが、**「出先で家族を1人だけ失効させたい」といった場面では不便になる。** FR-405（即時失効）は急ぐ操作でありうるので、**狭い幅では列を落として縦に積む**対応だけは入れる。
- **P5 の「情報密度が高くてよい」を、文字の大きさとしては満たしていない。** 満たしたのは「1画面に多くの行が見える」ことまでである。実際に P5 が窮屈だと言った場合、**見直すのは本ADRではなく NFR-14 のスコープ**（＝[05_要件定義.md](05_要件定義.md)）であることを、ここに記録しておく。

## ADR-037: 家族向けの移動を「前進する導線」だけで構成する

**ステータス**：承認（2026-09-13） ／ **関連**：NFR-11・NFR-15・[09_画面設計.md](09_画面設計.md) 1-2・3章

### 文脈

NFR-15 は「家族の閲覧導線に、横スワイプ・長押し・**階層移動を必須としない**」と定める。しかし家族向けの画面は最低でも3つ必要になった——一覧（SF-01）、通知からの着地点（SF-02）、設定（SF-03）。**画面が複数ある以上、移動は発生する。**

問題は移動の有無ではなく、**移動したあとに戻れるか**である。P2 はブラウザの戻るボタンを使いこなすとは限らず、iPhone のジェスチャによる戻るは NFR-15 が避けたい操作そのものである。

### 決定

**家族向けの移動は、「次に行く先が書かれた大きな導線」だけで構成する。**

- 階層は**2階層まで**（SF-01 ⇄ SF-02、SF-01 → SF-03 → SF-01）。
- **「戻る」と書かない。行き先を書く**（SF-02 の末尾は「ほかの お知らせも 見る」）。
- **ブラウザの戻る・スワイプによる戻るを前提にしない**（使っても壊れないが、それ無しで完結する）。
- パンくず・タブ・ドロワーを置かない。
- **さかのぼりは無限スクロールにせず、「もっと前を 見る」ボタンにする。**

### 根拠

1. **「戻る」は行き先を指していない。** どこへ戻るのかは、そこへ至った経路に依存する。通知メールから SF-02 に着地した人にとって、「戻る」はメールアプリである。**経路によって意味が変わる語を、P2 の画面の唯一の出口にしない。**
2. **行き止まりを作らないことが、戻る導線の代わりになる。** どの画面にも「次にできること」が1つ書いてあれば、利用者は前に進むだけで元の場所に着く。**巡回する構造にすれば、戻る操作は要らない。**
3. **無限スクロールには終わりが見えない。** 読み込みが自動で走ると、P2 には「自分が何かを起こした」認識がないまま画面が伸びる。**明示的なタップは、押した人が結果を予期できる**——NFR-11（説明を読まずに達成できる）は、予期できることを含む。
4. 常設のナビゲーションを置かないことは [ADR-039](#adr-039) と同じ判断に立っている。**常時画面にある操作は、常時押し間違えられる。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 各画面の左上に「戻る」を置く | 上記1。加えて左上は、片手持ちで最も押しにくい位置である |
| ブラウザの戻るに任せる（画面内に導線を置かない） | P2 がブラウザの UI を認識している保証がない。**アプリのように見える画面で、ブラウザの機能を使わせるのは説明が要る**（NFR-11 違反） |
| 無限スクロール | 上記3。加えて、読み込みの途中で新しい投稿が入ると既読が二重に現れる（[07_API設計.md](07_API設計.md) 3-6 がカーソル方式を選んだ理由と同根） |
| 下部タブで一覧・設定を並べる | 設定が常時画面に出る。[ADR-039](#adr-039) に反する |

### 結果（引き受けた代償）

- **P1・P3 にとっては操作が冗長になる。** 「もっと前を 見る」を何度も押すのは、無限スクロールに慣れた P3（SNSネイティブ）には遅い。**最も弱いユーザーに合わせた結果、慣れたユーザーが少し損をする**——これは [04_to-be.md](04_to-be.md) 3-3 が置いた原則の、画面上での現れ方である。
- **画面が増えると、この規則の維持コストが上がる。** 2階層という制約は、次段で機能を足すとき（コメント＝[ADR-011](#adr-011)、まとめ配信＝[ADR-010](#adr-010)）に最初に破られる候補である。**破るときは、NFR-15 を満たす別の形を同時に示すこと**を条件とする。

## ADR-038: 反応を「ありがとう」の文字ボタンにし、もう一度押して取り消す

**ステータス**：承認（2026-09-13） ／ **関連**：FR-301・NFR-13・NFR-15・NFR-18・[ADR-011](#adr-011)・[ADR-020](#adr-020)

### 文脈

[ADR-011](#adr-011) により、家族が持つ表現は一押しだけである。[ADR-020](#adr-020) により、それは冪等な1件であり、取り消しは削除で表す。**残っているのは「画面上でそれをどう見せ、どう取り消させるか」である。**

制約が3つ重なる。**NFR-13**（カタカナ語を使わない＝「いいね」「リアクション」が使えない）、**NFR-15**（長押しを使えない）、**NFR-18**（色だけで状態を伝えられない）。

### 決定

- ボタンの表示は**文字で「ありがとう」**。アイコンのみにしない。
- 押した後は**「ありがとうを つたえました ✓」**に変わる。**状態を文字で書く。**
- **取り消しは、同じボタンをもう一度押す**（トグル）。
- 押した直後にだけ、**「まちがえたら、もう一度 おしてください」**を直下に出す。

### 根拠

1. **アイコンは学習を要求する。** ハートや拍手の意味は、SNS の文脈を共有している人にしか通じない。P2 のスマホ用途は LINE のみ（01_ペルソナ）であり、**共有されている語彙は「ありがとう」という日本語のほうである。**
2. **誤操作から自力で戻れることは、NFR-11 の一部である。** [07_API設計.md](07_API設計.md) 4-3 が `DELETE .../reaction` について書いたとおり、**誤操作から復帰できないことは P2 にとって利用の終わりに近い。** 取り消し手段を持たない選択肢は、この時点で落ちる。
3. **取り消しの手段として使えるものが、ほぼ1つしか残らない。** 長押しは NFR-15 で使えず、別ボタンを常設すると 1画面の主要操作が2つになる（NFR-16・[ADR-036](#adr-036) の密度規則）。**同じボタンのトグルが、制約を全部通る唯一の形である。**
4. **トグルの弱点（押せば消えると分からない）は、説明文で塞ぐ。** ただし常時は出さず、**押した直後にだけ**出す——常設すると、まだ押していない人にまで取り消しの説明を読ませることになる。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| ハート等のアイコンのみ | 上記1。加えて、押した状態を色の変化だけで示すことになり NFR-18 に反する |
| 取り消しを持たない（押したら確定） | 上記2。誤タップが取り返しのつかない操作になる |
| 長押しで取り消す | NFR-15 に正面から反する |
| 取り消し専用のボタンを常設する | 1件あたりの操作要素が2つになり、一覧の1件が縦に伸びる（NFR-16） |
| 押す前に確認を挟む | 「一度の操作で伝えられる」（FR-301）に反する。**一押しの価値は、押すだけで済むことにある** |

### 結果（引き受けた代償）

- **二度押しで、意図せず取り消される。** 反応が届いたことを職員が見た後に取り消されると、職員の側には「消えた」だけが残る（SS-01 の一覧から消える）。緩和は2点——**状態が常に文字で書かれていること**と、**再度押せば戻ること**。**通知は送っていない**ので、職員が取り消しに気づく経路もない（[ADR-021](#adr-021)）。
- **M4（反応率50%）の測定値に、押し直しの揺れが乗る。** 冪等な1件として数える（[ADR-020](#adr-020)）ので二重計上はされないが、**取り消された反応は数に残らない。** 指標としては「押した人の数」ではなく「いま反応が付いている投稿の割合」を見ることになる。
- 反応の種類を増やすとき（[ADR-011](#adr-011) の次段）、**トグルという形が最初に壊れる。** 種類が2つ以上あれば「もう一度押す」は曖昧になる。そのときはボタンの形から作り直す。

## ADR-039: 家族の設定を一覧の末尾に置き、常設のナビゲーションを作らない

**ステータス**：承認（2026-09-13） ／ **関連**：FR-203・FR-406・NFR-13・NFR-16・[07_API設計.md](07_API設計.md) W6

### 文脈

[07_API設計.md](07_API設計.md) W6 は「家族向け画面にサインアウトを置くか」を決着させ、**置く**とした（FR-406・AC-B4 ②）。NFR-13 は「ログアウトはこの語彙例外の唯一の持ち出し先であり、**常時表示せず設定相当の場所に置く**」と条件を付けている。通知の停止（FR-203）も同じ場所に要る。

**つまり「設定」という画面は要るが、そこへの入口を常時画面に出してはいけない。**

### 決定

- **設定への導線は、一覧（SF-01）の末尾に1つだけ置く。**
- ヘッダに歯車・メニュー・アイコンを置かない。**常設のナビゲーションを持たない。**
- 通知メールのフッタにも、設定への直接リンクを置く。

### 根拠

1. **常時画面にある操作は、常時押し間違えられる。** P2 が日常で触るのは SF-01 と SF-02 の2画面であり、そこに設定への入口が常駐していると、**誤って入る面を毎回の閲覧に晒すことになる。** 一覧の末尾なら、スクロールしきった人しか到達しない。
2. **到達する必要がある人が、ちょうど到達できる。** 通知を止めたいのは P3（頻度を自分で調整したい）と P1 であり、どちらもスクロールで下端に着ける。**P2 は到達しないが、到達する必要もない**——[ADR-010](#adr-010) が「設定項目を持たないこと自体が P2 への配慮」と決めた延長にある。
3. **通知を止めたい人は、たいてい通知を見ている最中である。** メールのフッタに置けば、一覧を開いて下までスクロールする必要がない。**止めたい気持ちが起きた場所に、止める手段を置く。**
4. NFR-16（1画面に情報を詰め込まない）に照らして、**ヘッダに置けるものは入居者の名前だけ**である。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| ヘッダに歯車アイコン | 上記1。加えてアイコンのみの表現は [ADR-038](#adr-038) と同じ理由（学習を要求する）で採らない |
| 下部タブに「設定」を並べる | 常時表示になり NFR-13 の条件に反する。[ADR-037](#adr-037)（常設ナビを持たない）とも衝突 |
| メールのフッタにだけ置く | メールを開けない・消してしまった家族が到達できなくなる。**ログアウト（FR-406）は AC-B4 ② の唯一の契機**であり、到達不能にはできない |
| 設定画面を持たず、通知停止をメール内のリンクだけで行う | ログアウトの置き場が無くなる（W6 の決着に反する） |

### 結果（引き受けた代償）

- **P2 が偶然そこに到達し、ログアウトを押す可能性が残る。** 押されれば、次に必要なのはメールアドレスとパスワードの入力であり——**P2 にとっては利用の終わりになりうる。** 緩和として確認を1枚挟み、「もう一度 入るには、メールアドレスと パスワードが 必要です」と書くが、**リスクはゼロにならない。** これは [ADR-012](#adr-012) が作った構造上の弱点が、画面に現れたものである。
- **設定の発見性は低い。** 「通知を止めたいのに見つからない」という問い合わせが施設に行きうる（M5：問い合わせが増えていないこと、に逆行する）。メールのフッタがその緩和だが、**観測されたら位置を見直す。**
- 「この方の ようすを 見ている人」（[06_リソース設計.md](06_リソース設計.md) 6-2 注2）も同じ場所に置くことになり、**設定画面に3つの関心事が同居した。** 増えるようなら分割するが、MVP では分けない。

## ADR-040: 投稿の作成を1画面の縦1列に積み、ウィザードにしない

**ステータス**：承認（2026-09-13） ／ **関連**：M2・FR-105・NFR-17・[ADR-006](#adr-006)・[ADR-017](#adr-017)

### 文脈

投稿に必要な入力は4つある——入居者・写真・本文（任意）・投稿者。これをステップに分ける（入居者 → 撮影 → 本文 → 確認）か、1画面に積むかで、M2（撮影開始〜送信完了60秒）と FR-105（中断されても失われない）への効き方が変わる。

現場は**呼び出しが常時入る職場**（P4）であり、**中断は例外ではなく前提**である。

### 決定

**1画面の縦1列に、上から「入居者 → 写真 → ひとこと → 投稿する人 → 送る」を積む。**

- ステップ分割・確認画面を持たない。
- **送信ボタンは画面下端に固定**する（NFR-17：片手で完結）。
- 写真が着くまで送信ボタンを押せない状態にし、**理由を文字で書く。**

### 根拠

1. **中断からの復帰が、ウィザードでは重くなる。** ステップに分けると、復帰時に「どのステップにいたか」を復元する必要が生じる。**1画面なら、復元するのは値だけである**（[09_画面設計.md](09_画面設計.md) 5-2：`photoId`・入居者・職員・本文の4つ）。FR-105 の実装が単純になる。
2. **「あと何をすれば送れるか」が一望できる。** 必須は写真1枚だけ（[ADR-006](#adr-006)）であり、**残りは空のままでよい**ことが、画面を見れば分かる。ウィザードでは各ステップを通過させられるため、**任意の項目まで「通らされる」形になり、[ADR-006](#adr-006) の意図が画面で裏返る。**
3. **画面遷移そのものが秒を食う。** 4ステップなら遷移が3回。M2 の60秒に対して無視できる量ではない。
4. **確認画面を置かない**のは [ADR-009](#adr-009) と同じ筋である。誤りは事後の削除（FR-106）で回収でき、**回収可能な誤りのために、毎回の発信に1画面を足すのは割に合わない。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| ステップ分割（ウィザード） | 上記1〜3。中断前提の現場と噛み合わない |
| 1画面だが送信前に確認を挟む | 上記4。M2 に効かず、[ADR-009](#adr-009) の判断とも一貫しない |
| 撮影から始める（入居者を後で選ぶ） | 撮ってから「誰の写真か」を選ぶ順序は、同意なしの入居者を撮った後に気づく形になる（INV-3）。**選べない人は最初から選ばせない**ほうが、60秒の中で損が少ない（[07_API設計.md](07_API設計.md) 4-2 と同じ論法） |

### 結果（引き受けた代償）

- **縦に長くなり、送信ボタンが画面外に出る。** 下端への固定で対処するが、**固定領域が画面を狭める**（小さい端末ほど効く）。NFR-16（詰め込まない）との緊張がここにある。
- **すべての項目が最初から見えているため、「任意なのに埋めたくなる」圧力が働く。** [ADR-006](#adr-006) が下げたかったのは、まさにこの心理的な負荷である。**「なくても送れます」と画面に書く**ことで対処するが、効くかどうかは A3（実機計測）で見る。
- 項目を足したくなったとき、**この画面はいくらでも伸ばせてしまう。** [ADR-006](#adr-006) の歯止めルール（家族の要望を根拠に必須入力を増やさない）が、画面設計の側でも守られる必要がある。

## ADR-041: 撮影を OS のカメラに委ね、アプリ内のカメラを持たない

**ステータス**：承認（2026-09-13） ／ **関連**：NFR-31・NFR-32・NFR-33・M2・C6

### 文脈

撮影の手段は2つある。**(a) `<input type="file" accept="image/*" capture="environment">` で OS の標準カメラを呼ぶ。(b) `getUserMedia` でブラウザ内にカメラ画面を自前で作る。**

(b) は撮影から送信までを1画面に留められ、連続撮影もでき、見た目も作り込める。一方で、**権限ダイアログの挙動・背面カメラの選択・向きの補正が端末ごとに異なる。**

### 決定

**OS のカメラに委ねる（(a)）。アプリ内にカメラ画面を持たない。**

- 戻ってきた画像を、端末側で長辺1600px に縮小してから送る（[08_DB設計.md](08_DB設計.md) 6-4）。

### 根拠

1. **対象端末が読めない。** NFR-33 は「施設にすでにある共用端末」を前提とし、新規導入を排している（C2）。**どの機種が来るか分からない**状況で、`getUserMedia` の挙動差を引き受けるのは、検証できない前提を1つ増やすことである。
2. **職員が既に知っている操作である。** P4 は私物スマホで Instagram を使う。**OS のカメラは、説明の要らない唯一の撮影 UI** であり、M2 の20秒を最も確実に通せる。
3. **実装量と運用対象を増やさない**（C6）。カメラ UI は、向き・露出・撮り直し・権限の拒否と、状態の多い部品である。**MVP で最初に作るものではない。**
4. 縮小だけはアプリ側で行う。これは**回線（NFR-35）と3秒（NFR-34）に直接効く**一方、端末差の影響を受けにくい処理である。**端末差が読めない部分は委ね、読める部分だけ自前で持つ**、という線引きにした。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| `getUserMedia` で自前のカメラ | 上記1・3。**連続撮影ができる利点はあるが、MVP の投稿頻度（入居者あたり週2〜3件＝M1）に連続撮影の需要がない** |
| 縮小もサーバ側で行う | 実行時間と帯域をアプリに持ち込む（[ADR-027](#adr-027) が避けたのと同じ理由）。C6 にも反する |
| 施設の共用カメラで撮り、端末から選ぶ運用を続ける | **K1 の律速そのもの**（[04_to-be.md](04_to-be.md) 3-1）。解こうとしている課題に戻ってしまう |

### 結果（引き受けた代償）

- **撮り直しの作法が OS 任せになる。** 端末によって手順が違い、施設への手順書（NFR-75）で統一して説明できない。
- **ギャラリーから既存の写真を選べてしまう端末がある。** `capture` の扱いは実装依存であり、**「その場で撮る」を技術的に強制できない。** 古い写真や、他の入居者が写った写真が選ばれる可能性が残る——**防止ではなく、操作記録（NFR-45）と管理者の事後閲覧（FR-505）で追う**。[ADR-007](#adr-007) が採ったのと同じ構えである。
- **連続撮影ができない。** 1投稿1枚（[ADR-006](#adr-006)）である限り問題にならないが、**複数枚を許す拡張をするときは、この決定が最初の制約になる。**

## ADR-042: 投稿者の選択を端末に記憶し、既定で選択済みにする

**ステータス**：**撤回**（2026-09-13、[ADR-047](#adr-047) による） ／ **関連**：FR-107・FR-302・M2・[ADR-007](#adr-007)・[ADR-018](#adr-018)・NFR-45

> **本ADRは撤回された。** 投稿者を一覧から選ぶ操作は、職員が認証主体になったこと（[ADR-047](#adr-047)）により不要になった——**投稿者はセッションから定まる。** 本ADRが解こうとしていた「職員50名の一覧から自分を探す」問題は、問題ごと消滅している。

### 文脈

[ADR-007](#adr-007) は、共用端末で職員を識別する手段として「投稿時に一覧から自分を選ぶ」を選んだ。**求められているのは認証ではなく帰属である**と整理したうえでの判断である。

画面設計に残ったのは、**その選択をいつ・どの状態で出すか**である。毎回まっさらな未選択から選ばせると、職員50名（NFR-36）の一覧から自分を探す操作が、投稿のたびに発生する。

### 決定

**直近に選ばれた職員を既定の選択状態にする。**

- 選択は**端末のブラウザストレージ**に保持し、**8時間で忘れる**（おおよそ1シフト）。
- **送信ボタンの直上に、投稿者の氏名を大きく出す**（変更は1タップ）。

### 根拠

1. **同じ職員が連続して投稿する**のが現場の実態である。シフト中に担当8〜10名（P4）の様子を出すなら、選択は最初の1回で足りる。**毎回選ばせるのは、同じ答えを繰り返し要求することである。**
2. **M2 に直接効く。** 50名の一覧から自分を探す操作は5〜10秒に相当し、60秒のうち1割を超える。
3. **8時間で忘れるのは、シフトの境界を跨がせないため。** 早番が終わった端末に、遅番の職員が最初の投稿をするとき、**前の担当者が既定で選ばれている状態が最も危ない。** 時間で切っておけば、シフトを跨いだ誤帰属はまず起きない。
4. **氏名を送信ボタンの直上に置く**ことで、押す直前に必ず目に入る。**既定値を使うことの危険は「確認されないこと」であり、位置で緩和できる。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 毎回まっさらな未選択から選ばせる | 上記1・2。**正しさは上がるが、M2 を毎回削る。** [ADR-007](#adr-007) が「職員ごとのログインは現場で回らない」とした理由と同じものが、規模を小さくしてここに現れる |
| 端末に「いまのシフト担当」を設定する画面を作る | 設定操作が1つ増え、切り替え忘れが起きたときの誤帰属は本案より大きい（8時間で自然に切れない） |
| 記憶を無期限にする | シフトを跨いだ誤帰属が常態化する。上記3 |
| 職員ごとに4桁PIN | [ADR-007](#adr-007) が「MVP では省くが、なりすましが問題化したとき最初に足す候補」として既に整理済み。**本ADRはその判断を前倒ししない** |

### 結果（引き受けた代償）

- **誤帰属が起きうる。** 同一シフト内で端末を持ち替えたとき、前の職員のまま投稿される可能性がある。**結果として、反応（FR-302）が別の職員に届く**——K3 の解消が、その1件については裏返る。
- これは [ADR-007](#adr-007) が引き受けた「同一施設内でのなりすましは技術的に防げない」と**同種の代償**であり、新たな譲歩ではない。緩和も同じく**追跡**による：投稿は端末とともに記録され（[06_リソース設計.md](06_リソース設計.md) R8）、管理者は事後に全投稿を確認できる（FR-505）。
- **8時間という値に根拠はない。** シフトの実態に合わせるべき値であり、実地検証に送る（[09_画面設計.md](09_画面設計.md) X4）。

## ADR-043: 端末のホームに施設全体の反応を出し、個人の絞り込みを二次に置く

**ステータス**：承認（2026-09-13） ／ **関連**：FR-302・FR-303・K3・M4・[ADR-021](#adr-021)・[ADR-007](#adr-007)

### 文脈

[ADR-021](#adr-021) は、職員が認証主体でないことから、**反応をプッシュせず共用端末上の一覧で受け取る**と決めた。[07_API設計.md](07_API設計.md) 4-2 は `GET /api/staff/posts?staffId=` を「FR-303 を素直に表現したもの」とし、`staffId` の指定を必須にしている。

画面に残ったのは、**端末を開いた職員が、自分の分を見るために毎回自分を選ぶのか**という点である。これは [ADR-042](#adr-042) が投稿側で解いたのと同じ摩擦が、受け取り側に現れたものである。

### 決定

**端末のホーム（SS-01）に、施設全体の新しい反応を、投稿者名つきで時刻順に出す。**

- 「自分の分だけ 見る」は**二次の導線**（SS-03）に置く。
- **件数の多い順に並べない。ランキングを作らない。**

### 根拠

1. **気づかれなければ、反応は存在しないのと同じである。** K3（反応が戻らない）を解くのは機能ではなく到達であり、[ADR-021](#adr-021) がプッシュを持たないと決めた以上、**「端末を開いた人が必ず目にする場所」が唯一の到達経路**になる。自分を選ばせる一段は、その経路に摩擦を置く。
2. **FR-302 が求めるのは「職員本人に届くこと」であって、「本人だけが見ること」ではない。** 投稿者名が併記されていれば、本人が見ても、同僚が見ても本人に届く。むしろ**同僚が「さくらさん、ありがとう来てるよ」と言える状態**のほうが、施設内では強く届く。
3. **職員間にアクセス境界は無い**（[ADR-007](#adr-007)：職員間に境界を引くことは保護すべき利益に対応していない）。**隠す理由がないものを、一段隠すために操作を要求しない。**
4. **投稿頻度が低い**（入居者あたり週2〜3件＝M1）ため、施設全体でも一覧は現実的な長さに収まる。個人で絞らないと読めないほどの量にならない。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 職員を選んでから自分の反応だけを見る | 上記1。**受け取りに毎回1操作を課す。** 投稿側で [ADR-042](#adr-042) が外した摩擦を、受け取り側で残すことになる |
| ホームに「自分宛て」の件数バッジだけ出す | 「自分」が誰かを端末が知らない（職員は認証主体でない）。[ADR-042](#adr-042) の記憶を流用すると、**シフト交代直後に他人の件数を見せることになる** |
| 反応の多い投稿を上に出す | 下記の代償（比較の芽）を最も強くする形である |

### 結果（引き受けた代償）

- **他の職員に届いた反応が、常に目に入る。** 自分にだけ来ないことが可視化され、**比較や引け目の芽になりうる。** これは P4 の「やりがい」を支えるはずの機能が、逆方向に働く経路である。
- 緩和は**並びの設計に限る**——時刻の降順のみとし、**件数で並べ替えない／集計しない／ランキングを作らない。** 「誰が多いか」を画面から読み取れない形にする。
- **ただし緩和は完全ではない。** 眺めていれば傾向は分かる。**この代償は、K3 の到達（上記1）と引き換えに引き受ける**——反応が誰にも気づかれない状態より、比較の芽があっても届くほうを採る。実運用で問題が観測されたら、**ホームを「直近24時間」に絞る**などで露出を減らす余地を残す。

## ADR-044: 表示文言の辞書を画面側に持ち、主体ごとに別の語彙を割り当てる

**ステータス**：承認（2026-09-13） ／ **関連**：[ADR-029](#adr-029)・[ADR-030](#adr-030)・NFR-13・FR-204・[07_API設計.md](07_API設計.md) W5

### 文脈

[ADR-029](#adr-029) は「API は機械可読な `code` のみ返し、日本語の表示文言を持たない」と決め、**`code` と日本語の対応表を W5 として画面設計へ送った。**

ここで問題になるのは、**同じ `code` が3種類の主体に届く**ことである。`session_expired` は家族にも管理者にも起きる。ところが NFR-13 は「家族向けの文言に技術用語・システム用語を使わない」と定める一方、管理者には**正確な語のほうが役に立つ**（P5 は業務PCで Excel を使う人物であり、「セッションの期限が切れました」で通じる）。

### 決定

**辞書を `code` → {家族向け・職員向け・管理者向け} の3列で持つ。**

- 家族向けは 2-2 の語彙規則を通した文（「久しぶりのご利用です。メールアドレスと パスワードを 入れてください」）。
- 管理者向けは正確な語（`traceId` を併記する）。
- **辞書に無い `code` は、主体ごとの共通の1文へ落とす**（家族：「うまくいきませんでした。もう一度 おためしください」）。
- **原因を利用者の言葉にしない。** 書くのは「いま何が起きたか」と「次に何をするか」の2つだけ。

### 根拠

1. **NFR-13 の対象は「家族向け」に限定されている。** 全主体に同じ文言を配ると、家族の水準に引きずられて管理者の画面から情報が落ちるか、管理者の水準に引きずられて家族の画面に「セッション」が出るかの、どちらかになる。**要件が分けている以上、辞書も分ける。**
2. **翻訳漏れが静かに起きない形にする。** 既定の落とし先を主体ごとに用意しておけば、**辞書に無い `code` が来ても、家族の画面に英語や `code` そのものが出ることはない。** [ADR-002](#adr-002) が申し送った「Cognito 由来のエラーをそのまま露出させない」も、この落とし先で最終的に塞がれる。
3. **原因を書かない**のは、[ADR-030](#adr-030) と同じ構えである。`404` は「存在しない」としか言えない（「見る権限がありません」と書けば存在を漏らす）。同様に「サーバーが混雑しています」と書いても、**家族にできることは1つも増えない。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 単一の辞書を全主体で共有する | 上記1。どちらかの主体が必ず損をする |
| API が主体を見て日本語を返す | [ADR-029](#adr-029) に正面から反する。**表示文言がサーバとクライアントに分かれて存在する状態**を作り、語彙の統制点が2つになる |
| 家族向けだけ辞書を持ち、他は `code` を出す | 職員・管理者の画面が英字の羅列になる。P5 は日本語でなければ判断も実行もできない（NFR-75 と同じ前提） |

### 結果（引き受けた代償）

- **辞書が3倍になり、`code` が増えるたびに3箇所を埋めることになる。** 埋め忘れは既定の文に落ちるため事故にはならないが、**「うまくいきませんでした」だけが出る画面が静かに増える**可能性がある。緩和として、**既定の文が使われたことを記録に残す**（どの `code` が辞書から漏れているかを後から数えられるようにする）。
- **`─` を置いた欄がある**（家族に `resident_consent_missing` は起こりえない等）。これは「起こらない」という設計上の主張であり、**もし出たらそれ自体が不具合である。** 起こらないはずの組み合わせが出たときに気づけるよう、既定の文へ落ちた記録（上記）で検出する。
- 文言の最終的な質は、**A1（70歳以上の被験者による無支援の確認）でしか判定できない。** 本ADRが決めたのは構造であって、文そのものの良し悪しではない。

## ADR-045: 取り返しのつかない操作の確認画面は、影響件数を約束しない

**ステータス**：承認（2026-09-13） ／ **関連**：[ADR-033](#adr-033)・[ADR-034](#adr-034)・[ADR-019](#adr-019)・FR-405・FR-602・INV-11・[07_API設計.md](07_API設計.md) 4-5

### 文脈

管理者には、影響の大きい操作が4つある——**同意の撤回**（その入居者の全投稿が家族から見えなくなる＝[ADR-033](#adr-033)）、**家族の失効**（FR-405）、**退居・データ保存**（紐づく家族が全員失効＝INV-11）、**退居・データ削除**（物理削除＝[ADR-019](#adr-019)）。

ところが [07_API設計.md](07_API設計.md) 4-5 は、影響件数（`affectedPosts`）を**実行の応答で返す**と決め、**プレビュー用の `GET` を持たない**とした。理由は「操作を2段階にすると、管理者が確認せずに通す経路が増える」ためである。

**つまり確認画面は、何件に影響するかを知らないまま出すことになる。**

### 決定

- **確認は独立した画面として持つ**（ダイアログで済ませない）。
- 確認画面には、**件数ではなく「起きること」を言葉で書く**（「この方の これまでの お知らせが、すべて ご家族から見えなくなります」）。
- **件数は実行後に示す**（「42件の お知らせが 見えなくなりました」）。
- **戻せない操作（退居・データ削除）だけ、入居者の氏名の入力を求める。**

### 根拠

1. **[07_API設計.md](07_API設計.md) 4-5 の判断を、画面の都合で覆さない。** プレビュー用の `GET` を足せば件数は出せるが、それは同ADRが避けた「確認せずに通す経路」を作り直すことである。**下流が上流の判断を都合で覆し始めると、判断の記録が意味を失う。**
2. **件数は、実は判断の材料として弱い。** 「42件が見えなくなる」と知っても、管理者がすることは変わらない——**撤回の申し出があったから撤回するのであって、件数で決めるのではない**（[ADR-033](#adr-033) 根拠2）。件数が効くのは*誤操作に気づく*場面だが、それは**実行後に示しても間に合う**（同意は戻せる＝[ADR-033](#adr-033)）。
3. **戻せるか戻せないかで、確認の重さを変える。** 同意の撤回と家族の失効は戻せるので、確認は1枚でよい。**退居のデータ削除だけは戻せない**ため、氏名の入力という摩擦を置く。**すべてに同じ重さの確認を置くと、どれも読まれなくなる。**
4. **ダイアログにしない**のは、[ADR-036](#adr-036) の寸法規則（当たり判定48px・詰め込まない）を小さな枠の中で守るのが難しく、かつ**「閉じる」と「実行する」が近接する形になる**ためである。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| プレビュー用の `GET` を足して件数を見せる | 上記1。[07_API設計.md](07_API設計.md) 4-5 が明示的に却下した形に戻る |
| 4つすべてに氏名の入力を求める | 上記3。急ぐ操作（端末紛失時の失効＝FR-405）に摩擦を足すのは危険ですらある |
| 確認を持たず、実行後に取り消せるようにする | 退居のデータ削除は取り消せない（[ADR-019](#adr-019)）。**取り消せない操作が1つでもある以上、確認を一律で外せない** |
| ダイアログで確認する | 上記4 |

### 結果（引き受けた代償）

- **管理者は「42件が消える」と知らずに実行する。** [ADR-033](#adr-033) は「影響件数を応答に含めるのは**確認画面に出す値として使う**ため」と書いていたが、**その使い方は成立しない**——出せるのは実行後だけである。本ADRは、同ADRのその一文を**実行後の表示として解釈し直した**ものであり、決定そのものは変えていない。
- **誤操作の発見が、実行の後になる。** 同意の撤回は戻せるが、**戻すまでの間に家族が見に来れば空の画面になる**（[ADR-033](#adr-033) が既に記録した代償）。本ADRはその窓を短くしない。
- **氏名の入力は、急いでいる管理者を苛立たせる。** 退居処理は退居手続きの混乱の中で行われる（[ADR-034](#adr-034) 根拠2）。それでも**戻せない操作に摩擦を置かない選択はしない。**

## ADR-046: 施設の業務ルールを設計の制約に固定しない（C1 の撤回）

**ステータス**：承認（2026-09-13） ／ **置換対象**：[05_要件定義.md](05_要件定義.md) C1 ／ **関連**：C2・C6・NFR-33・FR-107・[ADR-001](#adr-001)・[ADR-007](#adr-007)

### 文脈

[05_要件定義.md](05_要件定義.md) 7章は、C1 として次を制約に置いていた。

> C1　職員の私物スマートフォンでの入居者撮影は施設ルールで禁止。発信は**施設管理下の共用端末**で行う

出所は [01_ペルソナ.md](01_ペルソナ.md) P4 と [02_as-is.md](02_as-is.md) 脚注であり、**観察された事実としては正しい。** P4 の施設では実際にそう運用されている。

問題は、その事実を**全施設に効く設計の制約へ変換していた**ことである。本システムは個人開発の OSS であり（C6）、[ADR-001](#adr-001) により提供側の共有環境へ複数施設を収容する。**配布するソフトウェアの制約が、1施設の業務ルールで決まっていた。**

### 決定

1. **C1 を撤回する。** システムは、発信に使う端末が共用か私物かを**制約しない**。
2. 私物端末を禁止する施設は、これまで通り禁止できる。**禁止は施設の運用で担保するものであり、システムが強制するものではない。**
3. **[01_ペルソナ.md](01_ペルソナ.md)・[02_as-is.md](02_as-is.md) の記述は変更しない。** 観察された事実としては正しく、撤回するのは*事実を制約へ変換したこと*である。

### 根拠

1. **一般化が検証されていなかった。** C1 が記述しているのは P4 の施設の運用であって、介護施設一般の規則ではない。私物端末の業務利用を認める施設は実在する。**1施設の観察を、全施設が従う制約として固定していた。**
2. **P5 撤回と同じ構造である。** [ADR-001](#adr-001) は「施設が自らクラウドを契約したい」という未検証の想定が設計を縛っていたことを理由にモデルAを撤回した。**C1 も形は同じである**——出所が想定ではなく観察である点だけが違い、*一般化が検証されていない*点は変わらない。
3. **C1 が設計に与えていた影響が、根拠の強さに見合っていなかった。** C1 は「端末は施設の物理的管理下にある」を保証し、その保証の上に [ADR-007](#adr-007)（施設単位サインイン）・[ADR-018](#adr-018)（端末が認証主体）・[ADR-032](#adr-032)（端末90日）が積まれていた。**1つの業務ルールが、認証アーキテクチャ全体を決めていた。**

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| C1 を維持する | 私物端末を許す施設に「共用端末で使ってください」と要求することになる。**導入の入口に業務ルールの変更を置く**のは、[ADR-001](#adr-001) が退けた形と同じである |
| C1 を「推奨」に格下げする | 推奨に実体がない。システムの挙動が変わらないなら、記述を残しても読み手を惑わせるだけである |
| 私物端末を明示的に推奨する | 逆向きに業務ルールを固定することになる。**システムは端末の種類に関知しない**が正しい位置である |

### 結果（引き受けた代償）

- **[ADR-007](#adr-007)・[ADR-018](#adr-018)・[ADR-042](#adr-042) が撤回になった。** いずれも C1 の「物理的な境界」を根拠に持っていた。置換は [ADR-047](#adr-047)。
- **私物端末に入居者の写真が残りうる。** C1 が副次的に守っていた利益である。システムはこれを禁止しないため、**施設の運用判断に委ねる。** MVP では技術的な抑止（保存の禁止等）を持たない。**C1 撤回で新たに生じたリスクであり、明示しておく。**
- **C2・NFR-33 は趣旨を保ったまま緩める。** 「新規端末の導入を前提としない」は維持し、「共用端末**で**動く」を「共用端末**でも**動く」に変える。
- **FR-107（個人ログインなしで発信）が撤回になる。** 要件そのものが C1 由来だった（[ADR-047](#adr-047)）。

## ADR-047: 認証主体を職員個人にする（端末を認証主体から外す）

**ステータス**：承認（2026-09-13） ／ **置換対象**：[ADR-007](#adr-007)・[ADR-018](#adr-018)・[ADR-042](#adr-042)（すべて撤回） ／ **関連**：[ADR-046](#adr-046)・[ADR-021](#adr-021)・[ADR-032](#adr-032)・FR-107・FR-302・M2・NFR-36・NFR-45・C6

### 文脈

[ADR-007](#adr-007) は「端末は**施設の物理的な管理下**にあり、施設外に持ち出されない前提（C1）。この物理的な境界を、認証の一部として使う」として、**職員個人に認証資格情報を持たせない**と決めた。[ADR-018](#adr-018) はその粒度を端末単位に定め、[ADR-042](#adr-042) は投稿者の選択を端末に記憶する形を決めた。

**3本が共通して立っていた根拠は C1 である。[ADR-046](#adr-046) がそれを撤回した。**

### 決定

1. **職員個人を認証主体にする。** 職員はサインインし、**投稿はセッションから帰属する。**
2. **端末を認証主体から外す。** 端末リソース（`devices`）を持たない。
3. **投稿者の選択UIを持たない。** 投稿者はセッションから定まる。

### 根拠

1. **帰属が「申告」から「認証」になる。** [ADR-007](#adr-007) は「求められているのは*帰属*であり*認証*ではない」と整理したが、その整理は**認証を課せない事情**（C1・M2）に支えられていた。事情が消えたなら、**認証で帰属するほうが強い**——申告は誤りうるが、認証は誤らない。
2. **[ADR-007](#adr-007) が最も大きく引き受けた代償が解消する。** 「同一施設内でのなりすましが技術的に防げない」を、[ADR-007](#adr-007) は*防止ではなく追跡で抑える*としていた。**防止できるようになる。**
3. **管理者の運用が減る。** 端末の登録・機種変更・失効（[ADR-018](#adr-018) が「管理者の作業になる」と引き受けたもの）が丸ごと不要になる。C6 に効く。
4. **M2 は期間ではなく、セッションの延長で守る。** [ADR-007](#adr-007) が「職員ごとに ID／パスワード」を却下した理由は「共用端末で毎回のサインインは、P4 の1分の大半を食う」だった。**セッションを長く持ち、アクセスのたびに延長すれば、サインインは実質的に初回だけになる**（[ADR-032](#adr-032) 改訂）。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 端末を認証主体として残し、職員認証を追加する | 認証主体が2層になり、失効・セッション・監査がすべて2系統になる。**端末を認証する利益が、C1 撤回後は残っていない** |
| 職員ごとに4桁 PIN（[ADR-007](#adr-007) の折衷案） | 認証として弱いうえ、Cognito の標準機能から外れる。**[ADR-002](#adr-002) が避けた自前の認証ロジックを持つことになる** |
| 投稿者の選択を残し、認証と併用する | 選択と認証が食い違ったとき、どちらが正か決められない。**帰属の根拠は1つでよい** |
| 端末リソースを監査軸として残す（認証はしない） | [ADR-018](#adr-018) 根拠2「追跡できる軸は多いほうがよい」は生きているが、**私物端末を許した以上、施設が把握していない端末の記録は照合に使えない。** 必要になれば操作記録（[06_リソース設計.md](06_リソース設計.md) R12）側で扱う |

### 結果（引き受けた代償）

- **職員50名分のアカウント管理が発生する**（NFR-36）。[ADR-018](#adr-018) は「端末の登録は**施設あたり1〜数台**であり、管理の手間は小さい」としていたが、**その前提が変わった。** 介護は離職率が高く、入退職のたびに発行と失効が走る。**C6 に直接効くため、管理者の職員管理画面は手を抜けない。**
- **共用端末での切り替えコストが残る。** 私物端末なら M2 は守れるが、**共用端末を使い続ける施設では職員ごとのサインイン／サインアウトが発生し、[ADR-007](#adr-007) が却下した問題がその運用にだけ残る。** MVP では解かず、未決事項とする。
- **FR-107（個人ログインなしで発信）が撤回になる。** 要件そのものが C1 由来だった。
- **投稿の端末記録（[ADR-018](#adr-018) 根拠2）が失われる。** 追跡の軸が1つ減るが、**職員が認証されたことで、より強い軸が1つ増えている。**
- **[ADR-021](#adr-021) の根拠が変わる（決定は変えない）。** 同 ADR は「職員は認証主体ではなく、個人宛ての経路が存在しない」ことを理由に、反応の到達を共用端末上の一覧で担保した。**職員が認証主体になった今、個人宛ての経路は作れる。** それでも通知を送らない決定は**維持する**——理由が「経路が無い」から「MVP で通知を増やさない」に変わるだけである。

## ADR-048: 全主体をメールアドレスで識別する

**ステータス**：承認（2026-09-13） ／ **置換対象**：[ADR-015](#adr-015)（撤回） ／ **関連**：[ADR-002](#adr-002)・[ADR-003](#adr-003)・[ADR-012](#adr-012)・[ADR-016](#adr-016)・[ADR-031](#adr-031)・[ADR-046](#adr-046)・[ADR-047](#adr-047)・NFR-42・NFR-46

### 文脈

[ADR-015](#adr-015) は「人＝メールアドレス／端末＝ユーザー名」と決め、ユーザープールに**2種類のサインイン方法**を有効にすることを要求していた。理由は「端末にメールアドレスは存在しない」ことだった。

[ADR-047](#adr-047) で端末が認証主体から外れ、**メールアドレスを持たない主体が消えた。** 残る論点は、新たに認証主体となった職員をどう識別するかである。職員は業務用のメールアドレスを持たないことがある（P4 は業務 PC をあまり使わない）。

### 決定

**管理者・職員・家族のすべてをメールアドレスで識別する。** ユーザープールのサインイン方法は**メールアドレスのみ**とする。

### 根拠

1. **[ADR-015](#adr-015) の理由が消えた。** 識別子を主体の種類で分けていたのは、端末の存在が理由だった。理由が消えれば、分ける必要もない。
2. **家族には必ずメールアドレスがある。** 通知（[ADR-031](#adr-031)）と招待（[ADR-016](#adr-016)）が要求するためである。**持っているものとは別の識別子を覚えさせるのは、純粋な負担増**であり、[ADR-012](#adr-012) が「覚えるものを増やさない」とした趣旨に反する。P2 は CLAUDE.md が最重要制約に置く相手であり、[ADR-012](#adr-012) でパスワードを課した時点で既に一度譲歩している。**その上に積まない。**
3. **職員も私物のメールアドレスで足りる。** [ADR-046](#adr-046) が私物**端末**を許容した以上、私物の**メールアドレス**を許容しないのは一貫しない。業務用を配っている施設は業務用を使えばよい——**どちらを使うかは施設の運用判断**であり、システムは関知しない（[ADR-046](#adr-046) と同じ立場）。
4. **Cognito の標準機能が、主体によって欠けない。** 招待（[ADR-016](#adr-016)）もパスワードの再設定（NFR-46）も、メールアドレスがあれば標準フローで動く。[ADR-002](#adr-002) が Cognito を選んだ根拠3「標準機能だけで MVP の認証が成立する」が、**全主体に一様に効く。**
5. **プール設定が単純になる。** サインイン方法が1種類になり、[ADR-015](#adr-015) が「**後から変更できない項目に触れる**（サインイン方法はプール作成時に決まる）」と警告した箇所の選択が減る。

### 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| 全主体をユーザー名で識別する | 家族が自分のユーザー名を覚える必要が生じる。[ADR-015](#adr-015) が同じ理由で却下しており、**[ADR-047](#adr-047) はその理由を何も変えていない。** 上記2 |
| 職員だけユーザー名で識別する（[ADR-015](#adr-015) の構造を維持） | 主体によって識別子の種類が変わる構造が残り、プールに2種類のサインイン方法が要る。**職員が私物のメールアドレスを使えるなら、分ける利益がない** |
| ユーザー名でサインインし、家族のユーザー名にメールアドレスを入れる | サインイン方式は1本になり家族の負担も増えないが、**同じものを2つの名前で呼ぶことになる。** 識別子がメールアドレスなら、そう呼ぶほうが正直である |
| 職員に施設ドメインのメールアドレスを発行させる | 施設に新たな作業を課す。[ADR-001](#adr-001)・[ADR-046](#adr-046) が退けた「導入の入口に技術作業を置く」形と同じ |

### 結果（引き受けた代償）

- **1メールアドレス＝1主体になる。** [ADR-015](#adr-015) が家族について記録した代償（単一プール＝[ADR-003](#adr-003) でメールアドレスが全体一意）が、**職員にも及ぶ。**
  - **掛け持ち勤務の介護職員は実在し、夫婦入居より発生確率が高い。** 同じ人が2施設で働く場合、施設ごとに別のメールアドレスが必要になる。
  - これは [ADR-003](#adr-003) の代償であって本 ADR 固有の問題ではないが、**発生確率が上がったこと**を [08_DB設計.md](08_DB設計.md) U16 に追記する。U16 は「観測されたら [ADR-003](#adr-003) を見直す」と記録している。
- **メールアドレスを持たない職員は登録できない。** 施設が業務用を用意するか、本人の私物アドレスを登録してもらう必要がある。**仮パスワードを管理者が手渡す経路は MVP では作らない**——[ADR-002](#adr-002) の標準機能から外れ、[ADR-046](#adr-046) 撤回後に唯一残る自前の配布経路になるためである。
- **管理者は、重複したメールアドレスの登録を拒否される。** 「別の施設で既に使われている」ことは他施設の情報であり、**理由を明かさずに拒否するしかない**（NFR-42）。[ADR-015](#adr-015) が家族について記録していた代償が、職員にも及ぶ。
