# API設計

本書は、[06_リソース設計.md](06_リソース設計.md) が定めたリソース（R1〜R15）・不変条件（INV-1〜12）・アクセス規則を、**HTTP インターフェースの形**に落とす。step5 の2本目である。

> **本書のスコープ**
> - **含む**：URL とメソッド、リクエスト／レスポンスの形、ステータスコード、認証・認可の通し方、エラー・ページング・冪等性の規約、写真の配信、通知の送出。
> - **含まない**：テーブル・カラム・インデックス・制約の実装（→ [08_DB設計.md](08_DB設計.md)）、画面構成と文言（→ 次段）。
> - **設計判断とトレードオフは本書に書かず、[ADR.md](ADR.md) に置く。** 本書に現れる判断は [ADR-024](ADR.md#adr-024)〜[ADR-035](ADR.md#adr-035) に対応する。
>
> 要件ID（FR-／NFR-／AC-B／M／C）の出典は [05_要件定義.md](05_要件定義.md)。リソースID（R／INV／V）の出典は [06_リソース設計.md](06_リソース設計.md)。

### 0-3. 構成要素

```
[家族のブラウザ]   [職員のブラウザ]     [管理者のブラウザ]
        │                  │                   │
        │   Cookie（不透明なセッションID）        │
        ▼                  ▼                   ▼
┌────────────────────────────────────────────────────┐
│  Next.js（App Router）                              │
│   proxy.ts ─ 楽観的チェック（Cookie とパスの整合だけ） │
│   app/**/page.tsx ─ 初期表示は DAL を直接呼ぶ          │
│   app/api/**/route.ts ─ HTTP API（本書の対象）         │
│   lib/dal ─ 認可とテナント条件の唯一の通り道           │
│   定期実行 ─ 掃除・期限切れ・生成・再送（ADR-035）      │
└──────┬───────────────┬────────────────┬────────────┘
       ▼               ▼                ▼
  PostgreSQL      オブジェクト      Cognito User Pool
   （08で設計）      ストレージ        （ADR-002/003）
```

**認可の判断は `lib/dal` に一点集約する。** `proxy.ts` は Cookie の有無とパスの名前空間が食い違うときにリダイレクトするだけで、**DB を見ないし、認可の根拠にもしない**（Next.js の指針どおり、Proxy は楽観的チェックに留める）。Route Handler も Server Component も、データに触れるときは必ず DAL を経由する。[ADR-003](ADR.md#adr-003) の「担保箇所を一系統に寄せる」と、[06](06_リソース設計.md) 7章の INV-4・INV-7 の実装上の置き場所がここである。

### 0-4. HTTP に出すもの／出さないもの

読み取りのうち**画面の初期表示に必要なものは、Server Component が DAL を直接呼ぶ**。HTTP エンドポイントは次の3つに限る（[ADR-024](ADR.md#adr-024)）。

1. **状態を変える操作**
2. **初期表示のあとにクライアントが追加で取りに行く読み取り**（さかのぼり読み込みなど）
3. **リダイレクト・ファイルの受け渡しなど、HTTP の振る舞いそのものが必要なもの**

4章の一覧の **RSC** 印は、同じ DAL 関数を Server Component の初期表示からも呼ぶことを示す。

## 1. 名前空間

```
/api/auth/*     認証・セッション（全主体共通の入口）
/api/staff/*    職員セッション（発信）
/api/family/*   家族セッション
/api/admin/*    管理者セッション
```

**名前空間を主体で分ける**（[ADR-026](ADR.md#adr-026)）。同じ投稿（R8）を扱っても、家族向けと職員向けは**別のパス・別の表現・別の認可**である。

**URL にバージョンを置かない。** クライアントとサーバが同一デプロイであり（ブラウザのみ＝NFR-32）、古いクライアントが残留しない。残留が起きる事情（ネイティブアプリ等）が生じたときに `/api/v2/*` を足す余地は残す——使われない分岐を初版に持ち込まない。

## 2. 共通の表現

### 2-1. リソースと URL の対応

| リソース | 主な URL |
|---|---|
| R1 施設 | `/api/admin/tenant`・`/api/staff/tenant` |
| R2 管理者 | `/api/admin/administrators` |
| ~~R3 端末~~ | **欠番** — [ADR-047](ADR.md#adr-047) により端末はリソースでなくなった |
| R4 職員 | `/api/admin/staff`・`/api/staff/members` |
| R5 入居者 | `/api/admin/residents`・`/api/staff/residents` |
| R6 家族 | `/api/admin/residents/{id}/family`・`/api/admin/family/{id}`・`/api/family/relatives` |
| R7 招待 | `/api/admin/family/{id}/invitations` |
| R8 投稿 | `/api/staff/posts`・`/api/family/posts`・`/api/admin/posts` |
| R9 写真 | `/api/staff/photos`・`/api/{role}/photos/{id}` |
| R10 反応 | `/api/family/posts/{id}/reaction`（`/api/staff/posts` に集計で同梱） |
| R11 通知先 | **専用のURLを持たない**（6-3） |
| R12 操作記録 | `/api/admin/audit-logs` |
| R13 文例 | `/api/staff/phrases` |

| R15 エクスポート | `/api/admin/exports` |

### 2-2. 形式

| 項目 | 決定 |
|---|---|
| Content-Type | `application/json`（写真のバイト列は API を通らない＝[ADR-027](ADR.md#adr-027)） |
| 日時 | RFC 3339・UTC・秒精度（`2026-09-12T04:31:00Z`）。表示時刻への変換はクライアント |
| 識別子 | UUIDv7 の文字列表現（[ADR-014](ADR.md#adr-014)） |
| 一覧 | `{ "items": [...], "nextCursor": "…" \| null }` |
| 未知のフィールド | リクエストでは**拒否する**（`400`）。誤ったフィールド名を黙って無視しない |
| 表示文言 | **返さない**（[ADR-029](ADR.md#adr-029)） |

### 2-3. 投稿の表現

**家族向け**

```json
{
  "id": "0192f7a1-3c4e-7b2d-9f10-8a5c6e2b4d31",
  "postedAt": "2026-09-12T04:31:00Z",
  "text": "お昼にお庭を散歩しました",
  "photo": {
    "url": "/api/family/photos/0192f7a1-3c4e-7b2d-9f10-8a5c6e2b4d31",
    "width": 1600,
    "height": 1200
  },
  "author": { "name": "佐藤 さくら" },
  "myReaction": { "reactedAt": "2026-09-12T05:02:11Z" }
}
```

- `author` は**氏名のみ**（[06](06_リソース設計.md) R4：家族が「誰が書いたか」を見る）。職員の識別子は家族に出さない——家族から職員を名指しできる経路を作らないため（[ADR-011](ADR.md#adr-011) と同じ趣旨）。
- `residentId` を含めない。家族は1人の入居者にしか紐づかないため（[06](06_リソース設計.md) 4章）、表現に出す意味がない。
- `myReaction` は `null` 可。**他の家族の反応は返さない**（誰が反応したかを家族間で見せない。[06](06_リソース設計.md) 6-2 注2 が家族に開くのは氏名と続柄までである）。
- `photo.width` / `height` を返すのは、**読み込み中のレイアウトのずれを防ぐ**ため。写真が画面最大の要素である以上（NFR-16）、がたつきが最も目立つ。
- **状態を返さない。** 家族が受け取る一覧には公開中の投稿しか含まれない（INV-4）ので、`status` という概念を家族向けの表現に持ち込まない。

**職員・管理者向け**

```json
{
  "id": "0192f7a1-…",
  "postedAt": "2026-09-12T04:31:00Z",
  "text": "お昼にお庭を散歩しました",
  "photo": { "url": "/api/staff/photos/0192f7a1-…", "width": 1600, "height": 1200 },
  "resident": { "id": "0192f7b2-…", "name": "山田 太郎" },
  "author": { "id": "0192f7c3-…", "name": "佐藤 さくら" },
  "reactions": { "count": 3, "latestAt": "2026-09-12T07:45:00Z" },
  "status": "published",
  "deletedAt": null
}
```

- 反応は**件数と最新時刻**のみ。誰が反応したかを職員に見せることは FR-302／FR-303 が要求していない。
- `status` は `published` / `deleted`。削除済みが含まれるのは管理者向けの一覧だけ（FR-505）。

## 3. 共通規約

### 3-1. 認証

| 項目 | 決定 |
|---|---|
| 資格情報の検証 | Amazon Cognito User Pools（[ADR-002](ADR.md#adr-002)） |
| クライアントが持つもの | Cookie `__Host-session`（**不透明なセッションID**のみ）。`HttpOnly` / `Secure` / `SameSite=Lax` / `Path=/` |
| Cognito のトークン | **ブラウザに渡さない。サーバ側に保持する**（[ADR-025](ADR.md#adr-025)） |
| 有効期間 | 主体ごと（3-3） |
| 失効 | DAL が**毎リクエストで主体の有効状態を確認**する。管理者の失効操作（FR-405）は次のリクエストから効く＝**即時**（INV-7） |

### 3-2. テナントと主体

- **施設の識別子は URL にもリクエストボディにも現れない**（[ADR-013](ADR.md#adr-013)・[06](06_リソース設計.md) 2-1）。セッションから解決する。
- 同様に、家族の識別子・**職員の識別子**もクライアントから受け取らない。投稿の投稿者（[06](06_リソース設計.md) R8）は**セッションから埋める**（[ADR-047](ADR.md#adr-047)）。
- クライアントが送ってよい識別子は、**同一施設内で自由に選べるもの**（`residentId`・`postId`・`photoId`）に限る。**`staffId` は旧版では職員の申告値だったが、[ADR-047](ADR.md#adr-047) により認証主体から導出される。**DAL がテナント条件つきで存在を確認する。
- **唯一の例外は文例（R13）**。施設に属さない読み取り専用のリソースであり（[06](06_リソース設計.md) 0-1）、テナント条件を持たない。**DAL の中で「テナント条件を持たない」ことを明示的に宣言する経路を1つだけ用意し、そこを通す**——例外を暗黙に許すと、他のリソースでも条件の欠落が見過ごされるため。

### 3-3. セッションの有効期間（V4 の決着）

[ADR-032](ADR.md#adr-032)。

| 主体 | 有効期間 | 根拠 |
|---|---|---|
| 職員 | **30日**（アクセスのたびに延長する） | C1 撤回（[ADR-046](ADR.md#adr-046)）により端末の物理境界を寿命の根拠にできなくなった。家族より長くする根拠が無い。**毎日使う職員は延長で実質切れない**ため M2 は損なわれない（[ADR-032](ADR.md#adr-032) 改訂） |
| 家族 | **30日**（アクセスのたびに延長する） | AC-B3「初回以降、同一端末では再入力なしに利用できる」。想定投稿頻度（週2〜3件＝M1）なら、見ている限り期限切れに達しない |
| 管理者 | **12時間**（延長しない） | 権限が最も重い。初期設定（NFR-74：4時間以内）を1セッションで通せる長さは確保する |

この表の有効期間は **AC-B4 ①「一定期間の経過」の実体**である。AC-B4 は再認証の契機を3つに限定しており、API 上ではそれぞれ次に対応する。**この3つ以外の理由でセッションを切らない**——たとえば IP やユーザーエージェントの変化を理由にした再認証は行わない（家族は移動中に閲覧する＝P1）。

| AC-B4 の契機 | API 上の実体 |
|---|---|
| ① 一定期間の経過 | 上表の有効期間。超過したセッションは `401` |
| ② 明示的なログアウト | `DELETE /api/auth/session`（FR-406） |
| ③ 認証情報の失効 | `DELETE /api/admin/family/{id}/access`（FR-405）／パスワードの変更・再設定（`PUT /api/auth/password`）。いずれも当該主体の既存セッションを破棄する |

### 3-4. CSRF

`SameSite=Lax` により、他サイトからの `POST`/`PUT`/`PATCH`/`DELETE` に Cookie は付かない。加えて、**状態を変えるメソッドでは `Origin` ヘッダを検証する**（自サイト以外・欠落は `403`）。トークンを画面に埋め込む方式は採らない——Cookie が JS から読めない構成（[ADR-025](ADR.md#adr-025)）と噛み合わず、配る仕掛けを増やすだけになる。

### 3-5. ステータスコード

| コード | 用途 |
|---|---|
| `200` / `201` / `202` / `204` | 成功 |
| `400` | 形式が不正（必須欠落・未知のフィールド・型違い） |
| `401` | セッションが無い／期限切れ |
| `403` | 主体の種類が名前空間と合わない／`Origin` 不正 |
| `404` | **存在しない、または自分の到達範囲の外**（3-7） |
| `409` | 状態の衝突（同意なし、退居済み、失効済み、写真が未アップロード、`Idempotency-Key` の競合） |
| `413` | 写真が上限超過 |
| `422` | 形式は正しいが値が受け付けられない（文字数超過など） |
| `429` | レート制限 |
| `500` | サーバ内部 |

### 3-6. ページング

```
GET /api/family/posts?limit=20&cursor=eyJ0IjoiMjAyNi0wOS0xMlQwNDozMTowMFoiLCJpIjoiMDE5…
```

- カーソル方式。`limit` 既定20・最大50。
- **カーソルは `(投稿日時, 識別子)` を符号化した不透明な文字列**。UUIDv7 は時刻順に並ぶが、**その性質にカーソルの正しさを依存させない**（識別子の方式を将来変えたときにページングが静かに壊れるため）。
- 並び順は投稿日時の降順のみ。**クライアントが並び順を指定できない**（FR-201 は「新しい順」しか要求していない）。
- 件数の総数を返さない。総量は施設の規模を推測させる情報であり、画面にも要らない（NFR-16）。

オフセット方式を採らないのは、さかのぼり読み込み（FR-201）の最中に新しい投稿が入ると、既読の投稿が二重に現れるため。代償として任意のページへ跳べないが、家族にも職員にもその操作は無い。

### 3-7. 「無い」と「見えない」を区別しない

**到達範囲の外にあるリソースには一律 `404` を返す**（[ADR-030](ADR.md#adr-030)）。`403` は「存在はする」という情報を漏らす。NFR-41 の「他の入居者の情報に到達する経路が存在しないこと」は、**存在の有無すら伝えない**ところまで含むと解釈する。

ただし**主体の種類と名前空間の不一致は `403`**（家族セッションで `/api/admin/*` を叩いた等）。これはリソースの存在ではなく経路の誤りを伝えているだけなので、漏洩にならない。

### 3-8. 削除

**`DELETE` は論理削除**（[ADR-019](ADR.md#adr-019)）。`204` を返し、リソースは状態が変わるだけで消えない。物理削除が起きるのは、退居時の削除操作（FR-602）と、仮のまま期限を過ぎた写真の掃除（INV-8）だけである。

### 3-9. 冪等性

| 操作 | 方式 |
|---|---|
| 投稿の作成 | `POST` ＋ **`Idempotency-Key` ヘッダ必須**（[ADR-028](ADR.md#adr-028)） |
| 写真の枠の確保 | `POST` ＋ `Idempotency-Key` 任意 |
| 反応 | **`PUT` / `DELETE`**。1家族×1投稿＝1件（[ADR-020](ADR.md#adr-020)）なので、再送が同じ状態に収束する |
| その他の更新 | `PATCH` / `PUT` |

`Idempotency-Key` はクライアント生成の UUIDv7。保持期間は**24時間**とし、それを過ぎたキーの再利用は新規作成として扱う。

### 3-10. エラー

RFC 9457（`application/problem+json`）。**日本語の表示文言を返さない**（[ADR-029](ADR.md#adr-029)）。

```json
{
  "type": "https://example.invalid/probs/resident-consent-missing",
  "title": "Resident has no photo consent on record",
  "status": 409,
  "code": "resident_consent_missing",
  "instance": "/api/staff/posts",
  "traceId": "0192f7a1-3c4e-7b2d-9f10-8a5c6e2b4d31"
}
```

- **`code` が唯一の機械可読な契約。** クライアントが自前の辞書で日本語文言を引く。`title` は英語（開発者・ログ向け）。
- **Cognito 由来のメッセージをそのまま載せない**（[ADR-002](ADR.md#adr-002) の申し送り）。`code` に写像してから返す。
- `traceId` は操作記録（R12）と突き合わせるための識別子。

主なコード：`session_required` / `session_expired` / `credentials_invalid` / `rate_limited` / `resident_consent_missing` / `resident_discharged` / `photo_not_uploaded` / `photo_already_used` / `post_deleted` / `family_revoked` / `invitation_expired` / `idempotency_key_conflict`。

### 3-11. 操作記録

**状態を変えるすべての操作と、拒否したすべてのアクセスを R12 に記録する**（NFR-45・INV-9）。DAL の経路に組み込み、個々のハンドラに任せない。

記録する項目は [06](06_リソース設計.md) R12 のとおりで、API 側から加えるのは `traceId` である。**行為者はセッションから定まる**（[ADR-047](ADR.md#adr-047)）——旧版は投稿時に選ばれた職員を*申告値*として記録していたが、認証で定まるようになった。

**到達範囲の外を参照して `404` になったアクセスも記録する。** [ADR-003](ADR.md#adr-003) が「防止だけに賭けない。越境を検出できるようにする」と決めているため、`404` を返して終わりにしない。

### 3-12. レート制限

| 対象 | 制限 | 根拠 |
|---|---|---|
| `POST /api/auth/session` | 識別子ごと・IPごとに試行回数を制限（Cognito 側に加えてアプリ側でも） | NFR-46 |
| `POST /api/auth/password-reset` | 同一識別子へ 5回/時 | 総当たりとメール爆撃の防止 |
| `POST /api/staff/photos` | 職員あたり 60回/時 | ストレージへの書き込み口の乱用防止 |
| `POST /api/admin/exports` | 施設あたり 3回/日 | 施設の全データが出る操作（[06](06_リソース設計.md) R15） |

超過時は `429` と `Retry-After`。

### 4-1. 認証・セッション `/api/auth`

| メソッド | パス | 内容 | 要件 |
|---|---|---|---|
| `POST` | `/api/auth/session` | サインイン。Cookie 発行 | FR-401・[ADR-012](ADR.md#adr-012) |
| `DELETE` | `/api/auth/session` | サインアウト | **FR-406**・AC-B4 ② |
| `POST` | `/api/auth/initial-password` | 招待直後のパスワード設定 | FR-401・AC-B1・AC-B2 |
| `POST` | `/api/auth/password-reset` | 再設定の開始（コード送付） | NFR-46 |
| `PUT` | `/api/auth/password` | 再設定の完了 | NFR-46 |
| `GET` | `/api/auth/me` | 現在の主体 | ― |

**`POST /api/auth/session`**

```
POST /api/auth/session
{ "identifier": "hanako@example.com", "password": "…" }

200 OK   Set-Cookie: __Host-session=…
{ "subject": "family" }
```

- **3種の主体で入口を1つにする。** 識別子は全主体がメールアドレスである（[ADR-048](ADR.md#adr-048)）。フィールド名は `identifier` のままとし、**利用者に「自分はどの種類か」を選ばせない**（NFR-11）。主体の種別はサーバが解決する。
- 応答の `subject` は `admin` / `staff` / `family`。クライアントはこれで遷移先を決める。
- 招待直後の家族には、Cognito が `NEW_PASSWORD_REQUIRED` を返す。このとき `200` で次を返す。

```json
{ "subject": "family", "next": "initial_password", "challengeToken": "…" }
```

`challengeToken` は**サーバ側のチャレンジ状態に紐づく短命（10分）の不透明な値**であり、Cognito のセッション文字列そのものではない（[ADR-025](ADR.md#adr-025)）。

**`POST /api/auth/initial-password`**

```
POST /api/auth/initial-password
{ "challengeToken": "…", "newPassword": "…" }

200 OK   Set-Cookie: __Host-session=…
```

**引換のロジックをアプリが持たない**（[ADR-016](ADR.md#adr-016)）。このエンドポイントは Cognito のチャレンジ応答を中継するだけで、仮パスワードの検証も、有効期限の判定も Cognito 側で行われる。**アプリがするのは、成功したという結果を招待（R7）に記録すること**だけである。求める入力は新しいパスワードのみ（AC-B2：付随する入力を求めない）。

**`DELETE /api/auth/session`**

```
DELETE /api/auth/session

204 No Content   Set-Cookie: __Host-session=; Max-Age=0
```

- **サーバ側のセッション実体を削除する**（[ADR-025](ADR.md#adr-025)）。Cookie を消すだけにしない——消し損ねた Cookie が再送されても、実体が無ければ `401` になる。
- 保持していた Cognito のリフレッシュトークンも同時に破棄する。
- **家族向け画面にも置く**（FR-406）。AC-B4 が再認証の契機を3つに限定しており、②の明示的ログアウトは**家族自身が引ける唯一の契機**であるため、UI が無ければ要件を満たせない。NFR-13 の語彙例外の持ち出し先はここだけであり、常時表示せず設定相当の場所に置く。
- **職員が退職するときの手順**は、**ログアウト（本人）と管理者による失効（FR-405）の二本立て**とし、導入手順書（NFR-75）に置く。本人が操作するとは限らないため、施設側の失効を一次手段とする位置づけは変えない（[ADR-047](ADR.md#adr-047) の代償：入退職は端末の入れ替えよりはるかに頻繁である）。

| `POST` | `/api/staff/photos` | 写真の枠を確保し、送信先を得る | [ADR-017](ADR.md#adr-017)・NFR-35 | |
| `POST` | `/api/staff/posts` | 投稿の作成 | FR-101・FR-104 | |

**`GET /api/staff/residents`**

INV-3 により、**同意が「無」の入居者と退居した入居者は返さない**。一覧に出してから投稿時に断るのではなく、**選べない状態にする**——選べたものが後で拒否される体験は、60秒（M2）の中で最も損な形である。

**`POST /api/staff/photos`（V10 に関わる）**

```
POST /api/staff/photos
{ "contentType": "image/jpeg", "byteSize": 812345, "width": 1600, "height": 1200 }

201 Created
{
  "photoId": "0192f7d4-…",
  "upload": {
    "method": "PUT",
    "url": "https://<storage>/…?X-Amz-Signature=…",
    "headers": { "Content-Type": "image/jpeg" },
    "expiresAt": "2026-09-12T04:36:00Z"
  }
}
```

- 写真リソース（R9）を**「仮」の状態で作る**。`photoId` は投稿の作成時に使う。
- `contentType` は `image/jpeg` / `image/png` / `image/webp` のみ。`byteSize` の上限は **10MB**（超過は `413`）。
- **端末側で長辺 1600px 程度に縮小してから送る。** 回線品質が低い施設（NFR-35）と、撮影から送信まで60秒（M2）の両方に効く。縮小はクライアントの責務とし、サーバ側での再エンコードを MVP では持たない（C6：運用対象を増やさない）。
- 送信先の URL は**5分**で失効する。失敗したら `POST` からやり直す（仮の写真は INV-8 で掃除される）。

> **FR-105（中断されても入力内容が失われない）は、この2段階がそのまま満たす。** 写真は先にサーバへ渡っており、端末に残るのは「どの入居者を選んだか」「本文」という小さな値だけである。これを端末のブラウザストレージに1件だけ保持する（**V10 の決着**）。サーバ側に下書きリソースを作らない（[06](06_リソース設計.md) R8）。

**`POST /api/staff/posts`**

```
POST /api/staff/posts
Idempotency-Key: 0192f7e5-…
{
  "residentId": "0192f7b2-…",
  "photoId": "0192f7d4-…",
  "text": "お昼にお庭を散歩しました"
}

201 Created  → 投稿（職員向け表現）
```

- **宛先を受け取らない**（[ADR-008](ADR.md#adr-008)／FR-104）。届く先は入居者 → 家族の関連から導出される（[06](06_リソース設計.md) 4章）。
- **投稿者を受け取らない。** 投稿は**セッションの職員に帰属する**（[ADR-047](ADR.md#adr-047)）。旧版は `staffId` を*この API で唯一の申告値*として受け取っており、[ADR-007](ADR.md#adr-007) の代償としてなりすましを技術的に防げなかった。**その代償は解消した。**
- `photoId` は「仮」の写真で、かつ実体がアップロード済みであることを確認する。未完了なら `409 photo_not_uploaded`、既に他の投稿に使われていれば `409 photo_already_used`（INV-8）。
- `text` は任意・**200文字まで**（超過は `422`）。文例（R13）を挿入した結果もここに入る——**文例の識別子を送らない**。職員が編集した後の本文が唯一の事実であり、どの文例から始めたかは投稿の属性ではない。
- INV-3 に反する入居者は `409 resident_consent_missing` / `409 resident_discharged`。
- 成功後、通知を**トランザクションの外で**送る（[ADR-031](ADR.md#adr-031)）。通知の成否はこの応答に影響しない。

**`GET /api/staff/posts`**

```
GET /api/staff/posts?scope=mine&limit=20&cursor=…
```

**既定は `scope=mine`**（セッションの職員自身の投稿）。FR-303「自分の投稿に届いた反応」がこれで満たされる。`scope=facility` で施設全体の投稿も読める（[06](06_リソース設計.md) 6-2：職員は自施設の投稿を読める）。**旧版は `staffId` の指定を必須としており、値を変えれば他人の分も見えた**——[ADR-047](ADR.md#adr-047) により、自分の分は**認証から定まる**。

**これが職員への反応の到達経路である**（[ADR-021](ADR.md#adr-021)）。職員個人へのプッシュ通知は持たない（[ADR-021](ADR.md#adr-021) の決定は維持。根拠の変化は [ADR-047](ADR.md#adr-047) 結果）。

**`DELETE /api/staff/posts/{postId}`**

論理削除（3-8）。**自分の投稿だけを削除できる**——他の職員の投稿は `404`（[ADR-030](ADR.md#adr-030)）。FR-106 の「職員は自分の投稿を削除できる」が、**API の境界としてそのまま実現される**（[ADR-047](ADR.md#adr-047)）。旧版は職員を認証していなかったため境界を施設単位とし、画面の既定で絞って代替していた（[06](06_リソース設計.md) 6-2 が要件との差分として記録していたもの。**差分は解消した**）。削除は操作記録に残る。

**`GET`/`PUT /api/family/notification`**

### 4-4. 写真の配信（全主体共通）

```
GET /api/{role}/photos/{photoId}

302 Found
Location: https://<storage>/…?X-Amz-Signature=…     ← 5分で失効
Cache-Control: private, no-store
```

**V2 の決着**（[ADR-027](ADR.md#adr-027)）。

- **`<img src>` に置くのは、この安定した API の URL。** 時限付きURLを表現に直接埋めない——埋めると、画面を開いたまま放置した家族の写真が静かに表示されなくなる。
- ハンドラは DAL を通して**その主体がその写真に到達してよいか**を判定してからリダイレクトする（家族なら INV-4）。判定に失敗したら `404`（3-7）。
- リダイレクト自体をキャッシュさせない（`no-store`）。リダイレクト先はブラウザのキャッシュに乗るが、5分で失効する。
- **写真のバイト列がアプリケーションサーバを通らない。** 帯域と実行時間をアプリに持ち込まないことが、NFR-34（3秒以内）とコスト（NFR-76）の両方に効く。

```
POST /api/admin/residents/{id}/family
{ "name": "山田 太郎", "relationship": "長男", "email": "taro@example.com" }
→ 201 Created  （状態は「招待前」）

POST /api/admin/family/{familyId}/invitations
→ 201 Created  { "id": "…", "sentTo": "taro@example.com", "expiresAt": "…", "kind": "initial" }
```

登録と送付を分けるのは、名簿の一括登録（C5：Excel からの移行）と家族への送付のタイミングが一致しないため（[06](06_リソース設計.md) 5-1）。再送は同じ `POST` で、**前の招待は失効する**（INV-6）。

> `email` は MVP で必須である。**名簿に載っても到達しない家族が存在しうる**（P2。[ADR-012](ADR.md#adr-012)）。API は到達性を保証しない——保証できないことを、施設への説明（NFR-75）でカバーする。

**`PUT /api/admin/residents/{id}/photo-consent`（V5 の決着）**

```
PUT /api/admin/residents/{id}/photo-consent
{ "granted": false }

200 OK
{ "granted": false, "recordedAt": "…", "recordedBy": "…", "affectedPosts": 42 }
```

同意を「無」に変更すると、**その入居者の既存の投稿はすべて家族から見えなくなる**（[ADR-033](ADR.md#adr-033)）。`affectedPosts` は影響を受ける件数で、**変更前に確認画面へ出すための値**である（同じ値を返す `GET` のプレビューは持たず、実行結果として返す——操作を2段階にすると、管理者が確認せずに通す経路が増えるため）。

**`POST /api/admin/residents/{id}/discharge`（V6 の決着）**

```
POST /api/admin/residents/{id}/discharge
{ "dischargedOn": "2026-09-30", "dataAction": "retain" }   // "retain" | "delete"
```

[06](06_リソース設計.md) 5-3 が「3つが1つの操作として実行されること」を要求した複合操作。**入居者を退居にする／紐づく家族をすべて失効にする（INV-11）／データの扱いを決める**を1つのリクエストで行う。

`retain` を選んだ場合、**退居日から1年で自動削除する**（[ADR-034](ADR.md#adr-034)）。応答に `dataDeletionScheduledOn` を含め、いつ消えるかを管理者に明示する。

**`POST /api/admin/exports`（V3 の決着）**

```
POST /api/admin/exports
{ "scope": "tenant" }                              // または { "scope": "resident", "residentId": "…" }
→ 202 Accepted  { "id": "…", "status": "accepted" }

GET /api/admin/exports/{id}
→ { "id": "…", "status": "ready",
    "url": "/api/admin/exports/{id}/download", "expiresAt": "2026-09-13T00:00:00Z" }
```

受付だけを同期で行い、**生成は定期実行に任せる**（[ADR-035](ADR.md#adr-035)）。中身は投稿・写真・名簿の機械可読な形式（ZIP 内の JSON と画像ファイル）とし、特定の提供者への固定化を作らない（FR-601）。`/download` は写真と同じく `302` で時限付きの経路へ渡す（4-4）。

エクスポートの依頼と取得は、それ自体が操作記録に残る（[06](06_リソース設計.md) R15）。

## 5. 認可の通し方

### 5-1. 3つの層

| 層 | 何をするか | 何をしないか |
|---|---|---|
| `proxy.ts` | Cookie の有無と、パスの名前空間（`/staff` `/family` `/admin`）の整合だけを見て、不一致ならリダイレクト | **DB を見ない。認可の根拠にしない** |
| `lib/dal` | **本番の認可**。セッションの検証、主体の有効状態の確認（INV-7）、テナント条件の付与、家族の入居者条件の付与（INV-4） | ― |
| DB | 行レベルのアクセス制御（**採否は [08_DB設計.md](08_DB設計.md)**） | ― |

`proxy.ts` を認可の根拠にしないのは、Next.js の指針（Proxy はプリフェッチを含む全ルートで走るため楽観的チェックに留めるべき）に加えて、[ADR-003](ADR.md#adr-003) の「分離の担保箇所を一系統に寄せる」に従うため。担保は DAL にあり、`proxy.ts` はログイン画面へ早く戻すためだけに存在する。

### 5-2. DAL の規約

- データに触れる関数は**必ずセッションの検証を最初に通す**。
- クエリを組み立てる関数は**セッションを引数に取る**。テナント識別子を単独の引数として受け取る関数を作らない（呼び出し側が任意の値を渡せる形にしない）。
- 家族向けの読み取りは、**セッションから導出した入居者を必ず条件に含む**（INV-4）。
- テナント条件を持たない経路は**文例（R13）ただ1つ**とし、明示的に宣言する（3-2）。
- この規約は**レビューで守るのではなく型で守る**（テナント条件の付いていないクエリを作れなくする）。実装方式は [08_DB設計.md](08_DB設計.md) の V7 と合わせて決める。

### 5-3. 主体 × 名前空間

[06](06_リソース設計.md) 6-2 の表を、経路の言葉に置き換えたもの。

| 経路 | admin | staff | family |
|---|:---:|:---:|:---:|
| `/api/auth/*` | ○ | ○ | ○ |
| `/api/staff/*` | ✕ `403` | ○ | ✕ `403` |
| `/api/family/*` | ✕ `403` | ✕ `403` | ○ |
| `/api/admin/*` | ○ | ✕ `403` | ✕ `403` |

**管理者が `/api/staff/*` に入れない**ことで、「管理者は投稿を作成できない」（[05](05_要件定義.md) 3-2・[06](06_リソース設計.md) 6-2 注4）が経路の構造として成立する。画面に出さないだけでは要件を固定したことにならない。管理者が発信するには**職員としてサインインする**必要がある。

## 6. 通知

### 6-1. 経路（V1 の決着）

**MVP の通知はメールで送る**（[ADR-031](ADR.md#adr-031)）。通知先（R11）の方式は `email`、宛先は家族のメールアドレスである。

### 6-2. 送出

| 項目 | 決定 |
|---|---|
| 起点 | 投稿が「公開中」になった**あと**、トランザクションの外で（[06](06_リソース設計.md) 5-2） |
| 宛先 | その入居者に紐づく、**利用中**かつ**通知が有効**な家族全員（FR-202：一人ひとりへ直接） |
| 本文 | **投稿の内容を含めない。** 「新しいお知らせがあります」と、投稿1件への直接リンクのみ |
| リンク先 | `/posts/{postId}`。未サインインならサインインへ誘導し、**完了後に元のリンク先へ戻す** |
| 失敗 | 再試行する（[ADR-035](ADR.md#adr-035)）。**投稿の作成は取り消さない**。失敗は操作記録に残す |
| 停止 | `PUT /api/family/notification`（FR-203） |

**本文に内容を含めない**のは、メールが転送・共有の経路になることを避けるため（NFR-55）。写真をメールに載せると本システムの外に個人情報の複製が残り、失効（FR-405・INV-7）が効かなくなる。

### 6-3. 通知先にエンドポイントを置かない

[06](06_リソース設計.md) 6-2 は家族が通知先を作成・削除できるとしていたが、**MVP では通知先の方式が `email` ただ1つで、宛先は家族のメールアドレスと常に一致する**。家族が別の宛先を足す意味がないため、**通知先の URL を作らず、招待の送付時に自動で1件作る**。家族に開くのは可否の1ビットだけである（4-3）。

方式が増えたとき（[ADR-004](ADR.md#adr-004) の再開や SMS の追加）に `/api/family/notification-targets` を足す余地は残す。**リソースを分けておいた [06](06_リソース設計.md) R11 の判断は、この拡張のために効いている**——今その URL を作らないだけである。

### 6-4. 職員への反応

**通知を送らない**（[ADR-021](ADR.md#adr-021)）。職員は認証主体ではなく、個人宛ての経路が存在しない。反応は `GET /api/staff/posts` で受け取る（4-2）。
