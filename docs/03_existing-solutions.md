# 既存の手段でできること・できないこと（既存アプリ比較）

本書は、[02_as-is.md](02_as-is.md) で整理した課題（K1〜K5）に対して、**すでに存在する手段・サービスで解けるところと解けないところ**を突き合わせる。
目的は「本システムの存在理由」を、思い込みでなく比較で示すこと。

> 本書のスコープは「既存手段の**できる／できない**の評価」までとする。
> **本システムで何をどう作るか（解決方針・機能・画面・技術）は書かない**（それは次の `04_to-be.md` 以降で決める）。
> 登場人物・課題は [01_personas.md](01_personas.md) / [02_as-is.md](02_as-is.md) を参照。

## 1. 比較の軸

as-is の課題（K1〜K5）とペルソナ制約から、「解決に不可欠な条件」を7軸に落とす。各軸の右列は、その軸が満たされないと誰の・どの課題が残るかを示す。

| 軸 | 内容 | 満たされないと残る課題 |
|---|---|---|
| **A. 直接到達** | 施設 → 家族一人ひとりへ、**太郎を介さず**届くか | K2（太郎ボトルネック） |
| **B. 個別配信** | 「その入居者の様子」を**個人単位**で出せるか（一斉配信でない） | K4 |
| **C. P2が使える** | 記憶・入力を求めない認証と、迷わない操作か | 論点2・P2（最重要制約） |
| **D. 現場で完結** | 職員が**施設管理下の共用スマホ／タブレット**で「撮る→短く書く→個別に届く」を数十秒で | K1・P4 |
| **E. 反応が返る** | 家族の感謝・反応が**職員本人に戻る**経路があるか | K3 |
| **F. 施設で管理** | データを**施設側で保持**できるか（セルフホスト可） | P5 |
| **G. 見合うコスト** | 80名規模の施設が**継続できる**費用・運用負荷か | P5 |

## 2. 比較対象

現状使われている、または代替になりうる手段を5つ取り上げる。

| 手段 | 位置づけ |
|---|---|
| **LINE公式アカウント** | 現状、施設が家族向けに一斉配信で使用中 |
| **ほのぼのNEXT（家族連絡オプション）** | 介護記録ソフトに付属する家族向け連絡機能 |
| **市販の家族連絡アプリ** | きずなネット等、施設向けに提供される汎用の連絡・写真共有サービス |
| **電話＋紙の連絡帳** | 現状のアナログ運用（比較の基準線） |
| **汎用クラウド（Googleフォト共有 等）** | 施設が自前で流用する想定の一般ツール |

## 4. 手段ごとの詳細

### 4-1. LINE公式アカウント
- **できる**：P2（ハナ子）が唯一使いこなせるUIで、認証もLINEアカウント任せ＝記憶・入力が要らない（**C ○**）。友だち登録した家族へ直接届き、無料〜低コスト（**G ○**）。
- **できない**：一斉配信が基本で、「この入居者の今日」を**個人単位で送り分けられない**（**B ×**）。友だち全員に配信されるため、家族ごとの直接到達は運用でしか担保できない（**A △**）。施設管理端末から投稿すること自体はできるが、送れるのは一斉配信で、撮影から個別配信までは現場で完結しない（**D △**）。1対1トークで返信は来るが担当が定まらず記録に残らない（**E △**）。データはLINE社側（**F ×**）。
- **一言**：P2適合という最難関を唯一クリアするが、個別性・データ主権で詰む。

### 4-2. ほのぼのNEXT（家族連絡オプション）
- **できる**：入居者単位の記録が土台なので個別配信の素地はある（**B ○**）、家族アプリ経由で直接も届く（**A ○**）。
- **できない**：業務システム然としたID/パスワードlog inで、P2は初回で脱落（**C ×**）。入力は**事務室PCからのみ**で、施設管理端末を使っても現場で完結しない（**D ×**、as-is 4-1）。家族→職員への反応は主眼になく戻らない（**E ×**）。家族向けオプションは**月額数十万円規模**で施設規模に見合わない（**G ×**、P5 Pain）。データ保持形態はベンダー依存（**F △**）。
- **一言**：個別性は満たすが、最重要制約のP2とコストで現場に入らない。

### 4-3. 市販の家族連絡アプリ（きずなネット等）
- **できる**：施設→家族の直接・個別配信を前提に設計され、写真共有・既読/コメントを備える（**A ○ / B ○**）。
- **できない**：アプリのインストールとID/パスワード認証が前提で、P2の記憶・入力の壁を越えられない（**C ×**）。施設管理端末にアプリを入れれば撮影〜個別配信を現場で完結できる余地はあるが、運用は製品次第で、施設の**私物スマホ撮影禁止・共用カメラ**運用と噛み合わないことが多い（**D △**）。反応機能はあってもP4の「報われる感覚」設計まではまちまち（**E △**）。クラウドSaaSで施設側にデータを置けない（**F ×**）。月額は施設規模で発生（**G △**）。
- **一言**：家族連絡の王道だが、P2適合とセルフホストという本件固有の2条件で外れる。

### 4-4. 電話＋紙の連絡帳（基準線）
- **できる**：紙は完全に施設内で完結（**F ○**）、追加費用ゼロ（**G ○**）。
- **できない**：電話は太郎にしか行かず、連絡帳は面会時しか読めない＝**そもそも届かない**（**A ×**）。個別ではあるが滞留する（**B △**）。電話は誰でも使えるが施設がP2にかけない運用（**C △**）。撮影から配信までを現場で完結できない（**D ×**）。感謝は職員に戻らない（**E ×**）。
- **一言**：現状そのもの。データ主権と低コスト“だけ”は満たす＝守りたい長所の基準。

### 4-5. 汎用クラウド（Googleフォト共有 等）
- **できる**：撮った写真を共有リンク/招待で直接渡せる（**A ○**）、無料（**G ○**）。
- **できない**：Googleアカウント・共有リンク操作はP2に不可（**C ×**）。アルバム単位で入居者単位の個別管理は手作業（**B △**）。撮影自体は施設管理端末で行えるが、入居者ごとの送り分けは手作業になり現場で完結しない（**D △**）。コメントは付くが介護文脈の反応設計はない（**E △**）。データはGoogle側（**F ×**）。
- **一言**：手軽だが、P2適合・個人情報の施設管理・運用ルール適合をすべて外す。

## 5. 比較から分かったこと

### 5-1. 「全部入り」が存在しない
7軸を同時に満たす既存手段は無い。特に以下の**3条件が同時に成立する手段が皆無**である。

- **C. P2が使える**（記憶・入力を求めない） — 満たすのは実質 LINE のみ
- **B. 個別配信** — LINE が最も苦手
- **F. 施設で管理**（セルフホスト） — SaaS系はすべて×

強みが手段ごとに分散しており、**「LINE並みにP2が使えて、ほのぼの並みに個別で、紙並みに施設内に置ける」**の交点に既存プロダクトが居ない。ここが本システムの空白地帯である。

### 5-2. 既存手段から引き継ぐべき長所（守るべき基準）
比較は「既存を全否定して作り直す」ためではない。次は**満たせている数少ない長所**であり、本システムでも下回ってはならない基準になる。

- LINE の **C（P2適合）と G（低コスト）**
- 紙／電話の **F（施設内でデータが完結）**

### 5-3. 次工程（ToBe）への申し送り
本書は「何を作るか」を決めないが、ToBe が満たすべき**必要条件**は比較から確定した。

1. **A＋B の両立**：施設から、家族一人ひとりへ、入居者単位で直接届く。
2. **C を最優先**：P2が使えない設計は、他がどれだけ良くても不可（＝設計の起点）。
3. **D**：施設管理下の共用スマホ／タブレットで、撮影から個別配信まで現場で完結（PC前提の運用は現場で回らない）。
4. **E**：家族の反応が職員本人に戻る。
5. **F＋G**：施設側でデータを持て、80名規模で継続できるコスト・運用。

> これらを**どう実現するか**は `04_to-be.md`（解決方針）で扱う。認証方式・技術選定はそこで確定済みの設計判断（別途）と接続する。

## 脚注：本書の前提について

- 各手段の○△×は、**一般的な製品特性と as-is の設定に基づく想定評価**であり、個別製品の最新仕様を逐一検証したものではない。実導入検討時に製品ごとのトライアルで再評価する。
- 「市販の家族連絡アプリ」はカテゴリとしての一般像であり、特定製品の優劣を断じるものではない。
- コスト（G）の水準は as-is 脚注・P5 Pain（既存ベンダーの家族向けサービスが月額数十万円規模）を根拠とする。
