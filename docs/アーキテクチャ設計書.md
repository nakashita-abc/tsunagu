# アーキテクチャ設計

本書は、[05_要件定義.md](05_要件定義.md) の要件を満たすコードを**どの単位に分けて置くか**を定める。

> **本書のスコープ**
> - **含む**：層の定義、各層の責務と禁止事項、ディレクトリ対応、依存方向、driver の切り替え、分割の判断基準。
> - **含まない**：エンドポイントの仕様（[06_API設計.md](06_API設計.md)）、テーブル定義（[DB設計書.md](DB設計書.md)）、画面構成（[09_画面設計.md](09_画面設計.md)）。
>
> 実装時の手順は `.claude/skills/implementation/SKILL.md` が本書を参照する。

## 0. 採用する構成

**Presentation / Service / Repository の3層**とする。

| 層 | 役割 | 置き場所 |
|---|---|---|
| Presentation | 外界との境界。HTTP と画面 | `web/app/**` |
| Service | ユースケースの手順とビジネス規則 | `web/lib/service/*.ts` |
| Repository | 永続化・外部サービスへのアクセス。契約と実装 | `web/lib/repository/<name>/*.ts` |

層ではない置き場所を2つ持つ。

| 置き場所 | 役割 | ディレクトリ |
|---|---|---|
| モデル | **型のみ**。ふるまいを持たない。どの層からも参照してよい | `web/lib/model/*.ts` |
| 共有 | 副作用のない純粋関数。特定の層に属さないもの | `web/lib/shared/*.ts` |

### 0-1. なぜ3層か

| 検討した案 | 判断 |
|---|---|
| **3層（採用）** | MVPの規模（エンドポイント2本・画面5枚）に対して、層の数と実装量が釣り合う。契約（interface）は Repository が自分で持つ |
| usecase + port + domain の4〜5層 | 却下。`domain` に置くビジネス規則が現時点でほぼ無く、空の層を作ることになる。「将来の拡張を見越した先回りの抽象化をしない」という方針に反する |
| 層を定義せず責務分離の原則のみ | 却下。層の境界がパスから読み取れないため、実装のたびに解釈が揺れる |

**この判断は ADR 候補（High）**。複数の妥当な案があり、「層の少なさ」と「ドメインロジックの置き場の明確さ」のトレードオフがある。

### 0-2. なぜ型だけ別に置くか

3層には domain 層がないため、`TimelinePost` のようなドメインの型に行き場がない。現状は `web/lib/db/types.ts` が「ドメインの型」「永続化の契約」「driver 依存の実装詳細」を1ファイルに同居させており、どの層のものか判別できない。

そこで**型だけを `lib/model/` に集約し、ふるまい（ビジネス規則）は Service に置く**。`lib/model/` は層ではないので、どの層からも参照してよい。

**この判断も ADR 候補（Medium）**。「契約を Repository が持つ」案との比較になる。

## 1. 依存方向

```
app/**/route.ts, page.tsx            Presentation
        │ 呼ぶ
        ▼
lib/service/*.ts                     Service
        │ 契約にだけ依存する
        ▼
lib/repository/<name>/types.ts       Repository（契約）
        ▲ 実装する
        │
lib/repository/<name>/stub.ts
lib/repository/<name>/postgres.ts    Repository（実装）
lib/repository/<name>/index.ts       driver の切り替え

lib/model/*.ts   型のみ。どの層も import してよい／どの層も import しない
lib/shared/*.ts  純粋関数。Presentation・Service・Repository から import してよい
```

**逆向きの import は禁止。**

## 2. 各層の責務と禁止事項

### 2-1. Presentation（`web/app/**`）

| やること | やらないこと |
|---|---|
| cookie・クエリ・ボディの取り出しと**形式の検証** | データの取得・更新を Repository に直接依頼する |
| 認証主体の解決の**呼び出し**（判定そのものは Service） | ビジネス規則の判断（期限・権限の条件分岐の中身） |
| HTTP ステータスと Problem Details の組み立て | `stub.ts` / `postgres.ts` を直接 import する |
| レスポンスの整形（日時の文字列化、フィールドの選択） | 写真参照の URL 解決など、保存方式に依存する処理 |
| 画面のレンダリング | |

`traceId` の生成、`instance` の指定、`problemResponse()` の呼び出しはこの層に残す。

### 2-2. Service（`web/lib/service/*.ts`）

| やること | やらないこと |
|---|---|
| ユースケース1件の手順を組み立てる | `NextRequest` / `NextResponse` / `cookies()` を触る |
| ビジネス規則の判断（セッションの有効期限、在籍状態、同意の有無） | HTTP ステータスコードや Problem Details を組み立てる |
| 複数 Repository の呼び出しの調整 | SQL・S3・Cognito の API を直接呼ぶ |
| **テナント境界の適用**（4章） | 画面の文言を決める |

結果は「成功／失敗の種別」を表す値で返す。HTTP への翻訳は Presentation の責務。

**Service が1行の委譲だけになっても層を飛ばさない。** 層の有無がエンドポイントごとに違うと、次にどこを読めばよいかが分からなくなる。一貫性を優先する。

### 2-3. Repository（`web/lib/repository/<name>/*.ts`）

| ファイル | 役割 |
|---|---|
| `types.ts` | 契約（interface）とクエリの入力型。`lib/model/` の型だけを参照する |
| `index.ts` | driver の切り替え。呼び出し側に実装を見せない入口 |
| `stub.ts` | 固定データによる実装 |
| `postgres.ts` / `cognito.ts` | 本番実装（未実装のものは `throw` する） |

| やること | やらないこと |
|---|---|
| 永続化・外部サービスへのアクセス | `NextRequest` / `NextResponse` / `cookies()` を知る |
| 保存形式と `lib/model/` の型の相互変換 | HTTP ステータスや Problem Details を組み立てる |
| 保存方式に依存する解決（写真参照 → URL、カーソルの符号化） | ユースケースの手順を組み立てる |
| 全クエリへの施設スコープの適用（4章） | |

### 2-4. モデル（`web/lib/model/*.ts`）

型・列挙・判別可能な共用体のみ。**関数を置かない。** 他のどのディレクトリも import しない。

### 2-5. 共有（`web/lib/shared/*.ts`）

副作用のない純粋関数と、環境変数の読み出し。ここに置くのは「どの層からでも呼んでよく、呼んでも層の境界を壊さないもの」に限る。迷ったら層のどれかに置く。

## 3. driver の切り替え

環境変数で実装を差し替える。切り替えの判断は `index.ts` の内側に閉じ、呼び出し側は driver の種別を知らない。

| 変数 | 値 | 既定 | 未実装時の挙動 |
|---|---|---|---|
| `DB_DRIVER` | `stub` / `postgres` | `stub` | `postgres` は `throw`（スキーマ適用とクエリ実装が必要） |
| `AUTH_DRIVER` | `stub` / `cognito` | `stub` | `cognito` は `throw`（User Pool の用意と `InitiateAuth` 実装が必要） |

値の読み出しは `lib/shared/env.ts` の `getDbDriverName()` / `getAuthDriverName()` を使う。**`process.env` を直接読まない**（許容値の検証がここに集まっているため）。

写真参照の URL 解決は保存形式に従うため、判断を `DB_DRIVER` に相乗りさせる（`stub` は完成形の URL を持ち、`postgres` は S3 の `object_key` を持つ）。

## 4. テナント境界（NFR-47）

施設間のデータ分離は**アプリケーション側の責任**であり、インフラの契約境界に依存させない（[05_要件定義.md](05_要件定義.md) NFR-47・ADR-001・ADR-003）。実装上の規定は次の3つ。

1. **`facilityId` はセッションから解決したものだけを使う。** リクエストのパス・クエリ・ボディから受け取らない（[06_API設計.md](06_API設計.md) 0章）。
2. **Repository の全クエリに施設の絞り込みをかける。** 契約の入力型に `facilityId` を必須で持たせ、省略可能にしない。
3. **クライアントが送ってよい識別子は、同一施設内で自由に選べるものに限る**（`postId`・`residentId` 等）。`staffId`・`familyMemberId` は送らせない（NFR-41・NFR-42）。

家族は自分が紐づく入居者の情報のみにアクセスできる（NFR-41）。したがって家族向けのクエリは、施設の絞り込みに加えて `familyMemberId` による絞り込みも必須とする。

## 5. 分割の判断基準

層を定めた目的は責務の分離だが、**分離そのものを目的にしない。**

| 基準 | 内容 |
|---|---|
| 変更しやすさ | この箇所に将来来る修正を想定し、その修正が1箇所で済む形にする |
| 重複 | 同じ処理が**3回目**になってから共通化する。2回目では抽象化しない |
| 直交性 | ある変更が無関係なファイルのテストを壊すなら、境界の位置が誤っている |
| 先回りしない | 今の要件にない引数・オプション・抽象を作らない |
| 行数 | **1ファイル300行は上限ではなく点検の観測点。** 超えたら責務の混在を確認し、混在していなければ分割しない。テストファイルと型定義ファイルは対象外 |

行数だけを理由にファイルを割ると、意味のない中間ファイルが増えて「過剰な責務の分離」になる。分割の根拠は常に責務であって行数ではない。

## 6. 現状のコードの帰属

本書の制定時点で、`web/` 配下は3層になっていない。移行先を次のとおり定める（移行は別タスク）。

| 現在のファイル | 移行先 | 備考 |
|---|---|---|
| `web/app/api/*/route.ts` | Presentation | 検証・認可の入口・Problem Details はここに残す。データ取得は Service 経由に変える |
| `web/app/**/page.tsx` | Presentation | 同上 |
| `web/lib/db/types.ts` の `Db` interface | `lib/repository/db/types.ts` | 契約 |
| `web/lib/db/types.ts` の `TimelineQuery` / `StaffReactionsQuery` / `Page<T>` | `lib/repository/db/types.ts` | 永続化の入出力型 |
| `web/lib/db/types.ts` の `TimelinePost` / `StaffReaction` / `AuthSubject` / `Session` / `SubjectKind` / `SubjectStatus` / `PhotoRef` | `lib/model/` | 型のみ。ふるまいを剥がす |
| `web/lib/db/types.ts` の `sessionTtlMs()` | Service | セッション有効期間はビジネス規則（ADR-032）。DB型定義ファイルに置くべきものではない |
| `web/lib/db/index.ts`（`getDb()`） | `lib/repository/db/index.ts` | driver 切り替え |
| `web/lib/db/stub.ts` | `lib/repository/db/stub.ts` | |
| `web/lib/db/cursor.ts` | `lib/repository/db/cursor.ts` | 符号化は保存方式の都合。`CursorPosition` 型は `lib/model/` |
| `web/lib/fixtures/*` | `lib/repository/db/fixtures/*` | stub 実装の一部 |
| `web/lib/auth/index.ts`（`getAuthDriver()`） / `stub.ts` / `types.ts` | `lib/repository/auth/*` | 契約と実装 |
| `web/lib/auth/session.ts`（`resolveSession()`） | Service | 期限の判定はビジネス規則 |
| `web/lib/auth/current-staff-stub.ts` | Service | 暫定。解消時に削除する |
| `web/lib/photos/resolve.ts`（`resolvePhotoUrl()`） | `lib/repository/photos/` | 保存方式に依存する。Presentation から直接呼ばない |
| `web/lib/http/problem-response.ts` / `rfc3339.ts` | `lib/shared/http/*` | Presentation からのみ使う想定だが、純粋関数なので共有に置く |
| `web/lib/env.ts` | `lib/shared/env.ts` | |
| `web/lib/rate-limit.ts` | `lib/shared/rate-limit.ts` | 単一インスタンス前提（NFR-46・NFR-76） |

### 6-1. 移行の順序

1. `lib/model/` を切り出す（型の移動のみ）
2. `lib/shared/` へ移動する（`env` / `http` / `rate-limit`）
3. `lib/repository/` に再編する（`db` / `auth` / `photos`）
4. `lib/service/` を新設し、`resolveSession()` と `sessionTtlMs()` を移す
5. `route.ts` を Service への委譲に書き換える

各ステップごとに `cd web && npm test` を通す。
