# 要件定義（MVP）

本書は、[04_to-be.md](04_to-be.md) で定めた解決方針を、**MVPとして実装可能な粒度の要件**に落とす。
あわせて、[01_ペルソナ.md](01_ペルソナ.md) が要件定義に申し送った**論点1〜4**の決着をここで付ける。

> **本書のスコープは「何を満たすか（What）」まで。**
> 画面・DB・API の具体（How）は step5 の各文書で扱う。

## 1. 目的とMVPの範囲

### 1-1. 目的（一文）

**施設で暮らす高齢者の日常の様子を、施設から家族一人ひとりへ入居者単位で直接届け、家族の反応を職員本人に返す。その入口を、最も弱いユーザー（P2）に合わせる。**


## 3. 利用者と役割

### 3-1. ロール（MVPは4つ）

| ロール | 該当ペルソナ | 位置づけ |
|---|---|---|
| **施設管理者** | P5 中村 | 入居者・職員・家族の名簿、同意、発信状況を管理する。1施設に1名以上 |
| **職員** | P4 さくら | 手元の端末（共用・私物を問わない）から発信し、自分の投稿への反応を受け取る |
| **家族** | P1 太郎、P2 ハナ子、P3 美咲 | 紐づく入居者の投稿を閲覧し、反応を返す。管理操作は持たない |
| **入居者（自律操作時）** | ―（該当ペルソナなし） | 施設が「自律的に操作できる」と判定した場合に限り、自分から家族へ直接発信する。管理操作は持たない（4-7・[ADR-049](ADR.md#adr-049)） |

### 3-2. 権限マトリクス

| 操作 | 施設管理者 | 職員 | 家族 | 入居者（自律操作時） |
|---|:---:|:---:|:---:|:---:|
| 投稿の作成 | × | ○ | × | ○（自分名義のみ、FR-703） |
| 自分の投稿の削除 | ― | ○ | × | ○（FR-706） |
| 任意の投稿の削除 | ○ | × | × | × |
| 自施設の全投稿・全反応の閲覧 | ○ | △（自分の投稿への反応） | × | × |
| 紐づく入居者の投稿の閲覧 | ― | ― | ○ | ― |
| 反応の送信 | × | × | ○ | × |
| 自分のログアウト（FR-406） | ○ | ○ | ○ | ○ |
| 入居者・職員の登録／変更 | ○ | × | × | × |
| 入居者の自律状態の設定・変更（FR-701） | ○ | ○ | × | ×（自分では設定できない） |
| 家族名簿の登録／変更／失効 | ○ | × | × | × |
| 写真掲載同意の記録・変更 | ○ | × | × | × |

> **自律状態（FR-701）を職員にも許すのは、既存の「入居者・職員の登録／変更」を管理者専任とした方針からの意図的な逸脱である。** 自律状態は登録情報ではなく日々の様子から現場が判断するものであり、判断の頻度・鮮度の面で管理者より現場の職員の方が実情に近い（[ADR-049](ADR.md#adr-049)）。**入居者本人がこの状態を自分で変更できない**のは、自律性の自己申告を認めると判定が形骸化するため。

> 施設管理者に投稿権限を与えない（×）のは、**発信は現場で起きる**という前提（D軸）を要件で固定するため。管理者が代行できると、K1（発信の入口が細い）の解決が管理者の手作業に化ける。

## 5. 非機能要件

### 5-1. NFR-1 ユーザビリティ（高齢の家族を床とする）

| ID | 要件 |
|---|---|
| NFR-11 | 家族向けの主要導線は、**説明を読まずに**目的を達成できること |
| NFR-12 | 本文の文字サイズは既定で**18px相当以上**。端末側の文字拡大設定に追従して崩れないこと |
| NFR-13 | 家族向けの文言に**技術用語・カタカナ語・システム用語**を使わないこと（「同期」「セッション」「認証」等を画面と通知に出さない）。**例外として、認証に伴う語（「ログイン」「パスワード」等）は認証画面に限って許容する**——[ADR-012](ADR.md#adr-012) で引き受けた代償であり、認証後の画面には持ち込まない。**ログアウト（FR-406）はこの例外の唯一の持ち出し先**であり、常時表示せず設定相当の場所に置く |
| NFR-14 | 操作要素の当たり判定は**48×48px相当以上**、要素間に十分な間隔を取ること |
| NFR-15 | 家族の閲覧導線に、**横スワイプ・長押し・階層移動を必須としない**（縦スクロールと単純なタップで完結する） |
| NFR-16 | 1画面に情報を詰め込まないこと。**写真を最大の要素**として扱うこと |
| NFR-17 | 職員の投稿導線は**片手で**完結できること |
| NFR-18 | 色のみに依存して情報を伝えないこと。文字と背景のコントラスト比 **4.5:1 以上** |

### 5-3. NFR-3 対応環境・性能

| ID | 要件 |
|---|---|
| NFR-33 | 職員側は**施設管理下の共用スマートフォン／タブレットでも、職員の私物端末でも**動作すること。**専用端末の新規導入を前提としない**（[ADR-046](ADR.md#adr-046)：端末の種類をシステムは制約しない） |

### 5-4. NFR-4 セキュリティ・テナント分離

| ID | 要件 |
|---|---|
| NFR-41 | 家族は、**自分が紐づく入居者の情報のみ**にアクセスできること。他の入居者の情報に到達する経路が存在しないこと |
| NFR-42 | 職員・管理者は、**自施設の情報のみ**を閲覧・操作できること |
| NFR-43 | 通信は暗号化されること。写真を含む個人情報は**保存時にも保護**されること |
| NFR-44 | 写真等のファイルは、**推測可能なURLで第三者が到達できない**こと（リンクを知っていれば誰でも見られる状態を作らない） |
| NFR-46 | 認証は**標準的な強度**を確保すること（推測されにくい資格情報、試行回数の制限、資格情報の再設定手段、保管時のハッシュ化）。[ADR-012](ADR.md#adr-012) により**認証を緩めない**選択を採ったため、緩めた分を別の要件で埋め合わせる構成は採らない |
| NFR-47 | **施設（テナント）間のデータ分離は、アプリケーション側の責任**として担保すること。提供側の共有環境に複数施設を収容するため、分離をインフラの契約境界に依存させない（[04_to-be.md](04_to-be.md) 4章／[ADR-001](ADR.md#adr-001)・[ADR-003](ADR.md#adr-003)） |

### 5-5. NFR-5 プライバシー・法令・責任分界

| ID | 要件 |
|---|---|
| NFR-51 | 個人情報保護法に準拠すること。利用目的を家族・入居者に明示できること |
| NFR-52 | 写真の掲載は、入居者本人または代理人の**同意の記録がある場合に限る**（FR-504） |
| NFR-53 | **健康状態・医療に関する情報を扱わない**（要配慮個人情報の取得を避ける）。扱うのは日常の様子に限る。**例外として、入居者が自律的に操作できるかどうかの状態（FR-701）のみを保持する**。この状態は現場の判断結果を表す1つの値であり、判断の根拠・経過・診断内容は持たない |
| NFR-54 | 撮影・投稿に**他の入居者が写り込む**可能性への運用上の注意を、導入手順書に記載すること。**この注意は、自律的に操作できる入居者本人にも、FR-701で状態を設定する時点で施設が伝える**こと |
| NFR-55 | 施設外への転送・SNS共有を機能として提供しないこと |
| NFR-56 | **施設と提供者の責任分界を文書で明示**すること。個人情報の取扱いにおける各者の立場、保存場所、事故時の連絡経路を含む |

> **NFR-53 は制約であると同時に設計上の防御である。** 扱う情報を日常の様子に限ることで、万一アクセスが漏れた場合のリスクの上限を下げている。次段で記憶・入力を求めない認証（AC-A）に戻る際、**この上限の低さが、認証を緩める判断の前提になる**（[ADR-012](ADR.md#adr-012)）。
> **NFR-53 の例外（自律状態フラグ）は、この防御の思想を変えるものではない。** 保持するのは「できる／できない」の1ビットのみで、判定の根拠・経過・診断内容という*詳細*は持たない。要配慮個人情報に実質的に触れうる情報を、ラベルの言い換えではなく**取得範囲を最小の1ビットに絞ることで**引き受ける、という設計判断である（[ADR-049](ADR.md#adr-049)）。
> **NFR-56 は [04_to-be.md](04_to-be.md) 4-1 が「モデルBを選んだ代償」として要件化を申し送った項目**である。データの管理主体が施設から提供者との共同体制に変わったことへの対応。
> **NFR-51 と、FR-602（退居時の削除）を欠番にしたことの関係（要注意）。** MVPは退居後もデータを保持し、**削除の手段をシステム機能として持たない**。個人情報保護法上の削除請求に応じる必要が生じた場合は、**提供者による運用（手作業）での対応**となる。利用目的の明示（NFR-51）と責任分界の文書（NFR-56）に、この運用対応を明記すること。**MVPの利用者数を限定的に保つ前提での割り切り**であり、保持が問題になった時点で FR-602 を復活させる。

### 5-6. NFR-6 データ主権 —— **撤回・欠番**

### 5-9. NFR-9 入居者本人向けユーザビリティ（自律操作時）

FR-7群（4-7）のための要件。**NFR-1群（P2を床とする家族向け基準）を継承したうえで、さらに厳格な基準を課す。** 入居者本人は家族以上に支援を受けにくい状況（施設内・職員が常時隣にいるとは限らない）で操作する可能性があるため。

| ID | 要件 |
|---|---|
| NFR-91 | NFR-11〜18は、入居者本人向けの発信導線にもすべて適用する |
| NFR-92 | 入居者本人向けの発信導線は、**主要な操作がボタン数個・単一画面に近い遷移で完結**すること。具体的な上限（タップ数・画面数）は画面設計（step5）で定める |
| NFR-93 | 入居者本人向けの導線に、**家族向け以上の機能・設定項目を追加しない**こと（発信できることだけに絞り、閲覧・履歴確認等の付随機能を持たせない） |

> NFR-92 の数値は、他のNFRの数値（5-1脚注）と同様に**仮置き**であり、実地検証で調整する。NFR-93 は、FR-7群の「システムは入居者の発信活動を管理しない」という線引き（4-7）を、入居者本人側のUIにも一貫させるための要件である。

## 6. 扱う情報（概念レベル）

DB設計は step5（[08_DB設計.md](08_DB設計.md)）で行う。ここでは**どんな情報を扱う必要があるか**だけを列挙する。

| 情報 | 主な内容 | 関連要件 |
|---|---|---|
| 施設（テナント） | 施設の識別、文例、運用設定 | NFR-47・FR-103 |
| 入居者 | 氏名、状態（入居中／退居）、写真掲載同意の有無、**自律的に操作できるかの状態** | FR-501・FR-504・FR-701 |
| 職員 | 氏名、利用可否、**認証に使うメールアドレス** | FR-502・[ADR-047](ADR.md#adr-047)・[ADR-048](ADR.md#adr-048) |
| 家族 | 紐づく入居者、続柄、通知の可否、アクセスの状態（招待前／招待済／利用中／失効） | FR-404・FR-203・FR-501 |
| 投稿 | 対象入居者、投稿者（**職員または入居者本人**）、写真、テキスト、日時、削除の記録 | FR-101〜106・FR-701〜706 |
| 反応 | 対象投稿、送信した家族、日時 | FR-301〜303 |

> **「施設」を最上位に置く。** 複数施設が同一の環境を使ってもデータが交差しないことを NFR-41・NFR-47 が要求するため。**分離の実現方式は step5**（[ADR-001](ADR.md#adr-001) の未決事項）。

## 8. トレーサビリティ

### 8-1. 課題（K1〜K6）→ 要件

### 8-2. 必要条件（A〜G。F は欠番）→ 要件

| **G** 見合うコスト | NFR-71〜73・NFR-75〜77（NFR-74 は欠番） |

**A・B・D・E・G は要件で満たす。C は MVP では部分的である。**

> **FR-7群（4-7・入居者本人の発信）は、この表のどのK番号・軸にも対応しない。** 01〜04の課題分析から導いたものではなく、汎用サービスとしての追加のため（3-1脚注・[ADR-049](ADR.md#adr-049)）。トレーサビリティの対象外として扱う。

これは軽い欠落ではない。[03_既存サービス比較.md](03_既存サービス比較.md) 5-1 は「**差別化の中心は C に一点集中する**」と結論しており、**MVP はその中心をまだ握っていない**。比較表（同 3章）に照らすと、MVP の位置は「市販の家族連絡アプリ（A○ B○ **C×** D△ E△ G△）を、D・E・G で上回ったもの」であって、**C で既存手段を抜いた状態ではない**。

この状態で MVP を出す判断と、その代償は [ADR-012](ADR.md#adr-012) に記録した。**MVPで検証できるのは「発信が続くか（M1・M2）」と「反応が戻るか（M4）」であり、本システムの賭けである C は次段まで検証されない。**

なお [03_既存サービス比較.md](03_既存サービス比較.md) 5-2 が「下回ってはならない基準」とした2点のうち、**G（低コスト）は NFR-76 で基準化している**。**C（P2適合）は MVP では基準に届かない**ことを、ここで明示しておく。

## 9. MVPから意図的に外したもの（次段へ）

1-2 の「含まない」が**方針として対象外**であるのに対し、こちらは**必要性を認めたうえで MVP から落とした**もの。落とした判断も設計判断であり、復活させるときに理由を読み返せるようにする。

### 9-1. 要件定義の時点で落としたもの

### 9-2. 設計後の見直しで落としたもの（2026-09-22・ペルソナ縛りの解除）

**判断の記録は [ADR-050](ADR.md#adr-050)。** 撤回した ADR は [ADR-023](ADR.md#adr-023)・[ADR-028](ADR.md#adr-028)・[ADR-034](ADR.md#adr-034)、改訂したのは [ADR-017](ADR.md#adr-017)・[ADR-019](ADR.md#adr-019)・[ADR-022](ADR.md#adr-022)・[ADR-035](ADR.md#adr-035)・[ADR-040](ADR.md#adr-040)・[ADR-045](ADR.md#adr-045)。

06〜09 の設計を終えた時点で、**要件のどれが実装難易度を跳ね上げているか**が具体的に見えるようになった。そこで、**特定のペルソナの事情に立脚していて、かつ実装量を大きく押し上げている要件**を洗い直して落とした。

上位の判断は CLAUDE.md の制約の撤回である——**「P2 が最重要制約」という位置づけをやめた**（2026-09-22）。ペルソナは利用者モデルの一例にすぎず、**一人物の事情を全要件の床に据えると、技術的制約と実装難易度が跳ね上がる**ため。以下はその適用結果である。

> **落とす基準は「ペルソナ由来かどうか」ではなく、「ペルソナ由来 かつ 実装量を押し上げるか」。** NFR-12〜18（文字サイズ・当たり判定・コントラスト・文言）も P2 由来だが、*実装を増やさない規則*であり削っても軽くならないため残した（5-1）。逆に FR-7群（4-7）はペルソナ由来ではないが、汎用サービスとしての価値を認めて残している。

| 落としたもの | 由来（縛り） | 落とした理由 | 消える設計 |
|---|---|---|---|
| **写真送信の再送・保留**（旧 NFR-35） | 施設の回線品質（[02_as-is.md](02_as-is.md) 脚注・P4） | **MVPで最も実装量の大きい要件だった。** 回線で送信が失敗したら、職員はその場で撮り直して送り直せる（職員は現場にいる＝D軸）。「失われない」ことを*システムの責務*として引き受ける根拠が、未検証の回線前提しかない | [ADR-020](ADR.md#adr-020)（2段階アップロード）・[ADR-028](ADR.md#adr-028)（`Idempotency-Key`）・書きかけの保持と再送導線 |
