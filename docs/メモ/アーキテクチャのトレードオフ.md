# アーキテクチャのトレードオフ

本書は、デプロイ先・API方式・認証基盤をめぐって検討した選択肢と、採用しなかった案を**なぜ外したか**を含めて記録する。
[05_要件定義.md](../清書/05_要件定義.md)・[06_API設計.md](../清書/06_API設計.md) の「決定」の裏にある判断過程のメモであり、本書自体は正式な設計書（清書）ではない。

> **現時点の結論**：デプロイは **Vercel**。AWSは **S3・Cognito** を使う（Lambda・API Gatewayは使わない）。

---

## 1. デプロイ先：Vercel

### 1-1. 比較した案

| 観点 | Amplify Hosting | Vercel（採用） | 常駐1コンテナ（Fly.io/Render/App Runner） |
|---|---|---|---|
| Next.js 16対応 | AWSのサポート表に依存し遅れうる（要確認） | 当日対応 | upstreamそのもの |
| VPC内private RDSへの接続 | 不可（要確認） | 不可 | 可 |
| デプロイ運用 | git push | git push（最良） | Dockerfile・ヘルスチェックを自前で用意 |
| インスタンス数 | N（自動スケール） | N（自動スケール） | 1（固定できる） |
| コスト（MVP規模） | 数百円〜/月 | Pro $20/月必須（Hobbyは商用不可） | 700〜4,000円/月 |
| OSS自己ホスト | △ | △ | ◎ docker composeがそのまま手順書になる |

Amplifyは「AWSアカウント1つに寄せる」利点以外はVercelと同じ制約（後述のサーバーレス特有の3点）を受けた上に、DXとNext.js追従で劣る。選ぶ理由が薄いため不採用。

常駐1コンテナは、後述の③点（レート制限・写真サイズ・private RDS）がすべて不要になる点で技術的には最も素直だが、Dockerfile・デプロイ経路・ロールバックを自前で持つ運用コストが[C6](../清書/05_要件定義.md)（個人開発・運用担当なし）に対して重いと判断し、今回は見送った。

### 1-2. Vercel（サーバーレス）を選んだことで生じる制約と対応

これが本ドキュメントで一番重要な部分。**AmplifyもVercelも同じ制約を受ける**ため、Amplifyに変えても解決しない。

#### ① インメモリのレート制限が機能しない

[lib/rate-limit.ts](../../web/lib/rate-limit.ts) の `signInRateLimiter` はインスタンスごとに別のMapを持つ。関数が複数インスタンスに散ると、[NFR-46](../清書/05_要件定義.md)（試行回数の制限）の実効上限がインスタンス数倍に緩む。

- Cognitoは**ユーザー単位のロックアウトを標準では持たない**（Advanced Security Featuresは有料・要確認）ため、代替にならない
- **対応**：レート制限をPostgresの共有テーブル（`sign_in_attempts(key, count, reset_at)`）に移す。MVPで実施する

#### ② 写真アップロードがVercelの本文サイズ上限に当たる

Vercelのリクエスト本文上限は4.5MB。スマホ写真（2〜5MB）がRoute Handler経由では収まらないことがある。

- [ADR-020](../清書/05_要件定義.md)（2段階アップロード）は「再送・保留のため」という理由で一度撤回したが、それとは別の理由（本文サイズ制約）で**ブラウザ→S3への署名付きPUT**だけは必要になる
- 再送・下書き保持（職員は現場にいる＝D軸）までは復活させない。ADR-020撤回の理由自体は生きている
- **対応**：写真は署名付きPUTでS3に直接アップロードする。サーバーを写真のバイト列が通らなくなるため、転送量・実行時間の面でも得

#### ③ VPC内private RDSに接続できない

VercelもAmplifyも任意のVPCにcomputeを置けない。

- RDSをパブリックエンドポイントにすると、Vercel/Amplifyは固定の送信元IPを持たないためSGを広く開けることになり、[NFR-43](../清書/05_要件定義.md)の説明が苦しくなる
- **対応**：DBはNeon / Supabaseなど、コネクションプーラ同梱のサーバーレスPostgresを使う（生`pg`×サーバーレスの接続枯渇対策も兼ねる）

### 1-3. CloudFront+S3を外した理由（補足）

元々知られていた「SSRができない」だけでなく、**[NFR-41](../清書/05_要件定義.md)（家族は紐づく入居者の情報のみにアクセス）をクライアント側だけでは保証できない**ことが本質。静的配信では認可判断がブラウザ内に降りるため「到達経路が存在しない」を満たせない。

## 2. API方式：Route Handlerのみ（API Gatewayは不採用）

### 2-1. 比較

| 観点 | Route Handler（採用） | API Gateway + Lambda |
|---|---|---|
| 認可の実装 | セッションcookie（httpOnly・同一オリジン）がそのまま効く | 別オリジン対応（CORS等）が必要になる |
| 型の共有 | `lib/db/types.ts` を画面とAPIで直接共有 | 二重管理 or OpenAPIコード生成が必要 |
| テスト | 既にvitestで直接叩けている（`route.test.ts`） | sam local等の基盤が別途必要 |
| IaC | 不要 | CDK/SAM/Terraformを1式維持 |
| WAF・使用量プラン | ホスティング側に依存 | 標準で付く |
| [C6](../清書/05_要件定義.md) 運用負荷 | ◎ | × |

API Gatewayの利点（WAF・VPC接続・使用量プラン）はどれも本物だが、MVPのどの要件もそれを要求していない。一方コストは「IaC・CI・ローカル環境・CORS・型同期を1人で永続的に維持する」形で確実に発生するため、[C6](../清書/05_要件定義.md) に照らして不採用。

### 2-2. ハイブリッドの線引き

分割する軸は「同期/非同期」であり、「Route HandlerかAPI Gatewayか」ではない。

| 処理 | 置き場所 | 理由 |
|---|---|---|
| 全API（投稿・一覧・反応・管理） | Route Handler | 認可がセッション起点。応答を返す必要がある |
| EXIF除去・向き補正・サムネイル生成 | S3 PutObjectイベント→Lambda | 署名付き直PUTにするとサーバーを通らないため、後処理はイベント駆動が唯一の経路。GPS付きEXIFの残存は[NFR-53](../清書/05_要件定義.md)（取得範囲の最小化）に反するため必須 |
| 家族への通知のファンアウト（FR-203） | Lambda or Vercel Cron | 投稿APIの応答を通知配信で待たせない |
| セッション30日失効の掃除（ADR-032） | 定期実行（EventBridge/Vercel Cron） | 定期処理 |

**API Gatewayはこの表のどこにも登場しない。** 非同期処理の起点はイベント（S3通知・スケジューラ）であって、HTTPエンドポイントではない。「ハイブリッド」で足すのはLambdaであってAPI Gatewayではない。

### 2-3. 既にこの形になっている

[lib/db/index.ts](../../web/lib/db/index.ts)・[lib/photos/resolve.ts](../../web/lib/photos/resolve.ts)・[lib/http/problem-response.ts](../../web/lib/http/problem-response.ts) で業務ロジックが`lib/`に寄せてあり、`route.ts`は薄い殻になっている。将来Lambdaに処理を出す必要が生じても、移すのはハンドラの殻だけで済むため、API Gatewayを先回りして入れておく理由はない。

### 2-4. 撤退条件（先に決めておく）

次のいずれかが起きたら、API Gatewayではなく**まず常駐コンテナへの移行**を検討する（VPC接続・長時間実行はコンテナ側で解けるため、API Gatewayを足すより安い）。

1. 同期APIで10秒を超える処理が必要になった
2. 施設数が増えてAPI単位のスロットリング/使用量管理が要るようになった
3. VPC内リソース（private RDS、ElastiCache）への同期アクセスが必須になった

## 3. 認証基盤：Cognito維持

### 3-1. 検討した案

| | 自前照合（argon2id+Postgres） | Supabase Auth一本化 | **Cognito（採用）** |
|---|---|---|---|
| ベンダー数 | 多い（Neon+R2+Resend） | 少ない | 中間 |
| 認証の責任 | 自分で持つ | 向こう持ち | 向こう持ち |
| OSS自己ホスト | ◎ docker compose完結 | △ | × 不可 |
| [NFR-71〜73](../清書/05_要件定義.md) との整合 | - | - | **◎ そもそも提供者ホスト型を要求している** |

[NFR-71](../清書/05_要件定義.md)（施設はクラウド契約・環境構築をしない）・[NFR-73](../清書/05_要件定義.md)（管理者画面から完結、管理コンソールに触れない）は提供者ホスト型を前提としており、自己ホスト不可は要件上の減点にならない。[NFR-84](../清書/05_要件定義.md)（OSS公開）は「コードを公開する」要件であって「誰でも動かせる」要件ではないため、Cognito維持と矛盾しない。

### 3-2. Cognitoに実装時に効いてくる注意点

#### IAM署名が要るAPIと要らないAPIを分ける

| Cognito API | IAM署名 | 使う場面 |
|---|:---:|---|
| `InitiateAuth`（`USER_PASSWORD_AUTH`） | 不要 | ログイン |
| `RespondToAuthChallenge` | 不要 | 初期パスワード設定 |
| `ForgotPassword` / `ConfirmForgotPassword` | 不要 | パスワード再設定（NFR-46） |
| `AdminCreateUser` / `AdminSetUserPassword` | 必要 | 職員・家族の招待（FR-502・FR-404） |
| `AdminDisableUser` | 必要 | 退居による失効（FR-501・INV-11） |

家族・職員が日常的に通る経路はIAM不要で動く。IAMが要るのは管理者機能のみ。静的アクセスキーを環境変数に置かず、Vercel OIDC federation（`AssumeRoleWithWebIdentity`）でロールを引き受ける（キーのローテーション運用が発生しない＝[C6](../清書/05_要件定義.md)に効く、Vercelのプラン要件は要確認）。

#### App clientはsecret付きで作る

[route.ts](../../web/app/api/auth/session/route.ts) はサーバーがパスワードを受けて照合する構成のため、フローは`USER_PASSWORD_AUTH`（App clientで`ALLOW_USER_PASSWORD_AUTH`の明示的な有効化が必要）。SRPはサーバーが既にパスワードを見ている構成では利点が出ないため不要。

App clientをsecret付きで作り`SECRET_HASH`を添えること。secretなしだとclient IDの漏洩だけでUser Pool APIを直接叩かれ、アプリ側レート制限（[lib/rate-limit.ts](../../web/lib/rate-limit.ts)）を迂回される。

#### `challengeToken`はCognitoの内部値を露出させない

[lib/auth/types.ts](../../web/lib/auth/types.ts) の`challenge.challengeToken`は、実装するとCognitoの`Session`文字列（`NEW_PASSWORD_REQUIRED`）になる。

- 寿命が約3分（要確認）。[NFR-11](../清書/05_要件定義.md)（説明を読まずに達成できる）と相性が悪い
- Cognito固有の値がAPI契約に露出すると、[ADR-024](../清書/05_要件定義.md)（APIが外から見える契約）の観点で将来の認証基盤変更時に契約が壊れる

**対応**：サーバー側で自前の短命チャレンジID（Postgresの一時レコード、またはCookie＋署名）を発行し、Cognitoの`Session`は内部に隠す。インメモリ保持は不可（Vercelは複数インスタンスのため、レート制限と同じ理由）。

#### レート制限はCognito採用後も自前が必要

Cognitoは**ユーザー単位のロックアウトを標準で持たない**（Advanced Security Featuresは有料・要確認）。アカウント全体のRPS上限はあるが、特定1アカウントへの総当たりは止まらない。[NFR-46](../清書/05_要件定義.md)を満たすための[`signInRateLimiter`](../../web/lib/rate-limit.ts)は引き続き必要で、Vercel上では共有ストア（Postgres）への移設が必須（1-2 ①と同じ対応）。

`SignInOutcome`の`rate_limited`枠はCognitoの`TooManyRequestsException`を受けられるが、CognitoはRetry-After相当の値を返さないため`retryAfterSeconds`は固定値を入れる。

## 4. 確定した構成

```
Vercel（Next.js 16 / Route Handler のみ、API Gatewayなし）
  ├─ Neon or Supabase … Postgres（セッション・名簿・投稿・sign_in_attempts）
  ├─ Cognito          … パスワード照合のみ。IAMはAdmin系APIのみ、Vercel OIDCで引受
  ├─ S3               … 写真。ブラウザから署名付きPUTで直接アップロード
  └─ Lambda           … S3 PutObjectイベント起動（EXIF除去・サムネイル生成）
```

VPCは使わない（VercelからVPC内リソースに到達できないため）。

### コスト概算

| | 月額 |
|---|---|
| Vercel Pro | ¥3,000（固定・Hobbyは商用不可） |
| Neon / Supabase | ¥0〜3,000 |
| Cognito | MVP規模（1施設あたり数十MAU）は無料枠内の見込み（価格体系は要確認） |
| S3 + Lambda | ¥100未満（写真は直PUT・署名付きURL直配信でVercelの転送量を通らない） |
| **合計** | **¥3,000〜6,000**（[NFR-76](../清書/05_要件定義.md) 上限¥10,000/施設に収まる） |

## 5. 設計書・実装への反映が必要な項目（未着手）

この構成を選んだことで、既存の設計書・コードに次の修正が必要になる。本ドキュメントは記録のみで、着手は別途指示があってから行う。

1. **ADR-020の部分復活** —— 「再送・保留のための2段階アップロード」は撤回のまま、「Vercelの本文サイズ制約のためのS3署名付きPUT」だけを新規ADRとして起こす
2. **[lib/rate-limit.ts](../../web/lib/rate-limit.ts) の前提修正** —— コード内コメント「単一インスタンスでの運用を前提とする」をPostgres共有ストア前提に書き換え、実装も移行する
3. **[06_API設計.md](../清書/06_API設計.md) の写真URL不一致の解消** —— [職員側の`/api/staff/photos/{id}`プロキシ経路](../清書/06_API設計.md#L71)と[家族側の署名付きURL直](../清書/06_API設計.md#L129)が不一致。署名付きURL直に揃える
4. **`challengeToken`の抽象化** —— Cognitoの`Session`文字列を直接返さない実装に変更
5. **デプロイ構成（Vercel）・認証基盤（Cognito維持）のADRを新規に起こす**
6. **`lib/env.ts`の`AuthDriverName`** —— 将来`"postgres"`（自前照合）を足せる形にはなっているが、今回は対応不要。自己ホスト要求が出た時点で判断する
