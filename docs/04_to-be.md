# To-Be（解決方針）

本書は、[02_as-is.md](02_as-is.md) の課題（K1〜K6）と [03_existing-solutions.md](03_existing-solutions.md) の必要条件（A〜G）に対して、**本システムが何をどう解決するか（解決方針）**を定める。

> 本書のスコープは「**解決の方針**」まで。
> **具体的な機能仕様・画面・DB・API（step5）／要件の粒度（step4）／特定プロダクト・技術の選定は書かない。**
> 認証やインフラの“方向”は示すが、実現手段（製品名）は step5 の設計で候補比較のうえ決める。
> 登場人物・課題は [01_personas.md](01_personas.md) / [02_as-is.md](02_as-is.md) を参照。

## 1. 解決コンセプト（一言）

**施設から家族一人ひとりへ、入居者単位で“届く”。その入口を最も弱いユーザー（P2）に合わせ、データは施設が持ち続ける。**

情報伝達がしにくい構造（K1〜K6）を、「①発信を太く → ②直接・双方向に届ける」で断ち、最重要制約のP2適合（③）を土台に置く。データ主権（F）と運用の軽さ（G）は施設側クラウド＋自動化で両立する。

---

## 2. 解決の背骨（どこを切れば連鎖が解けるか）

as-is 2-3 の連鎖図（K1・K2・K4・K6 → LOW〈家族が知れる情報が少ない〉→ ASK〈問い合わせ〉→ K5〈施設長疲弊〉、かつ LOW → K3〈反応が戻らない〉）に対し、次の順で攻める。

```
① 発信の入口を太くする（K1・K4／D）      … 職員が施設の共用端末で撮る→短く出す→届く
② 太郎バイパス＋双方向にする（K2・K3／A・B・E） … 施設⇄家族全員が直接やり取り
        └→ この時点で LOW が解消
             └→ ASK が減り、K5（施設長疲弊）は“帰結として”下がる
③ 受け取れる入口をP2に合わせる（K6／C）   … 記憶・入力を求めない認証
　　土台：データは施設が保持（F）＋ 運用は自動化で軽く（G）
```

**要点：K5 は直接いじらない。**上流の LOW を断つことで、問い合わせ（ASK）と施設長の疲弊（K5）が副次的に下がる——これが本システムの効き筋。

## 3. 中核となる3つの解決方針

### 3-1. 職員の発信を「施設の共用端末で撮る→短く出す→届く」にする（K1・K4／D軸）
- 職員が**施設管理下の共用スマートフォンまたはタブレット**を使い、撮影から発信までを数十秒で現場で完結できるようにする。共用カメラで撮って事務室PCへ取り込む・PCの空き待ちという現状の律速（P4 Pain）を外す。
- **新しい端末の導入は前提としない**。すでに施設にある共用端末の用途を、職員間の業務連絡から家族向けの発信まで広げる。
- これは**既存の介護記録（ほのぼのNEXT）を家族に開くのではなく、家族向けの新しい発信経路を作る**ことで K4 を解く。法定記録の公開には踏み込まない。
- 「書くハードル」を下げる方向とする（ゼロから書かせない）。※具体手段は step4/5。

### 3-2. 施設と家族全員が「双方向に・直接」やり取りする（K2・K3／A・B・E軸）
- 施設からの情報が、太郎（P1）を介さず**家族一人ひとりへ直接**届く。周辺の家族（P3）まで、又聞きなしで同じ情報が届く（K2＝太郎ボトルネックの解消）。
- 情報は**入居者単位**で個別に届く（B軸。一斉配信ではない）。
- 家族から職員へ**反応（感謝など）が戻る**双方向とする（K3の解消。P4のやりがい／P2の「ありがとうを伝えたい」の両方を満たす）。
- **K5 はこの結果として軽減される**（LOW解消 → 問い合わせ減）。直接の対策項目ではなく帰結。

### 3-3. 受け取る入口をP2に合わせる（K6／C軸）
- 最も弱いユーザー（P2）が使えることを**床（floor）**に置く。ここを満たせないと、他がどれだけ良くても最重要ユーザーに届かない。
- 認証は**本人に記憶・入力を求めない方式**とする（論点2への回答＝方針確定。具体的な認証手段は step5 で選定）。
- 「届いても使えない」（K6）を解くため、大きな文字・大きな写真・迷わない操作を前提にする。※UIの具体は step5。

## 4. データ保持の方針（F・G軸）

**モデルA：クラウドを“施設側の契約”で用い、データの管理主体は施設であり続ける。**

- 個人情報（家族に見せる様子・写真等）は、**施設が契約するクラウド上**に置く。第三者のSaaS事業者が全施設のデータを保持する形は採らない（P5の「外部事業者に預けたくない」＝F軸を維持。既存SaaSが全滅した差別化点をここで確保する）。
- **物理サーバーは持たない**（固定費・運用負荷を避ける＝G軸）。クラウドにより運用コストを抑える。
- 施設が「自分たちで回せる」よう、**日常のデータ管理は管理者用画面から**行える方向とする。クラウドコンソールの直接操作は初期構築時の最小限に留める（P5「ITに強い職員1人が数時間で」）。
- **環境構築はコード化して自動化**する方向（再現可能・属人化を避ける）。※IaC等の具体手段は step5。

> 「どのクラウドか」「管理画面の具体」「自動化の実装」は step5（設計）で決める。本書は“施設がデータ主権を保つ／物理サーバーを持たない／管理は施設で完結”という**方針**まで。

## 6. 今回のスコープ外（次段に送る）

- **緊急連絡（as-is 1-3）**：発熱・転倒などの緊急フローは本MVPに含めない。まず「日常の様子を届ける」に集中し、P2適合を優先する。緊急連絡は同期性・確実性の要件が別物で、次段で扱う。
- **介護記録（ほのぼのNEXT）そのものの置き換え・連携**：法定記録の代替は狙わない（3-1のとおり別経路を作る）。
- **医療・ケアプラン・請求**：as-is のスコープ外を踏襲。

## 7. 要件定義（step4）への申し送り

方針は定めたが、**具体値・分岐の決めどころ**は要件で詰める。personas 論点表と接続する。

- **論点1（通知頻度）**：デフォルト値と、設定変更を誰に許すか（P1=まとめ／P2=変更させない／P3=自分で調整）。
- **論点3（職員の入力負荷 vs 家族の希望量）**：「職員が書ける量」を上限とする歯止めの具体。
- **論点4（公開範囲）**：誰に見せるかの指定を「誰が・いつ」行うか（P1=親族を増やしたい／P5=一律運用）。
- **認証の具体手段（論点2）**：記憶・入力を求めない方式の候補比較は step5 だが、要件として「P2が初回から説明なしで到達できる」受け入れ基準を置く。
- **ターンキー度（F・G）**：「ITに強い職員1人が数時間で導入できる」を非機能要件として定義。
