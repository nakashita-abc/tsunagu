# Resource Design Review

リソース設計をレビューする。

対象:
$ARGUMENTS

## 目的

このSkillの目的は以下の2つ。

1. リソース設計として妥当かレビューする
2. 設計上の判断のうち、Design Decision / ADRとして記録する価値があるものを抽出する

設計を全面的に作り直すことが目的ではない。
ユーザーが自分で設計した内容をレビューし、設計上の問題や検討不足を指摘すること。

---

# 1. リソース設計レビュー

対象ファイルを読み、以下の観点でレビューする。

## リソースの抽出

- 要件に存在する重要な概念がリソースとして表現されているか
- DBテーブルをそのままリソースにしていないか
- UI単位や処理単位だけでリソースを決めていないか
- 独立した識別子を持つべき概念が適切に独立しているか
- 不必要に細かくリソースを分割していないか

## リソースの粒度

- 1つのリソースが複数の異なる責務を持っていないか
- 逆に、本来1つとして扱えるものを過剰に分割していないか
- ライフサイクルが異なる概念を同一リソースにしていないか

## リソース間の関係

- 親子関係
- 所有関係
- 参照関係
- 多対多関係
- 集約関係

について、要件との整合性を確認する。

URIの階層だけを見て関係を判断せず、
ドメイン上どのような関係なのかを確認する。

## 読み取りリソース

以下が必要に応じて表現されているか確認する。

- 個別リソース
- コレクションリソース
- 検索結果
- 絞り込み
- ページング
- 集約結果

## 書き込み・状態変更

状態変更について、以下のどちらとして扱うべきか検討されているか確認する。

- 既存リソースの状態変更
- 独立した書き込みリソース / ファクトリーリソース

単に「POSTだから書き込みリソース」と判断しない。

重要なのはHTTPメソッドではなく、
その操作自体をリソースとして表現する価値があるかどうか。

## URI

- リソースを名詞として表現しているか
- 操作名を不必要にURIへ入れていないか
- URI階層が深くなりすぎていないか
- 親子関係をURI階層で表現する必要が本当にあるか
- URIから内部DB構造が過度に露出していないか

# 2. ADR候補の判定

すべての設計内容をADRにしてはいけない。

以下の条件を満たすものだけをADR候補とする。

## ADRにする価値が高い判断

### A. 複数の妥当な選択肢が存在した

例:

- 独立リソースにする / 既存リソースに含める
- 状態として表現する / 独立した書き込みリソースにする
- ネストURI / フラットURI
- 1つのリソース / 複数リソース
- 同期処理 / 非同期処理

### B. トレードオフが存在する

一方の案を採用すると何かが良くなる一方で、
別の何かを諦める必要がある判断。

例:

- URIの分かりやすさ vs 疎結合
- シンプルさ vs 拡張性
- RESTとしての一般性 vs ドメイン固有の分かりやすさ
- 現在の要件への単純さ vs 将来の拡張

### C. 後から「なぜ？」と聞かれる可能性が高い

設計結果だけを見た人が、

「なぜこの構造にしたのか？」
「なぜ別の案にしなかったのか？」

と疑問を持つ可能性が高い判断。

### D. 将来変更すると影響が大きい

以下に影響する判断を優先する。

- API
- DB
- UI
- 認可
- 他リソースとの関係
- クライアント実装
- 将来の拡張

---

# ADRにしなくてよいもの

原則として以下はADRにしない。

- REST/APIの一般的な慣例をそのまま採用しただけ
- URIを複数形にした
- JSONフィールド名を決めた
- HTTPメソッドを通常の意味どおり割り当てた
- 明らかに選択肢が1つしかない
- 小さな命名判断
- 実装時に容易に変更できる判断
- 単なる設計書の説明

ただし、上記でも重要なトレードオフが存在する場合はADR候補としてよい。

---

# ADR候補ごとの評価

ADR候補には以下の3段階を付ける。

## High

ADRとして残すことを推奨。

条件:

- 複数の有力案がある
- トレードオフが明確
- システム構造への影響が大きい

## Medium

ADRにしてもよい。

条件:

- 選択肢はある
- 一定の設計意図がある
- ただし影響範囲は限定的

## Low

設計書に理由を一言残せば十分。
ADRは不要。

---

# 出力形式

以下の順番で回答する。

## 1. 総評

リソース設計全体について簡潔に評価する。

## 2. 修正・再検討すべき点

| 優先度 | 箇所 | 問題 | 理由 | 改善案 |
|---|---|---|---|---|

優先度:
- High
- Medium
- Low

問題がない箇所を無理に指摘しない。

## 3. ADR候補

| ADR候補 | 重要度 | 判断内容 | 比較すべき選択肢 | ADRにする理由 |
|---|---|---|---|---|

ADR候補がない場合は、
「現時点ではADRとして残すほど重要な判断はありません」
と明示する。

ADRを増やすこと自体を目的にしない。

## 4. ADRにしなくてよい判断

設計上の判断ではあるがADRにする必要がないものがあれば簡潔に示す。

## 5. ADRを書く場合の材料

HighまたはMediumのADR候補について以下を整理する。

### Context

なぜこの判断が必要になったか。

### Considered Options

どの選択肢が存在するか。

### Decision

現在の設計では何を選択しているか。

### Rationale

なぜその案が妥当か。

設計書に根拠が書かれていない場合は推測せず、
「根拠未記載」とする。

### Consequences

Positive:
- メリット

Negative:
- デメリット
- 将来的な制約

---

# 重要なレビュー方針

- ユーザーの設計意図を推測して事実として扱わない
- 根拠が設計書にない場合は「不明」とする
- 代替案があるだけでADRにしない
- 重要なトレードオフがある判断を優先する
- ADR件数を増やすことを目的にしない
- 小さなポートフォリオであればADRが数件でも問題ない
- 実装詳細ではなく設計判断を評価する
- 設計書とADRで同じ内容を重複して詳述しない

最も重要な判断基準は以下。

「面接で『なぜこの設計にしたのですか？』と聞かれたとき、
他にも妥当な選択肢があり、その中から理由を持って選択したと言えるか？」

YesならADR候補。
Noなら原則として設計書だけでよい。
