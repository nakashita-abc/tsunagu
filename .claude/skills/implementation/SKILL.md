# 実装の手順

このSkillは**順序とゲート**だけを持つ。層の責務・分割の判断基準といった**定義は持たない**。
正本は [docs/アーキテクチャ設計書.md](../../../docs/アーキテクチャ設計書.md)。本書に原則を書き写さない（正本が2つになると必ず片方が古くなる）。

各ステップは**前のステップを終えてから**進む。飛ばしたときは、飛ばしたことを明示する。

---

## 0. 前提の確認

| 確認 | 参照 |
|---|---|
| 依頼の内容が設計書に書かれているか | 設計書・[05_要件定義.md](../../../docs/05_要件定義.md)・[06_API設計.md](../../../docs/06_API設計.md)・[DB設計書.md](../../../docs/DB設計書.md)・[09_画面設計.md](../../../docs/09_画面設計.md) |
| 触るファイルが新構成か旧構成か | 設計書 §6「現状のコードの帰属」 |
| `web/app/**` を触るか | 触るなら `node_modules/next/dist/docs/` の該当ガイドを**先に読む**（Next.js 16.2.6 は流通情報と差異がある。`web/AGENTS.md`） |

**設計書に書かれていないものを実装しない。** 書かれていない／設計書と食い違うと判断したら、**コードより先に設計書を直す**。設計書の変更が必要だと分かった時点で手を止め、変更案を提示する。

**旧構成のファイルを触るときは、ついでに移行しない。** 設計書 §6 は移行を別タスクと定めている。今回の依頼に必要な変更だけを、そのファイルの現在の場所で行う。新規ファイルは新構成（`lib/model/` `lib/service/` `lib/repository/<name>/` `lib/shared/`）に置く。移行が必要だと判断した場合は、実装を止めて移行タスクとして切り出すことを提案する。

## 1. 層の確定

**コードを書き始める前に、次を宣言する。** 責務の分離はここで決まる。書きながら決めない。

```
層:        Presentation / Service / Repository / モデル / 共有 のどれか
ファイル:  追加・変更するファイルのパス
契約:      触る interface と入出力型（Repository を触る場合）
根拠:      その層に置く理由（設計書 §2 の「やること／やらないこと」のどの行に当たるか）
```

複数の層にまたがる場合は、**層ごとに分けて**宣言する。

判断に迷ったとき:

- 層の責務と禁止事項 → 設計書 §2
- 層ではない置き場所（モデル・共有）の条件 → 設計書 §2-4・§2-5。迷ったら層のどれかに置く
- Service が1行の委譲だけになっても層を飛ばさない → 設計書 §2-2

## 2. テスト先行（実装前のテスト実行）

実装より先に、**振る舞いをテストで書く**。書いたら**実装前に `cd web && npm test` を実行する**。

**期待する結果は「新しく書いたテストだけが落ちる」。**

| 実行結果 | 判断 |
|---|---|
| 新しいテストだけが落ちる | 正常。実装に進む |
| 新しいテストが通ってしまう | テストが振る舞いを押さえていない。テストを直す |
| 既存のテストが落ちている | **着手前から壊れている。** 実装に入らず、この事実を先に報告する |

テストの書き方:

- 対象は層の外から見た振る舞い。内部実装の形をテストに固定しない
- 正常系に加えて**境界と失敗系**を書く（未認証・期限切れ・他施設・他入居者・空の一覧・カーソルの末端）
- `web/app/**/page.tsx` のテストは現状書けない（`vitest.config.ts` が `environment: "node"`。設計書 §7）。画面を触る場合は、テストを書けない範囲を明示する

### 振る舞いを変えない変更の場合（リファクタ・移行・ファイル移動）

先に落ちるテストは書けない。代わりに次の手順を踏む。

1. 変更前に `npm test` を実行し、**通ることを確認して結果を記録する**
2. その箇所にテストが無い場合は、**現在の振る舞いを写し取るテストを先に書き、通ることを確認する**
3. 変更後、**同じテストが同じ結果で通る**ことで担保する

テストを書かずに振る舞いを変えない変更を行わない。「変えていないつもり」は担保にならない。

## 3. 実装

宣言した層・ファイルの範囲内で書く。範囲を超える必要が出たら、ステップ1に戻って宣言し直す。

分割するか・共通化するかの判断は **設計書 §5「分割の判断基準」に従う**。要点だけ再掲せず、迷ったら §5 を読む。特に次の2点を取り違えやすい:

- 共通化は同じ処理が**3回目**になってから。2回目では抽象化しない
- **1ファイル300行は上限ではなく点検の観測点。** 超えたら責務の混在を確認し、混在していなければ分割しない。行数を理由にファイルを割らない

## 4. 検査

**検査の対象は今回の差分だけ。** 既存のコードは設計書 §2 に違反している箇所がある（`app/**` からの `getDb` 直呼び等）。それらは §6 の移行対象であって、今回直す対象ではない。**既存の違反を見つけても、今回の依頼に含まれないなら直さず、報告だけする。**

### 4-1. 層の境界（アーキテクチャの崩壊を防ぐ）

差分で追加・変更した import 行を見る。

```bash
# リポジトリルートで実行する
git diff -U0 HEAD -- web/app web/lib | grep -E '^\+.*(import |from ")'
```

| 層 | 差分に現れてはいけないもの | 根拠 |
|---|---|---|
| Presentation `app/**` | Repository の直接呼び出し（`@/lib/repository/*`・`@/lib/db`・`stub`・`postgres`）。データ取得は Service 経由 | §2-1 |
| Presentation `app/**` | 保存方式に依存する処理（`resolvePhotoUrl`・カーソルの符号化） | §2-1 |
| Presentation `app/**` | ビジネス規則の条件分岐の中身（期限・権限の判定そのもの） | §2-1 |
| Service `lib/service/**` | `next/server`・`next/headers`・`NextRequest`・`NextResponse`・`cookies()` | §2-2 |
| Service `lib/service/**` | HTTP ステータス・Problem Details の組み立て、SQL／S3／Cognito の直接呼び出し | §2-2 |
| Repository `lib/repository/**` | `next/*` 全般、HTTP ステータス、ユースケースの手順 | §2-3 |
| モデル `lib/model/**` | **import 文そのもの**（型のみ・ふるまいなし・他を参照しない） | §2-4 |

```bash
grep -rn "^import\|function " web/lib/model 2>/dev/null   # 何も出ないのが正常
```

**逆向きの import は禁止**（§1）。Service → Presentation、Repository → Service の向きが差分に無いこと。

Route Handler にビジネスロジックを書いていないかは、この表の Presentation 3行で判定する。「書かない」という心構えではなく、**import とベタ書きされた条件分岐の有無**で見る。

### 4-2. テナント境界（NFR-47）

**ここは様式の問題ではない。間違えると施設間でデータが漏れる。**

| 検査 | 根拠 |
|---|---|
| `facilityId` をパス・クエリ・ボディから受け取っていないか。セッションから解決したものだけを使っているか | NFR-47、§4-1、06_API設計 §0 |
| Repository の入力型に `facilityId` が**必須**で入っているか（省略可能にしていないか）。全クエリに施設の絞り込みがかかっているか | §4-2 |
| クライアントに送らせている識別子が、同一施設内で自由に選べるものだけか（`staffId`・`familyMemberId` を送らせていないか） | NFR-41・NFR-42、§4-3 |
| 家族向けのクエリに `familyMemberId` の絞り込みがあるか | NFR-41、§4 |

### 4-3. YAGNI と型

| 検査 | 不合格のときの対処 |
|---|---|
| 差分の中に、**今回の依頼で一度も使われない**引数・オプション・分岐・export・型パラメータがあるか | 消す |
| 追加した interface に、**今は誰も呼ばないメソッド**があるか | 消す |
| 「将来必要になるから」を根拠にした抽象・設定・フックがあるか | 消す。先回りしない（§5） |
| `any` を使っていないか | 型を付ける（CLAUDE.md 禁止事項） |
| `process.env` を直接読んでいないか（`lib/shared/env.ts` 経由か） | §3 の getter を使う |

YAGNI の判定は「将来使うか」ではなく「**今回の差分とテストから呼ばれているか**」。呼ばれていないものは消す。

1つでも満たせないものがあれば、実装を完了としない。

## 5. 完了判定（実装後のテスト実行）

```bash
cd web && npm test        # 全て通る
cd web && npm run lint    # 新たな警告を出していない
```

加えて次を報告する。

- **実装前（§2）と実装後の実行結果の対比**。前は何が落ちていて、後は何が通ったか
- 書いたテストが**どの境界・失敗系を網羅したか**を1行で（カバレッジは `@vitest/coverage-v8` 未導入のため現状測れない。設計書 §7。数値の代わりに根拠を言葉で示す）
- ステップ1で宣言した層・ファイルと、実際の差分の**ずれ**（あれば）
- 設計書との食い違い、テストを書けなかった範囲、残した暫定処置、見つけたが直さなかった既存の違反

テストが落ちている・lint が通らない状態を「完了」と報告しない。落ちているなら落ちていると出力付きで言う。
